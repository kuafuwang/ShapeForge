## 2. 真实 Host Tiling

`msl-bundle` 候选的 `host_tiling` entry 是一个闭集 JSON 计划：

```json
{
  "schema_id": "tcenv.metal.host-tiling.1",
  "schema_version": 1,
  "writes": [
    {"workspace": "scratch", "kind": "linear", "start": 0, "step": 1,
     "count": "M", "stride": "H", "offset": 0, "dtype": "fp16"}
  ]
}
```

`HostTilingPlan.from_candidate` 只接受唯一的 `host_tiling` entry，拒绝未知字段、未知 workspace、dtype 不符和空 writes。`execute` 在 CPU 上按计划写 workspace；`msl-bundle` 的 device kernel 读取 `scratch[tg * H]` 作为行号，因此 Host Tiling 不是“改名的 device 初始化核”，也不是参考实现或输入预处理。

`CandidateLifecycle` 的 host step 是生产要求：候选带 `host_tiling` entry 但没有 host step 时，`validate_for` 在构建/执行前报错。`bundle.json` 归档了实际 host 执行记录（`host_runs[0].writes == 128`），`dispatch` 只包含 device stage；Host Tiling 本身没有假装成 device dispatch。

`zero:false` 的 workspace 在计时中不清零，Host Tiling 在计时外写一次；`zero:true` 的 workspace 在计时内清零，Host Tiling 必须在 `inside_timing` 中由 runtime 在清零之后执行。固定测试 `test_a4_declared_zero_workspace_is_cleared_inside_timing_and_host_tiling_restores_it` 同时覆盖后者。

## 3. read_write、workspace 与 timing 协议

v2 路径不经过 legacy `testing.py` 的“只在 out1 前恢复一次”逻辑，而是：

- `V2ArgSet` 按 ABI 分配 global 与 workspace 的真实 span；workspace 大小不由候选自报。
- `correctness_launch_plan` 产生逐 trial 的 fill plan：纯输出 poison/zero/poison，`read_write` 初值在每个 trial 前 `RESTORE_INITIAL`；`read_write` 终值是结果，参与差分和 unwritten 统计排除。
- `benchmark_launch_plan` 产生 benchmark fill plan；只有 geometry 声明 `zero:true` 的 workspace 在计时内清零，`zero:false` 不清零。
- Host prepare 的计时边界由 lifecycle `inside_timing` 决定；`zero:true` 时 `fill_workspaces` 先独立 commit/等待 GPU 完成，再在 CPU 执行 Host Tiling，最后提交 device 命令缓冲。`pre_dispatch` 这种“编码阶段写 CPU”的假顺序已删除。
- benchmark 连续 reps 不重置 guard；reps 后只做 guard/硬件状态检查，不做输出终值差分。第二次 launch 才越界的固定负例必须保持可见。
- `workspace_size_problems` 在分配前比较 launch workspace 与 ABI span；`V2ArgSet` 的证据字段 `workspace_bytes`、`workspace_zero`、`workspace_fills` 来自真实 ABI/geometry。

固定节点：

- `test_a4_read_write_initial_values_are_restored_on_every_trial`：真实三 trial；`y`/`acc` 初值每次都恢复，终值参与比较。
- `test_a4_declared_zero_workspace_is_cleared_inside_timing_and_host_tiling_restores_it`：`zero:true`、host inside timing、benchmark 全部真实。
- `test_a4_workspace_size_mismatch_is_refused_before_allocation`：`M*2=128` 对 ABI `65536` 的负例。
- `test_a4_host_tiling_plan_is_closed_and_required_not_a_renamed_kernel`：空 writes 计划被拒绝。
- `test_a4_a_bundle_that_ships_host_work_cannot_skip_its_host_step`：带 host entry 但没有 host step 的候选被拒绝。

## 4. 实际 dispatch、Derived Scalars 与反射

`MetalV2Runtime._bind` 从编译后的 kernel 取 Metal reflection，调用 `stage_binding.bind_pipeline_arguments` 按名解析每个 stage 的参数；Derived Scalar 不写死 binding slot，而由 `V2ArgSet.stage_args` 生成 `ScalarArg`，在真实 `setBytes` 路径写入。

`test_a4_derived_scalar_is_set_by_name_and_inactive_when_stage_is_not_dispatched` 的 kernel 只有在 `BLOCKS == 2` 时才写结果；测试同时断言：

- `result.execution["bindings"]` 有 `BLOCKS` 的 `role="derived_scalar"`, `value=2`；
- `when=false` 的第二个 stage 没有出现在实际 dispatch 记录中；
- 真实 runtime 只 dispatch 激活 stage。

`test_track_protocol.py` 与 `test_track_plane.py` 已加入 A4 固定 CPU 节点，覆盖 A2 协议/平面，而不是只靠 A4 测试替身。

`A4/evidence/` 归档七个 JSON：

- `single.json`、`bundle.json`、`newop.json`、`fusion.json`、`multistage.json`：候选/几何/bundle/artifact/native 摘要、canonical bundle、`execution_geometry.json` 的 SHA-256、真实 dispatch、`bindings`、workspace 字节/zero/fills、provider。`single.json` 另记 `presentation_sha256`、控制机冻结的 `track`（id/version/track_digest/registry_digest）与 worker 实际发布的 `worker` 身份。
- `derived.json`：`BLOCKS` 派生标量绑定值、inactive kernel 为空。
- `readwrite.json`：`y`/`acc` 的 `read_write` access 与真实 dispatch。

`verify_evidence()` 要求本次真实运行与归档逐字段相等，并检查：

- single dispatch 恰为 `rmsnorm_single`；bundle 恰为 `rmsnorm_bundle`，Host Tiling 由 `host_runs` 证明；
- single 的 TrackSpec digest/`track_version`/registry digest 等于 shipped `tracks.json` 的登记，worker 的 track digest/registry digest/`presentation_sha256` 逐项等于控制机冻结值；
- `bundle.workspace_bytes["scratch"] == 65536`、`workspace_fills == []`、`host_runs[0].writes == 128`；
- derived 的 `BLOCKS.value == 2`，inactive kernels 为空；
- readwrite 参数含 `access == "read_write"`；
- fusion 两个候选 candidate/geometry/bundle/artifact 均不同，实际 threads 分别为 128/256，replay stable。

## 6. 固定负例与自检

`A4/verify.py` 固定 37 个负例节点，覆盖：缺 `taic-launch`、fallback/grid 偏离、Host 未执行、workspace 大小/未声明、Host 计划闭集、A2 protocol/plane、宿主路径 include、stuck launch/stuck compile、超时/崩溃无 full build、报告 status 与 build 形状错配、worker build 缺失/额外/重复/别名 artifact entry、单文件 SOURCE path/media_type 漂移、partial 非 native `build_kind`、冻结 Track 读默认 registry/摘要漂移/渲染漂移、父进程编译边界、worker Track/build 漂移、编译失败 partial 等；另有真实 read_write、Derived Scalar、zero workspace 的固定正例 GPU 节点。新增的五个 CPU 负例分别固定：`EvalReport` 的 ok/compile_error/timeout/crash 与 partial/full 闭集对应；父进程用 canonical bundle 重算 artifact set 后拒绝缺失/额外/exact duplicate/casefold alias/decomposed-NFC alias entry；外部 worker 崩溃时报告没有 full build 且 `artifact_set_digest`/`native_digest` 为 null；单文件 SOURCE 必须逐项等于 canonical candidate entry（改名 path 或改 media_type 都拒绝）；compile_error partial 仍必须是 native build（simulator/source_only 拒绝）。`self_test()` 可独立重放三项 CPU 负例：

1. `msl-single` 缺 launch 被拒绝；
2. dispatch/fallback parity 对错误 grid/provider 可见；
3. `sigmoid_shift` 从 `tasks/` 自动发现，无需中央清单。

`verify.py` 不是只看固定 pytest 集合返回码；它读取证据字段并和归档比较。
