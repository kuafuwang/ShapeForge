## 6. 复核修正（R3-1b，2026-10-29）：Specialization 绑定、投影强制、AST/别名与 GPU spy

复核指出 §1–§2 的三处实质缺口，本节修正并以 CPU 用例锁定。

### 6.1 R-3-1：候选工厂没有收到 Specialization

- 事实：`artifact_builder(...)` 只接 contract/math/kernel_names，`evaluate.py`/`xcworker.py` 也没传
  Specialization，违反 §5.1（工厂输入含 Specialization）与 §5.3-2（LoweringProfile 登记名与 R1 `lower`
  同源）。
- 修正：
  - `Backend.artifact_builder(..., specialization=None)`（协议与 Metal 实现）；
  - `MetalSourceBuilder(specialization=…)`：带 Specialization 时**契约必须是同一对象**
    （`kernel_contract` 与之不同即 `ValueError`），诊断 profile 与 Specialization **互斥**；
    `build()` 时契约不是那份 Specialization 的契约 → `BuildError("toolchain_profile")`（组合根错误，
    不归责候选）；`lowering_identity` 暴露 `{opspec_digest, lowering_profile_digest}`，无法构造
    “任务身份”的 build 拿到 `None`。
  - `tcenv/evaluate.py`、`tcenv/xcworker.py` 传 `specialization=task.specialization`。
- 证据（CPU）：`test_a_candidate_build_is_bound_to_the_specialization`（正例：`builder.specialization is
  task.specialization`、`lowering_identity` 与 Specialization 逐字段相同；负例：诊断+Specialization 互斥、
  两份契约拒绝、build 时换成另一题的契约被拒）与
  `test_the_evaluator_hands_the_task_specialization_to_the_factory`（FakeNpu，记录工厂**实际收到的**
  关键字参数：`specialization is task.specialization` 且 `kernel_contract is task.contract`）。

### 6.2 R-3-2：`require_build_error_projection` 不在生产路径上；FakeTsm builder 附件缺失

- 事实：该检查只在测试里调用，`evaluate.py` 对任何 `BuildError("compile")` 直接产出候选
  `compile_error`；`tests/support/vendor_sim/module_builder.py` 的 `TXCC_FAIL` 路径抛不带 provenance /
  assembled digest 的 compile 错误。
- 修正：
  - `tcenv/evaluate.py`：映射到 `compile_error` **之前**强制 `require_build_error_projection(e)`；不通过则
    改判 `BuildError("toolchain_profile", "… not projectable …")`（基础设施失败、worker crash、build=null），
    绝不伪造 partial、绝不归责候选。
  - `tests/support/vendor_sim/module_builder.py`：`TXCC_FAIL` 带 `BuildProvenance(…, artifact_set_digest=None)`
    与 `assembled_sha256`（顺带修掉一个函数内 import 造成的 `UnboundLocalError`）。
- 证据：`test_every_registered_candidate_builder_carries_the_projection_on_compile_failure` 逐个覆盖
  **全部三个能产出候选报告的登记 builder**（生产 `MetalSourceBuilder` 用设备/编译替身、`FakeNpu`、
  `FakeTsm`），每个都断言 `error_class=compile`、provenance 非空且 `artifact_set_digest is None`、
  `assembled_sha256` 非空；`test_the_evaluator_refuses_to_blame_the_candidate_for_an_unprojectable_compile_error`
  证明缺附件时报告映射变成 `toolchain_profile` 而不是 `compile_error`。

### 6.3 R-3-3：结构检查仍是子串；GPU spy 计数把 internal-fill 算进候选

- 事实：`test_every_production_build_call_site_goes_through_the_factory` 用 `"artifact_builder(" in text`
  这类子串；属性扫描不跟踪 `compile = ctx.compile; compile(...)` 别名；`test_build_path_gpu.py` 的 spy
  同时包住 internal-fill 与候选工厂却断言 `len(calls) == 1`（真机 fresh context 会记录两次）。
- 修正：
  - 工厂检查改为 AST：解析出真实的 `artifact_builder(...)` 与 `.build(...)` 调用节点，要求二者都存在、
    `build` 在工厂之后，且候选调用点（evaluate/xcworker）**带 `specialization=` 关键字**；直接
    `MetalSourceBuilder(...)` 仍算失败。
  - 新增 `_alias_of_forbidden()` + `_alias_offences()`：跟踪 `x = ctx.compile` / `x = getattr(ctx,
    "compile")` 之后的 `x(...)` 调用，并按“所在函数”套用同一白名单；
    `test_a_compile_alias_is_a_bypass_and_is_reported` 先用三段合成源码做**检查器自检**（别名、`getattr`
    别名、`compile_all` 别名各一），再扫全生产树。
  - `tests/backends/metal/test_build_path_gpu.py`：把 spy 记录分成 `diagnostic`（`diagnostic_profile`
    非空）与 `candidate` 两类，分别断言——诊断侧恰好一次、profile 是 `metal.internal-fill`、
    `kernel_name == taic_fill_zero`、无 Specialization；候选侧恰好一次、`kernel_contract is task.contract`、
    `specialization is task.specialization`、`diagnostic_profile is None`、候选字节仍等于原文。

## 7. 复核修正（R3-1c，2026-10-29）：null `assembled_sha256` 不得投影成候选失败；第二处 GPU spy 分流

复核指出上一轮修正仍留一个缺口：`require_build_error_projection` 接受 `assembled_sha256=None`，于是
"合法 provenance + null digest" 的 `compile` 失败仍被映射成候选 `compile_error`。这条路径上不可能出现
合法的 null：`_evaluate_in_process` 从 Python `str` 出发、自己 `encode("utf-8")`，装配一定已发生。

### 7.1 修正

| 位置 | 变更 |

| `tcenv/remote/artifact_builder.py::require_build_error_projection` | 新增关键字 `require_assembled: bool = False`：为真时 `assembled_sha256 is None` 直接 `ValueError`，错误信息说明“这条构建路径一定先装配，null 只描述 builder API 的预装配拒绝”。默认模式（builder API / 直接调用）仍允许 null，保住非 UTF-8 字节那条唯一合法情形 |

判定链现在是：`compile` 失败 →（provenance 缺失 / artifact_set_digest 非空 / source 摘要空 / **digest 为

### 9.1 R-3-4：spy 装在了评测器不会使用的实例上

- 事实：`tcenv.evaluate` 经 `registry.load_backend(profile.backend)` 取 backend，而 `load_backend` 每次
  新建实例；用例里 `_record_builds(monkeypatch, MetalBackend(), …)` 装的是一个自己 new 的实例，
  真机上 candidate 记录必为空、fresh context 的 diagnostic 计数也对不上（复核用只读检查确认
  `spied_is_evaluator_backend: False`）。
- 修正（`tests/backends/metal/test_build_path_gpu.py`）：`_install_spy()` 先 `load_backend("metal")` 拿到
  实例、在**该实例**上装 spy，再把 `tcenv.backends.registry.load_backend` monkeypatch 成返回同一实例，
  因此“被 spy 的 backend”与“评测器拿到的 backend”是同一个对象；两个用例都改用这个 helper，文件里不再
  出现自己 `new` 的 `MetalBackend()`。
- 接线自检（CPU，`tests/backends/metal/test_diagnostic_builds.py`）：
  `test_the_spied_backend_must_be_the_one_the_evaluator_obtains` 先用“registry 交出的实例 = 被 spy 的实例”
  作正例确认记录出现，再用“registry 交出 A、spy 装在 B”复现失败形态，断言 B 上**零记录**——这个用例
  在接线错误时会立刻失败，不需要设备。

### 9.2 R-3-5：候选关键字用下标取，且第二条用例缺身份断言
