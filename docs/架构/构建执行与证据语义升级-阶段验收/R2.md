### 3.2 必须同时做的结构调整

> **H-19（IEEE 路径）**：在完成 `ieee_*`/`domain_case` 迁移前，先补上真正走 `prepare_case`/`inject_specials` 的旧/新对照（Metal 层），否则 IEEE 域只是名义上被覆盖。

1. **attr vs constant 的切分**：语义常量（rope `BASE`、lion `LR/WD/BETA1/BETA2`、FA `SM_SCALE`）进 OpSpec
   `attrs`（有 dtype/domain/default），启动/tiling 常量（`BLOCK_*`、`M_TOTAL`、`K_TOTAL`、`OH/OW`、`BLOCK_S`）
   进 profile `constants`（`symbol:`/`product:` 来源）。判据：改它会改变语义 → attr；只改变启动/分块 → profile。
2. **`Task.meta` 收敛为派生视图**：`ieee_base`/`ieee_inputs`/`ieee_max`/`domain_case` 迁到 OpSpec
   `cases.inputs`（schema 已支持 `inputs.<case>.*`，允许 `_` 前缀域键），`tcenv/backends/metal/testing.py` 与
   `tcenv/triton_runner.py::spec_fingerprint` 改为从 `task.semantic_instance.case_domain.inputs` 读取；
   `Task.meta` 若保留只能是由 OpSpec 物化的只读镜像（否则就是第二份输入域合同）。
3. **variant factory**：`parse_variant` 的文法、默认 alias 与约束登记为 `metal.gemm`/`metal.flash-attention` 的
   variant factory（id+version），由它结合语义实例产生具体 `LoweringProfile`（GEMM tile 必须整除 M/N/K，
   FA `BLOCK_M/N` 约束），非法文法拒绝；profile 不逐个登记进 `ArtifactBuilderRegistry`。
4. **`gen_*` 族**：`tasks/generated/elementwise.toml` 的表达式 → 确定性生成 `tasks/generated/<name>/opspec.json`
   （公式/数值规则全部进 JSON 与 `opspec_digest`），装配只读 OpSpec；TOML 退出。
5. **`sem_*` 族**：`tasks/semantic.py` 的 `IntProgram` 语句/数值规则与 `sem_gemm_neg`/`sem_attention_odd_scale`
   的构建后改写变成显式语义 + track 装配；`sem_int_<seed>` 的 dtype 别名 `{fp16,bf16,i32}→i32` 登记，其他拒绝。
6. **删除两处 `gpu` 覆盖**：`taic/orchestrator.py::Orchestrator.__init__` 与 `tcenv/cli.py::cmd_show` 的
   `replace(..., gpu=target.display_name)`（R1 已让目标名来自 profile，删除后 `N-2` 才成立）。
7. **`tcenv/evaluate.py::_callable_identity`（§4.4-4 / R0 清单第 13 项）**：仍对闭包 `defaults`/`repr` 取任意文本做身份，
   必须换成登记 `{implementation_id, implementation_version, params}` + pack digest，并删除该 repr 旁路；
   这是 R2 的删除项，不只是 R4 的清理项。
8. **`Task.meta`/`error_scan` 之外的登记补齐**：`mlx_compile`/`torch_compile`/`torch_half`/`mlx_half_compile`
   这些 baseline 也要有 `{implementation_id, implementation_version, params}`，否则 §7.2 的实现摘要不完整。

### 11.2 `sem_int` 视图与声明规则不一致（四处，均实测）

1. **`tasks/sem_int/program.py::_triton_stmt` 的 `mod` 渲染硬编码掩码**：`mod` 分支写
   `(({a}) & 0x{(1 << 31) - 1:X}) % {const}`，`triton_source` 只把 `hash_shift`/`loop_shift` 传下去，
   **没有**把 `rules["mod_mask"]` 传进渲染器。实测：把文档 `rules.mod_mask` 改成 `0x3FFFFFFF` 后
   `triton_source` 文本不变，`msl` 与 `evaluate` 都变——单一 stale view。
2. **`evaluate` 的 wrap 不是按语句 kind 取值**：`bin`/`sbin` 共用 `apply_wrap("bin", r)`，因此 `sbin`
   的 wrap 归属被 `bin` 代偿；`shr`/`mod`/`where`/`max`/`min` 则完全不看规则表。实测：把 `sbin` 移进
   `plain_kinds`、`shr` 移进 `wrap_kinds`（OpSpec 校验器**接受**该分区，因为覆盖完整且不重叠）后，
   `evaluate` 输出与默认规则**逐字节相同**——声明规则被无声忽略。
3. **`msl` 完全没有规则表版本/分区校验**：同一次 wrap 分区改写后 `msl` 文本逐字节不变，不报错；
   `triton_source` 只有一句裸 `assert wrap_kinds == set(WRAP_KINDS)`（`-O` 下会被剥掉，且是
   `AssertionError` 不是 `ValueError`）。`evaluate` 没有任何版本/分区校验。
4. **`tasks/sem_int/document.py::FORMULA` 与可编辑 `index_mask` 冲突**：`FORMULA` 是模块级常量，正文写死
   `(idx[i] & 7)`；文档里的 `rules.index_mask` 可编辑且已被三份视图读取。两者可以分叉，形成第二份语义事实。

**必须达到的终态**（二选一，逐视图分别成立，不能靠“比较元组”让某一个 stale view 混过去）：
每份视图要么**读取**声明值，要么在声明值超出它实现的闭集时 **fail closed**（`ValueError`，不是 `assert`）。

**必须新增的用例**（`tests/shared/test_sem_int_family.py`，逐视图独立断言）：

- `mod_mask`：正例（`mod_mask` 与语句 `const` 相容，如 7）三份视图都**变**，且 `triton_source`/`msl`
  文本里出现由文档值渲染的字面量；负例（`mod_mask` 为负或 ≥2^31）三份视图各自拒绝；
- wrap/plain：正例（登记默认分区）三份视图都接受；负例（把某个 kind 在 wrap/plain 之间搬动）
  **每份视图各自**拒绝或各自如实改变输出——不允许“只有一份视图报错、另一份静默忽略”；
- `index_mask`：`FORMULA` 必须由同一份规则表派生（改 `index_mask` ⇒ 文档 `formula` 与渲染/求值同向变化），
  不得留下模块级写死常量。

### 11.3 种子域漏检文本长度

`tasks/sem_int/task.py::parse_seed` 只判 `suffix.isdigit()` 与数值 `< 10**18`，因此
`sem_int_` + 18 个 `0` + `1`（19 位、leading zero）被接受并解析成 `1`（实测输出 `1`），与
`GENERATOR_PARAMS`/`SEED_DIGITS_MAX` 登记的“至多 18 位 ASCII 十进制数字”不一致。要求：按登记域限制
**位数**（`len(suffix) > SEED_DIGITS_MAX` 拒绝），保留 `sem_int_007` 合法别名（实测仍解析为 7），
新增超长负例（19 位、全部 leading zero 的 19 位、以及边界 18 位必须仍被接受）。

## 15. 复核修正（R2-5b，2026-10-29）：ASCII 数字与 `loop` 分区

复核指出 §12 的两处“已修”不成立，实测复现并在本节修正。**§12.2 表格里“`evaluate` 如实实现任意分区”
那句是错的**：本文上文保留原样以留痕，正确的结论见 15.2。

### 15.1 R-2-1：`parse_seed` 只查“是不是数字”，没查是不是 ASCII

- 复现：`parse_seed("sem_int_١")`（ARABIC-INDIC ONE）返回 `1`。`str.isdigit()` 对 Unicode 十进制数字为真，
  于是 `sem_int_١` 被当成 `sem_int_1` 的别名，走进登记域之外的题目名。
- 修正（`tasks/sem_int/task.py`）：后缀改为显式 ASCII 校验（`character not in "0123456789"`），空后缀同样拒绝。
- 负例（`tests/shared/test_sem_int_family.py`）：`sem_int_١`、`sem_int_۱`（EXTENDED ARABIC-INDIC）、
  `sem_int_１`（FULLWIDTH）、`sem_int_1١`（混写）、`sem_int_²`（superscript，`isdigit()` 为真但非十进制）
  同时断言 `parse_seed` 与 `get_task` 两条路径都拒绝；并保留“`int("١") == 1` 且 `"١".isdigit()`”这一行，
  证明只查数值或只查 `isdigit()` 都会漏。

### 15.2 R-2-2：`loop` 每轮内部回绕，所以 reference 也不能“实现任意分区”

- 复现：把 `loop` 从 `wrap_kinds` 移到 `plain_kinds`（OpSpec 校验器接受该分区），`evaluate` 的参考输出与
  默认规则**逐字节相同**——因为 `loop` 的每一轮 `wrap(wrap(acc*const)+b)` 写在循环体里，登记分区只影响
  最后那次 `apply_wrap`。§12.2 声称的“参考可如实实现任意分区”因此不成立。
- 判定：`loop` 的逐轮回绕是**登记算术**的一部分（Triton/MSL 的 int32 运算天然如此），没有哪个视图能表达
  “loop 不回绕”的分区。故终态改为：**三份视图一致 fail closed**。
- 修正（`tasks/sem_int/program.py`）：`_render_rules` → `_implemented_rules`，`reference` 也过同一道闸门
  （声明分区必须等于登记分区，否则 `ValueError`，错误信息点名 `loop` 的逐轮回绕）；循环体处加注释说明
  回绕为何属于登记算术。
- 负例（同一测试文件）：`loop`/`sbin`/`shl` 三种 kind 各取一份语句，先证明登记分区下参考可正常求值
  （正例），再证明搬到 plain 后 **triton / msl / reference 三者都拒绝**（`refused(...)` 逐视图断言）。
  §12.2 的“`evaluate` 实现任意分区”一行随之更正为“读取登记分区；非登记分区拒绝”。
