## 1. 唯一的纯函数比较器（§7.2）

`taic/policy.py`：

- `build_identity_view(report)` / `evaluation_identity_view(report)`：从 schema-4 报告**只读**投影身份，
  缺字段保持 `None`，不读文件、不补写。
- `compare_confirmation_identity(candidate_sha256, expected, search, confirmation)`：
  - `build` 比较 `candidate_sha256`、`assembled_sha256`、`opspec_digest`、`lowering_profile_digest`、
    `artifact_set_digest`、`native_digest` 与 `provenance.*` 全字段；
  - `evaluation` 比较 `evaluation_fingerprint`、两条 baseline 摘要、protocol/target/backend/version 与
    可选 `device_name`/`gpu_family`（`task_fingerprint` 只在 evaluation fingerprint 内比较）；
  - 规则：任一侧与冻结 expected 不同 = `mismatch`（标明 `side`）；expected 缺、或一边有一边没有 =
    `unknown`；`simulator` 没有 `native_digest` 时该字段整体缺席不算 unknown（`optional`）；
  - **只有** `assembled_sha256`/`artifact_set_digest`/`native_digest` 这三个 outcome 摘要做两期比较；
    BuildProvenance 是当前执行器/registry 事实，`expected.build.provenance` 为 `None` 时它的每个字段都是
    `unknown`，绝不退化成“两份 evaluator 自报值互相相等”（§7.2）；provenance 嵌套字段展平为点分路径；
  - 主状态按 mismatch 先于 unknown、build 先于 evaluation、字段路径字典序；`differences` 全量保留并按
    `(domain, field, kind, side)` 排序。不含 handle、主机路径、凭据或异常 repr。

## 2. 唯一最终发布谓词（§7.2）

`taic/policy.py::confirmation_publication(result, confirm_report, batches, expected, bindings)`，纯函数：

- 先复用既有检查（result 形态、`confirmation_source_sha256`、`confirmed_status`/confirm status、
  best/winner 两处摘要、label、中位数与逐批值、confirm report 的 kernel/label/values/speedup/candidate_us、
  cache_hit、timing、`batches_agree`）；
- protocol/target **只与冻结 expected 比较**，不读当前 `PROTOCOL_VERSION`/target 注册表；
- 冻结 expected 缺失/为空 → `not_confirmed`（不拿当前环境补值）；
- 每个胜者批次必须：`result.confirmations` 里有**逐字节相同**的 identity 记录、`identity.kind == "match"`、
  `shape=full`、`build_kind=native`、`measurement_kind=measured`、`cache_hit=false`、计时安静；
- 出口闭集 `PUBLICATION_REASONS`（既有原因码 + `confirmation_ineligible` + 四个 `*_identity_*`；
  不新增自由文本）；`allowed = status == "confirmed"`。

## 3. 本地确认门（`taic/orchestrator.py`）

- `_confirmation_expected(cand)`：只调用执行器的 `confirmation_expected(...)`（`LocalEvaluator`
  注入版本或 `tcenv.evaluate.confirmation_expected_document`），**不读也不复制 `cand.report`**。expected 只含
  当前可重算分量：当前源码的 `candidate_sha256`、任务 `Specialization` 的 opspec/lowering、registry 重算的
  implementation/environment/fingerprint、`PROTOCOL_VERSION`/`target_id`/backend/version，以及执行器能给出的
  BuildProvenance（拿不到时为 `None`）。`assembled_sha256`/`artifact_set_digest`/`native_digest` 是
  outcome-only：不放进 expected，比较器只做两期比较。文档无 handle、无主机路径；CPU 侧 helper 不探测设备。
- `_confirmation_batch(cand, rep, expected)`：记录 `{label, shape, build_kind, measurement_kind,
  cache_hit, timing_uncertain, identity}`；本地 evaluator 的 measurement_kind 取 `measured`，远端取
  evaluator provenance（未知时 `unknown`）。
- `_confirmation_batch_status`：身份不是 match → 该身份状态；`shape != full` →
  `build_identity_unknown`；非 native/非 measured/缓存命中 → `confirmation_ineligible`；计时不稳 →
  `timing_uncertain`。
- 每批在 `values.append` **之前**检查；失败批次：`entry["status"]=状态`、`entry["identity"]` 全量差异、
  `_failure_record(..., kernel_error=False)` 写入 `rechecks/`（带 `identity`，不改 `rep.status`、不计
  `hangs`、不 append）、`failed_batches = batches - batch_index`、`stop=True`（停止该候选剩余批次与后续候选）；
  已完整确认的先前候选仍留在 `confirmed`。
- 胜者确定后调用一次 `confirmation_publication`：`confirm_report` 的
  `benchmark.confirmation` 写入 `kernel_sha256/winner_label/confirmed_values/speedup/candidate_us/
  expected/batches`；`allowed` 才写 `res.confirmed_status="ok"` 与 `confirm_report.json`，否则写谓词返回的
  `不确定`/`未确认` 并**不写**报告、`_finish` 不派生 `confirmation_source_sha256`。
- 通过的批次也写 `entry["identity"]`（`kind=match` + 资格摘要），读盘谓词因此能区分“全 match”与“记录缺失”。

## 4. 读盘路径（`experiments/common.py`）

- `_read_confirm_report`：拒绝重复键的 loader，且 `schema_version` 必须**恰为 4**（旧确认报告不迁移、不双读）。
- `_conclusion_verdict`：由磁盘算出绑定组（`best.metal`、胜者候选文件、confirm 报告 status、result 的
  `confirmation_source_sha256`），从 confirm 报告取**冻结 expected 与逐批记录**，调用同一个
  `confirmation_publication`；`allowed` 才给 `speedup`（逐批中位数）。
- `published_conclusion`/`_published_verdict`：没有 confirm 报告时不再宣称 `confirmed`（返回 `未确认`），
  关闭“`confirmed_status == "ok"` 就算发布”的旁路；`summarize(run_dir=...)` 走完整谓词。

### 8.1 投影格式（`taic/artifacts.py`）

`EVALUATION_CONTEXT_SCHEMA_VERSION = 1`、`EVALUATION_CONTEXT_FILE_NAME = "evaluation_context.json"`，
固定 8 键闭集 `{schema_version, request_id, request_digest, candidate, evaluator_epoch, device_group,
build_provenance, baseline_environment_digest}`：

- `evaluation_context_document(...)` 组装并校验写入形状；`device_group`/`build_provenance` 只在对应 dialect
  下非空，`baseline_environment_digest` 取自已接受报告（可为 `null`）；不补字段、不探测设备。
  `candidate` 通用 dialect 是源码摘要字符串，NPU dialect 只允许 `{algorithm, value}` 两键。
- `validate_evaluation_context(...)` 按闭集校验：未知键、缺失键、`schema_version` 不是 1（含 `bool`、字符串）、
  类型非法一律 `SchemaError`；可空字段允许 `null`。嵌套 dialect 文档只要求是对象，第二套 dialect 校验留给
  `load_completed_context` 与行/result 对账，不在这里重复。
- `read_evaluation_context(path)`：文件不存在返回 `None`，存在但不可读/重复键/JSON 非法/schema 不符一律
  **`NeedsInspection`**（经 `loads_strict` 拒绝重复键后再校验）。

### 8.2 公开只读 path helper（`taic/evaluation_outbox.py`）

`EVALUATION_OUTBOX_DIR_NAME = "evaluation_outbox"`、`ROW_STATES = ("missing", "pending", "completed")`，
一个共用的 `_request_key`（`sha256(request_id)`）让写入侧 `EvaluationOutbox._key` 与只读侧不可能各自实现：

- `EvaluationOutbox.row_path/result_path/row_state`（静态方法）+ 模块级 `row_state`：不构造 outbox、不校验 HMAC。
- `row_state` 三值：`missing`、`pending`（含 `unavailable`）、`completed`；行不可读、重复键、非对象、
  `request_id` 不符、status 不在闭集 → `NeedsInspection`。被改写的行不能伪装成“没评过”。

### 8.3 `_read_candidates` 与 `Candidate` 挂载

- `taic/resume.py::_read_candidates` 解析投影后用 `row_state` 查行：`completed` → 挂载投影、
  `evaluation_context_state="completed"`；`missing`/`pending` → **unknown**（`evaluation_context=None`，记一条
  note，不拒绝续跑）；没有投影文件 → `"local"`；投影或行损坏 → `NeedsInspection`。
- `taic/orchestrator.py::Candidate` 新增 `evaluation_context: dict | None`，`restore` 从快照候选传入。
  投影非 `None` 只说明“行存在且 completed”，不说明 HMAC/receipt 已校验——那一步在
  `load_completed_context` 之后。

### 9.1 实现（`taic/evaluation_outbox.py`）

## 15. 评审后的两个实质缺口（2026-10-29 晚，与 `R6.md` §7 同一轮）

1. **谓词接受批次记录不全**：`confirmation_publication` 只遍历现有 `batches`，不看它是否覆盖

成立，于是「报告与冻结 expected 都没写 protocol/target」被判为一致；`expected_report_identity` 的完整性
清单里也没有这两项，所以 `evaluation` 投影缺它们同样不报 unknown。

这不是纯理论的：`experiments/common.py::_read_confirm_report` 只校验 `schema_version`，报告与冻结
expected 都来自磁盘，删字段即可到达。评审实测：从 `synthetic_confirmation_documents` 的合法绑定里同时删除
报告与冻结 expected 的这两个字段后，纯谓词仍返回
`{'allowed': True, 'status': 'confirmed', 'reason': 'confirmed'}`，`conclusion_verdict` 仍返回
`speedup=1.2, publication='confirmed'`。违反主 plan §7.2「expected 至少含 protocol/target、expected 不完整即
unknown」与 F-28，说明 §20 的「expected 必须完整」没有覆盖到这一对字段。

## 25. 评审阻断第七轮（2026-10-30）：retained result 用普通 `json.loads` 读，重复键在闭包前丢失（已修，待复核）

### 25.1 缺陷

`taic/evaluation_outbox.py::_read_completed_result` 用普通 `json.loads` 解析 retained result 信封，随后才把
`result.report` 交给 `EvalReport.from_json`。`json.loads` 对重复键只保留最后一个值、不记得重复过，于是
「用拒绝重复键的 loader 先读、再交给 schema 闭包」这条 §6.4 规则在这里被绕过：向 generic completed result
的 report 写入两个合法的 `schema_version: 4` 后，`load_completed_context(...)` 仍返回上下文
（评审复现输出 `ACCEPTED_DUPLICATE True`）。既有 AST 登记只检查「哪个文件调用 `from_json`」，
看不到「先存 payload、再间接调用」的这条路径。

### 25.2 修复

- `_read_completed_result` 改用模块里既有的 `loads_strict(text, what=str(result_path))` 解析**整份** result
  信封；`SchemaError` 沿既有边界转成 `EvaluationUnavailable("outbox_corrupt", ...)`，再由
  `load_completed_context` 统一成 `NeedsInspection`/`result_invalid`，`begin()` 的 completed 重放直接抛
  `EvaluationUnavailable(code="outbox_corrupt")`。仍然**不改写**信封原文，host HMAC 照旧按原字节验证。
- `tests/shared/test_report_schema4.py`：`test_every_registered_report_reader_uses_the_strict_loader` 的严格
  reader 登记表新增 `taic/evaluation_outbox.py`（token `loads_strict`）；并新增
  `test_the_outbox_retained_result_reader_never_parses_json_loosely`，对 `_read_completed_result` 做 AST
  检查，既要求出现 `loads_strict`、也禁止出现裸 `loads`——把「先存 payload 再间接调 `from_json`」这类
  登记表看不见的路径单独钉住。

## 27. 正式复核（2026-10-30）：胜者冻结 entry 的失败状态曾被顶层 `ok` 覆盖（已修）

### 27.1 复核发现的矛盾记录旁路

共同谓词原来只要求 `result.confirmations` 中胜者 entry 的 `identity` 与确认报告逐批记录一致，没有检查
entry 自己的 `status` 与 `failed_batches`。在一份其他绑定全部合法的文档上，仅作如下修改：

```text
result.confirmed_status = "ok"
result.confirmations[winner].status = "build_identity_mismatch"
result.confirmations[winner].failed_batches = 2
确认报告与批次 identity.kind 仍为 "match"
```

旧谓词仍返回 `{"allowed": true, "status": "confirmed"}`。这允许读盘路径用顶层 `ok` 推翻胜者自己的
失败记录；§19 的 finalize 漂移修复明明会同时写顶层与 entry 的失败状态，谓词却没有把后者纳入闭包。

### 27.2 修复

`taic/policy.py::confirmation_publication` 现在对胜者 entry 额外要求：

- `status` 恰为 `"ok"`；若它是四种确认身份失败状态之一，直接返回对应闭集原因码，其他非 `ok`
  状态返回 `not_confirmed`；
- `failed_batches` 必须是**非 bool 的整数 0**，缺失、`None`、bool 或正数都算记录不全；
- 既有要求不变：entry 与批次 `identity` 必须逐字节相同，批次身份必须为 `match`，先前已完整确认的
  候选在后续候选失败时仍可成为 winner。

新增负例：

- `tests/shared/test_r5_policy.py::test_a_failed_winner_entry_cannot_be_overruled_by_the_top_level_status`；
- `tests/shared/test_publication.py::test_a_failed_winner_entry_cannot_be_overruled_by_the_top_level_status`。

两者都覆盖「entry 身份失败」「status=ok 但 failed_batches>0」以及恢复完整记录后仍可发布的正例；
读盘用例还检查闭集原因码。既有手写合法夹具补上真实运行一直会写的 `status="ok"` 与
`failed_batches=0`，没有放宽任何断言。
