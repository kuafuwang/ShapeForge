## 0. 单一流程与 reviewer 收尾规则（最重要）

- Actor 从 **R1** 开始。**一个 RLAR 回合集中完成一个阶段**；一个阶段需要多轮修复时，留在该阶段直到
  该阶段硬验收全部通过，再进入下一阶段。
- **不要在阶段边界停下等用户**。用户已明确要求“一个 RLAR 内逐个执行 R1–R6”，不会在阶段之间再发
  “继续”。
- Reviewer 每轮直接检查实际代码、文档、diff 与测试证据（不是读 actor 的自我总结）。
- Reviewer 的 `done` 语义被本流程重定义：
  - 当前阶段**未通过** → `done=false`，给出同阶段的具体修正项（文件、符号、验收条目编号）。
  - 当前阶段**已通过但后面还有阶段** → `done=false`，并在 notes 明确写
    **“Rk 已通过，下一阶段 R(k+1)”**，让同一 RLAR 自动继续。R1/R2/R3/R4/R5 任一单阶段完成
    **都不能** `done=true`。
  - 只有 **R1–R6 全部完成且各自硬验收通过**，并且 **R7 的真实设备事项已逐条登记为未授权 blocked**
    之后，才允许 `done=true`。
- 规范内可自行决定的实现细节（R1 的 `work_accounting` 唯一来源、RMSNorm `LoweringProfile` 字段闭集
  与注册位置、`semantic_rules_version`/`work_accounting_version`/`lowerer.version` 取值、本地 pack
  文件集清单、纯函数签名细节）由 actor/reviewer 依规范自行决定并**记录**，**不要为这些停下来问用户**。
- 不要改变已定路线：OpSpec 两阶段派生（`instantiate` → `lower`）、唯一 `artifact_builder`、
  schema 4 唯一版本、六 RPC/field number/HMAC/BlobChannel/VendorDriver 不变、模拟不可发布。
  **不增加 P1/router/shape dispatcher 范围**（那是 R5b，§10，不在 R0–R7 验收内）。

## 1. 严格权限与测试红线

**禁止**：

- `uv run pytest -q -m 'not gpu and not llm and not slow'`（快速安全套件）。

- 纯离线：`prepare_resume`、`load_snapshot`、fake evaluator / `FakeNpu`、纯 AST/调用图检查、
