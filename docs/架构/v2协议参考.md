# v2 协议参考（给不看代码的人）

这份文档讲清楚：**v2 标准任务目录是什么、怎么加一个算子、怎么写一个候选内核、数字是怎么被测出来并发布的**。不需要读代码；文件名和字段名保留英文原样，方便你对照。

相关文档：主计划 `跨硬件算子生成分工_9aef8d3a.plan.md`；搜索侧接线 `搜索-v2接线.md`；计时优化见该文 §6。

---

## 1. v2 是什么

一个**算子**就是 `tasks/<算子名>/` 下的两个必需文件：

- **`opspec.json`**：任务合同（算什么、形状、类型、容差、用途）。
- **`reference.py`**：独立参考实现（判分 oracle）。

加一个算子，就只写这两个文件（需要性能对比时再加 `baselines.*`）。**没有 Triton 源码、没有逐题 profile、没有中央任务名登记**——v2 一律自动发现。

一个**候选内核**就是一个 `.metal` 文件，里面自带一个 `/* taic-launch */` 块声明启动几何（grid/threads/workspace/math）。**启动几何由候选自己声明，harness 不替你选**。

一次**评测** = 编译 → ABI 检查 → 安全检查 → 正确性 → 计时，产出一份 **schema-4 报告**（含身份摘要）。

一个**发布的 speedup** 只在通过**确认门**（fresh 重测 + 身份一致 + 计时安静）后才给出。

---

## 2. 标准任务目录

一个算子目录下的文件：

| 文件 | 必需？ | 作用 |
|---|---|---|
| `opspec.json` | **必需** | 任务合同 |
| `reference.py` | **必需** | 独立参考实现 |
| `reference.json` | 可选 | reference 版本、采样/误差尺度 profile |
| `baselines.json` | 可选 | 性能比较对象（mlx / torch_mps 等）的登记 |
| `baselines.py` | 有 baselines.json 时必需 | baseline 怎么跑 |
| `display.json` | 可选 | 题面文字的覆盖 |
| `known_good.metal` | 可选 | harness 自检核（不是 reference、不是 baseline） |

不允许出现：`task.py`、`track.json`、`kernel_triton.py`、逐题 LoweringProfile、专用题面模板、中央任务名登记。

## 3. `opspec.json` 里有什么

以 `gemm` 为例（节选）：

```json
{
  "spec_version": 2,
  "op_name": "gemm",
  "formula": "C[m,n] = sum_k A[m,k] * B[k,n]",
  "type_vars": { "T": ["fp16", "bf16"] },
  "symbols": { "M": {"min": 1}, "N": {"min": 1}, "K": {"min": 1} },
  "tensors": {
    "A": {"role": "input",  "dims": ["M","K"], "dtype": "T", "layout": "row_major", "strides": ["K","1"], "space": "global", "access": "read"},
    "B": {"role": "input",  "dims": ["K","N"], "dtype": "T", "layout": "row_major", "strides": ["N","1"], "space": "global", "access": "read"},
    "C": {"role": "output", "dims": ["M","N"], "dtype": "T", "layout": "row_major", "strides": ["N","1"], "space": "global", "access": "write"}
  },
  "numerics": { "acc_dtype": "fp32", "rounding": "single_round_at_output",
                "tolerances": {"fp16": {"rtol": 0.002, "atol_rel": 0.001}}, "exact": false },
  "cases": { "names": ["normal","wide_range","large","tiny","outlier","ieee"] },
  "sizes": {
    "paper": {"M": 2048, "N": 2048, "K": 2048, "usage": ["golden","benchmark"]},
    "small": {"M": 256,  "N": 256,  "K": 128,  "usage": ["golden","benchmark"]}
  },
  "work_accounting": { "flops": ..., "min_bytes": ... },
  "discovery": { "default_instance": {"dtype": "fp16", "size": "small"} }
}
```

各字段的含义：

- **`tensors`**：张量的角色（input/output/read_write）、形状、dtype、布局、stride、访问权限、内存空间（global/workspace）。**声明顺序就是 ABI 的 buffer 槽位顺序**。
- **`numerics`**：累加精度（`acc_dtype`）、舍入方式（`single_round_at_output`）、容差（`rtol`、`atol_rel`）、是否逐位一致（`exact`）。
- **`cases`**：正确性用例。`ieee` 会植入 NaN/Inf/-0.0，要求与 reference 逐位一致。
- **`sizes`**：每个尺寸档的符号取值与**用途**。`golden` = 只对答案，`benchmark` = 计时比速度。
- **`discovery.default_instance`**：默认 `(dtype, size)`。

## 4. `reference.py` 的接口

```python
def reference(inputs, attrs):
    return {"C": ...}          # 必需：标准答案（fp64/fp32 CPU 计算）

# 可选：
def gen_inputs(case, seed, instance): ...        # 自定义输入生成
def error_scale(inputs, reference_outputs, instance, tolerances): ...  # 误差尺度
```

reference 必须独立：不 import 候选、renderer 或 known_good。

## 5. 先分清三个「多」：msl-single、msl-bundle、portfolio 多 variant

刚接触的人最容易把这三者混为一谈，先讲清楚各自是干嘛的、什么时候用哪个。

### 5.1 `msl-single`（一个候选 = 一个 kernel）

**一个 `.metal` 文件 + 一句 `/* taic-launch */` 启动声明**，一次 dispatch 把活全干了。适合「一个 kernel 就能算完」的算子：GEMM、逐元素、多数简单融合。

这也是**目前搜索唯一支持的交付方式**。

### 5.2 `msl-bundle`（一个候选 = 多个文件）

**解决「一个 kernel 写不下/不合适」的问题。** 有些算子光一个 kernel 不够：

- **多阶段**：flash_attention 是 `Q·Kᵀ → softmax → ·V` 三步，需要多个 kernel 按顺序跑，中间结果要复用。
- **host 侧分块**：K 很大的 GEMM，一次算不完，要 host 侧把 K 切成几段、分段累加，还要预计算 tiling 表。
- **workspace 复用**：中间结果（softmax 系数、分块 partial sum）要一块临时显存，多个 kernel 共享。

这时候选就不只是「一个 kernel」，而是「**一段 host + device 协同的实现**」：host 文件管分块/调度/预计算，device 文件管计算，再加一份几何/资源声明。**这一组文件合起来就是一个 bundle。**

### 5.3 portfolio 多 variant（一个任务 = 多个实现）

**解决「不同 shape 该用不同 kernel」的问题。** 同一个算子，小 shape 和大 shape 的最优实现往往不同：

- variant A：小 shape 用的简单 kernel（可以是单文件）。
- variant B：大 shape 用的分块实现（可以是 bundle）。
- fallback：兜底的通用实现（不属于任何候选 shape 时用）。

**注意**：「多 variant」和「一个 bundle 是多文件」是两回事——**一个 variant 本身可以是单文件，也可以是 bundle**。portfolio 是「多个候选怎么按 shape 选」，bundle 是「一个候选怎么由多文件组成」。

### 5.4 什么时候用哪个

- 算子**一个 kernel 就能写好**（GEMM、逐元素、多数简单融合）：用 `msl-single`，**不需要 bundle**。
- 算子**要多阶段 / 要 workspace 复用 / 要 host 分块**（flash_attention、大 K GEMM、复杂融合）：才需要 `msl-bundle`。
- 同一个算子**不同 shape 要用不同实现**：用 portfolio 多 variant（variant 本身可以是 single 或 bundle）。

一句话：**bundle 不是「更高级的写法」，是「一个 kernel 写不下时的组织方式」。** 不要为了用 bundle 而用 bundle。

## 6. 写一个候选内核

一个 `.metal` 文件 + 一个 `/* taic-launch */` 块：

```metal
/* taic-launch
math fast
launch gemm_kernel grid=8,2,1 threads=256,1,1
*/

kernel void gemm_kernel(
    device const half* A [[buffer(0)]],
    device const half* B [[buffer(1)]],
    device half*       C [[buffer(2)]],
    ...)
{
    // 你的实现：tile 划分、数据搬运、MMA、写回
}
```

规则：

- **buffer 槽位 = `opspec.json` 里 tensors 的声明顺序**（A=0、B=1、C=2）。输入 `device const T*`，输出 `device T*`。
- **`taic-launch` 必须有且只有一个**：`launch <核名> grid=x,y,z threads=x,y,z`（可带 `threadgroup=<字节>` 与 `workspace=<名:zero>`）。
- **`math fast` / `math safe` / `math relaxed`**：数学模式。`safe` 保留 IEEE 特殊值，`fast` 快速近似，`relaxed` 介于其间（macOS 15+）。
- 不能改输入内容、不能用纹理、不能贴别人的核。

这叫 **`msl-single`** 交付方式。另一种是 `msl-bundle`（Host Tiling + 多文件 + Schedule），**目前搜索只支持 msl-single**。

## 7. 数字是怎么测出来的

一次评测（`evaluate_task`）按固定顺序：

1. **几何派生**：读 `taic-launch`，做合法性检查（越界、资源上限）。
2. **构建**：在**有界子进程**里编译（超时会被杀，防止死核冻住显示器）。
3. **ABI 检查**：核名、buffer 槽位、参数访问模式是否与合同一致。
4. **安全检查**：越界写、输入被改、输出未写全、竞争。
5. **正确性**：对 `cases` 的每个用例，与 reference 比对（容差见 `numerics`）。
6. **计时**（仅 `benchmark` 用途）：与登记的 baseline（mlx/torch_mps）**交错计时**，取中位数，报 `candidate_us`、`baseline_us`、`speedup`。

产物是一份 **schema-4 报告**：状态（ok / compile_error / abi_error / unsafe / incorrect / timeout / crash）、各关证据、计时、以及**身份字段**。

## 8. 身份字段（为什么数字可信）

报告里带一组摘要，把「这份数字是哪颗核、哪份合同、哪次构建、哪次测量」绑死：

| 字段 | 含义 |
|---|---|
| `candidate_sha256` | 候选源码的字节摘要 |
| `task_fingerprint` / `lowering_profile_digest` | 任务合同的身份（`TaskContract.fingerprint()`） |
| `task_pack_digest` / `deployment_pack_digest` | 任务包/部署包的摘要 |
| `presentation_sha256` | 题面渲染（给模型看的那份合同）的摘要 |
| `artifact_set_digest` | 构建产物（候选 + 几何）的摘要 |
| `native_digest` | 实际执行的 native pipeline 的摘要 |
| `evaluation_fingerprint` | 评测语义（任务 + 输入生成 + reference + baseline 环境）的摘要 |

**发布 speedup 的前提**：搜索期与确认期的这些身份完全一致（`identity.kind == "match"`），且候选没有被换、计时安静、不是缓存命中。

---

## 9. 确认与发布

搜索结束后，优胜候选要过**确认门**：

- **`confirm_subject`**：用**新鲜种子**（由 ValidationPlan 派生，与搜索期的 seed 7 不同）对同一颗核**再做一次真实构建与测量**，并与搜索期报告做 **R5 身份比较**。
- 结果是一个 verdict：`confirmed`（可发布）或 `rejected` + 原因（`timing_uncertain` / `*_identity_mismatch` / `cache_hit` / `not_fresh` / 等）。
- **只有 confirmed 才发布 speedup**；否则只记 `best_speedup`（搜索期的数，不算正式发布）。

发布读盘时还要做**三方摘要绑定**：`best.metal`、胜者候选文件、`confirmation_source_sha256` 必须指向同一颗核，且确认报告的 verdict 是 confirmed。

## 10. 搜索（`taic run`）怎么用

```bash
uv run python -m taic.cli run gemm --dtype fp16 --size small --budget 15
```

- **任务**：v2 标准目录（自动发现）。
- **预算**：每次请求前检查，超过就停；`--add-budget` 可续。
- **委员会**：两个（first = deepseek-flash，second = kimi-k3.1-pro），每轮一场新会话写核。
- **确认**：搜索结束后对优胜者跑确认门；只有 confirmed 才发布。

v2 搜索的内部结构：每颗候选被包装成一个**单 variant、恒真 guard 的 portfolio**（复用 portfolio 的评测/确认驱动），搜索期所有候选共用 **seed 7**，确认期用**新鲜种子**。

常用只读命令：

```bash
uv run python -m taic.cli brief <run_dir>     # 看一次运行的状态/加速比/花费
uv run python -m taic.cli resume <run_dir>    # 续跑（不重复计费）
uv run python -m tcenv.cli eval-v2 gemm <kernel.metal> --size small --quick   # 只对答案
uv run python -m tcenv.cli eval-v2 gemm <kernel.metal> --size small --timed   # 对答案 + 计时
```

## 11. 计时固定成本（为什么小算子难做）

小尺寸算子（launch-bound）的墙钟 ≈ **固定派发成本 + kernel GPU 时间**。固定成本里，候选的计时编码路径是大头：

- **单阶段、纯 buffer、无 fill** 的批次：走 harness 自有的 **ObjC 编码器**（`native_batch.m`），固定成本约 1.0 µs/iter。
- **多阶段、纯 buffer、无 fill** 的批次：现在也走 native（本次扩展），固定成本 **5.26 → 1.33 µs/iter（约 -75%）**。
- **带 fill/workspace 或动态 threadgroup** 的批次：仍走 PyObjC（固定成本较高），这是后续可优化的方向。

经验：small gemm 与 MLX 的 steel kernel 在相同编译器下性能相当，加速比围绕 1 波动是 launch-bound 的计时特性，不是 kernel 不行。要展示加速比，选**库没为这个 shape 调过的算子**（如 mamba2_chunk_scan 实测 1.459x）或更大尺寸。

---

## 12. 当前边界

- 搜索只支持 **`msl-single`**（`msl-bundle` 的 Host Tiling 未接）。
- **远程评测**、Instruments profiling、硬件特性反馈（hw_feedback）：v2 暂不支持，显式拒绝。
- **带 fill/workspace 的批次**：仍走 PyObjC（native fill 支持已回退）。
- **seed 纪律**：搜索期恒为 7；fresh 只发生在确认期。
- 报告协议：schema 4；`@variant` 题名在 v2 上被拒绝（几何由候选声明，不是第二份合同）。

# 附录：字段速查

按「出现在哪里」分组。字段名保留英文原样。

## A. `opspec.json` 字段

| 字段 | 含义 |
|---|---|
| `spec_version` | 合同版本，v2 恒为 `2` |
| `op_name` | 算子名（目录名须与它一致） |
| `category` | 类别（linear_algebra / elementwise / reduction / ...） |
| `formula` | 展示用公式（不参与语义校验，题面由 IR+Contract 渲染） |
| `type_vars` | 类型变量，如 `"T": ["fp16","bf16"]` |
| `symbols` | 形状符号及其约束，如 `"M": {"min": 1}` |
| `tensors` | 张量表（见 A.1） |
| `numerics` | 数值约束（见 A.2） |
| `attrs` | 语义属性（整型/浮点常量，如 scale） |
| `cases` | 正确性用例名列表（normal / wide_range / large / tiny / outlier / ieee / ...） |
| `sizes` | 每个尺寸档的符号取值与 `usage`（golden / benchmark） |
| `spec_params` | 规格参数名（M/N/K 等） |
| `work_accounting` | 工作量记账：`flops`（乘加数）、`min_bytes`（最小访存字节） |
| `discovery` | 发现元数据：`phase`、`default_instance`（dtype/size）、`variant_acceptance`（保留，未实现） |

### A.1 `tensors` 每项

| 字段 | 含义 |
|---|---|
| `role` | `input` / `output` / `read_write` |
| `dims` | 形状（用 symbols 表示） |
| `dtype` | 元素类型（`T` 或具体类型） |
| `layout` | 布局（`row_major` 等） |
| `strides` | 各维 stride（元素计） |
| `space` | 内存空间：`global` / `workspace` |
| `access` | 访问权限：`read` / `write` / `read_write` |
| `doc` | 说明文字（不影响语义） |

### A.2 `numerics`

| 字段 | 含义 |
|---|---|
| `acc_dtype` | 累加精度（`fp32` 等） |
| `rounding` | 舍入方式（`single_round_at_output`） |
| `tolerances` | 按 dtype 的容差：`rtol`（相对）、`atol_rel`（相对尺度绝对） |
| `exact` | 是否要求逐位一致（整型/位运算题） |

## B. schema-4 评测报告（EvalReport）字段

| 字段 | 含义 |
|---|---|
| `task` / `dtype` / `size` | 题、数据类型、尺寸档 |
| `mode` | 评测模式：`quick`（编译+ABI+安全+正确性）/ `timed`（含计时）/ `full`（含 shader 校验） |
| `status` | 判决：`ok` / `rejected` / `compile_error` / `abi_error` / `unsafe` / `incorrect` / `runtime_error` / `timeout` / `crash` / `refused_hang` |
| `stage` | 停在哪一关（device_check / screen / compile / abi / safety / correctness / bench / ...） |
| `message` | 诊断文本 |
| `seed` | 本次输入种子 |
| `compile` | 编译证据（`ok`、`errors` 等） |
| `abi` | ABI 检查（`ok`、`violations`） |
| `pipeline` | pipeline 信息（maxTotalThreadsPerThreadgroup、SIMD 宽度、静态 threadgroup 字节） |
| `safety` | 安全检查（越界、非确定、输入被改、输出未写） |
| `correctness` | 正确性（见 I） |
| `benchmark` | 计时（见 H） |
| `roofline` | 屋顶线分析（见 J） |
| `speedup` | 相对最强 baseline 的加速比（>1 为更快） |
| `speedups` | 相对每个 baseline 的加速比 |
| `candidate_us` | 候选每次 launch 的中位微秒数 |
| `baseline_us` | 各 baseline 的微秒数 |
| `compiler_baseline` | triton-msl 编译基线（可选） |
| `verification` | 形式验证（MSL 恒为 `unsupported`） |
| `build` | 构建记录（见 C） |
| `evaluation_fingerprint` | 评测语义摘要（见 D） |
| `baseline_implementation_digest` | baseline 实现摘要 |
| `baseline_environment_digest` | baseline 环境摘要 |
| `protocol_version` | 测量协议版本（当前 `"3"`） |
| `target_id` / `backend` / `backend_version` | 目标设备与后端 |
| `device_name` / `gpu_family` | 设备名与 GPU 家族 |
| `device_warnings` | 设备相关告警 |
| `timeline` | 各阶段耗时 |
| `cache_hit` | 是否命中评测缓存（确认门要求 `false`） |
| `elapsed_s` | 本次评测总耗时（秒） |
| `eligible` | 派生：安全且数值正确（`status == "ok"`） |
| `schema_version` | 报告 schema，恒为 `4` |

## C. build 记录字段

| 字段 | 含义 |
|---|---|
| `shape` | 构建形状：`full`（完整可执行）/ `partial`（编译失败的投影，不可执行） |
| `build_kind` | 构建方式：`native`（真实设备）/ `simulator`（模拟，不可发布） |
| `candidate_sha256` | 候选源码摘要 |
| `assembled_sha256` | 进入编译器的字节（头 + 候选）的摘要 |
| `opspec_digest` | OpSpec 摘要 |
| `lowering_profile_digest` | 合同指纹（v2 为 `TaskContract.fingerprint()`） |
| `artifact_set_digest` | 构建产物（候选 + 几何 + 生命周期）的摘要 |
| `native_digest` | native pipeline 的摘要 |
| `provenance` | 构建出处：`compile_profile`、`source_sha256`、`artifact_set_digest` 等 |
