## 1. 为什么要复核

原文有三句话同时成立不了：

1. 「2026-11-17 14:45 前后……整个图形界面冻结」；
2. 「等了约 10 分钟没有恢复，只能长按电源强制关机」；
3. 「重启后（14:48）4 分钟内 load average 升到 85.11 94.73 45.12」。

如果冻结发生在 14:45、又等了 10 分钟，关机最早也在 14:55，重启不可能记成 14:48。两条里至少一条是事后回忆，不是观测。

## 2. 三个可复核的锚点

都不需要重跑事故，只要读本机现有记录：

| 锚点 | 读数 | 怎么复核 |
| --- | --- | --- |
| 上次开机时间 | 2026-11-13 23:04（本次 11-24 01:47） | `last reboot`；`sysctl -n kern.boottime` |
| 冻结前的 uptime | `Time Awake Since Boot: 315707s` = 3 天 15 小时 41 分 47 秒 | 11-13 23:04 + 315707 s = **11-17 14:45:48** |

三条合起来：**14:45:48 系统仍在运行**（uptime 是那一刻读出来的）、**14:45:51 还有进程成功写盘**、**14:48 已经重新开机**。所以从「最后一次能写盘」到「开机」最多两分钟出头，电源是这段时间里按下的。

原文的「约 10 分钟」与这三条都对不上，属于事后回忆；它与「14:48 重启」不能同时为真。

## 3. 这次复核改变什么、不改变什么

- **不改变**：因果链本身。当天 GPU 崩 5 次（`BIF0 page fault`，signature 563）、`WindowServer` 被看门狗杀掉（14:45:11 / 14:45:21 超时，14:45:51 崩溃记录）、以及「全部由 Python 进程触发」都不依赖那 10 分钟。处置结论（开 `MTL_DEBUG_LAYER=1`、并发压到 1–2、`budget.duration` 压到 1–2 分钟）也不变。
- **改变**：把「等了约 10 分钟」当成观测值的读法。界面从哪一秒开始不响应，现有证据**定不出来**：14:45 的三条 `WindowServer` 记录都落在系统仍在写盘的那三秒里，它们说明 GUI 在这一刻被判死，不说明用户在更早就已经动不了鼠标。
- **不受影响**：14:53:41 起的写盘高峰是重启后重新拉起任务的痕迹，与「重启后 4 分钟内 load 升到 85」大致对得上（14:48 + 4 分钟 ≈ 14:52），这段可以保留。

## 4. 需不需要「重新测试得到证据」

不需要，而且做不到想要的因果：

- 这类证据是**过去某一次**事故的时间线，重跑只会产生一次**新的**事故和一组新的时间戳，不会改写 11-17 那天的记录。
- 复现它的方法是故意把 GPU 打到 `BIF0 page fault`，代价是整机冻结和强制断电——文件系统与在跑的 run 都有丢数据风险，而收益只是「证明它能复现」，这一点原文已经记过 8 次。
- 真正缺的不是复现，而是**当时没记时钟**。能被复核的锚点（`last reboot`、uptime、文件 mtime）都在，事后能算；唯独「我等了多久」只有人的记忆。

所以正确的动作是改记录习惯，不是重跑事故：下次当场把 `date`、`sysctl -n kern.boottime`、`last reboot` 三条贴进记录，再 `stat` 一下最后写过的文件。这条已经写进 [README.md](README.md) 的约定。

## 5. 复核用的命令（只读）

```bash
last reboot | head -5
sysctl -n kern.boottime
cd <repo> && find runs logs -newermt "2026-11-17 14:40" ! -newermt "2026-11-17 15:00" \
  -type f -exec stat -f "%Sm %N" -t "%H:%M:%S" {} + | sort | tail
```
