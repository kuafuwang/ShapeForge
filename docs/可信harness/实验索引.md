# 实验与尝试索引

这份索引回答“哪些实验已经做过、结果是什么、证据在哪里、下一步是什么”。它不是效果证据本身：每条结论都不能超过对应记录的范围。

跨任务、跨 backend 的收益评估按 [Harness 收益计分卡实施计划](harness收益计分卡-plan.md) 执行；不再用单个算子的 overlay 结果代替 harness 收益。

**保存规则**：`runs/` 在 `.gitignore` 中，原始 run 可能只存在于本机。每次付费或 GPU 实验结束后，必须把任务、臂、起始候选、模型、seed、预算、实际成本、主要数字、结论和证据路径写进本索引或它链接的仓库内文档。不能只留 run 目录名，也不能只留在对话里。

## 新实验的最小记录格式

```text
日期 / 实验名 / 假设
任务、target、dtype、size、起始候选 SHA、模型、run_seed
control/treatment 的各自配置与注入内容
预算上限、实际成本、是否调用 GPU/付费模型

适用范围、反例、是否允许发布、下一步
仓库内证据文档与原始 run 路径（两者都写）
```

新条目必须链接到**仓库内**的证据摘要；如果只有 `runs/` 原始文件，先复制关键结果再登记。这样即使 run 目录以后被清理，实验假设、数字、成本和“为什么停止”仍然可找回。

## 子任务汇报必须同时包含父任务进度

每次完成子任务时，交付不能只列改了哪些文件或跑了哪些测试，还必须同时写清：

1. **父任务是什么**：例如“代理反馈系统演进蓝图”，它要改善的是可信反馈闭环，而不是某一个工具。
2. **父任务已完成什么**：只列与该子任务相关的既有机制和证据，避免重复整份历史。
3. **父任务还剩什么**：包括未验证效果、等待的数据、明确不做的项。
4. **这次子任务改变了哪一格**：机制、数据质量、证据等级、效果验证，还是仅文档。
5. **下一步与证据入口**：下一件最有价值的事，以及本索引/相关 JSON/样本复核的位置。

这样每次报告既能看到局部完成情况，也能判断它是否推进了父任务，避免在多轮审计、探针和小实验中迷失总目标。
