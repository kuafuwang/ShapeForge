## 必须先裁的三处

这三处不裁，后面的 plan 会互相阻塞。裁的是规则归属，不是放宽 fail-closed。

### 1. $40 试点要求一个它不许产出的结论

plan-02 规定：`confirmatory_min_pairs` 未经真实 unchanged-control 校准之前，任何计划不得写出 `supports_effect` 或 `refuted`；3 对只能是描述性的 `inconclusive`。合成零效应数据不能解锁这个门槛。

plan-08 §⑦ 把下一次付费收成 S0（送达）加 S1（3 对、上限建议 $40），并写明 S1 唯一允许的效果结论是 `inconclusive`。

plan-08 §⑥ 又写：`paired_required` 的价值证据就是 plan-02 的 `supports_effect`；观察窗里没有它，就暂停这个方向的付费部分。

因此这份授权单的继续条件，等于另一次尚未计价的校准实验再加一次更大的确认实验。$40 窗口的完成标准应写成：treatment 的 TASK 回执与 control 的阴性断言成立，账单没有 unknown。`supports_effect` 留在那次确认实验的授权单里，那张单现在不存在。

### 2. 「不发布」没有指明发布的是哪一个结果

plan-06 对动态控制面写了：观察者尚未实现时，形式上合法的收窄记 `host_unverified`，并且「不发布、不采纳」。同文对评分字节被改的处置是「结果不得发布、不得作为采纳证据」。

本仓库里「发布」已经有固定含义：确认门重新测量并绑定之后的加速比。`sync_trust_status` 只在 `harness_auto` 打开后运行（上表）。一旦打开，一次合法的自动暂停就会改写臂内的 `trust.toml`。若实现者把 `host_unverified` 理解成核的确认结果也不得发布，信任收窄会卡住与评分无关的发布门。

应写成两句：合法收窄停止后续 overlay 注入，内核确认发布仍走现有确认门；`host_unverified` 只禁止把该 run 用作 harness 采纳或效果证据。非法扩权、审计被改、评分字节被改，才同时作废采纳与发布。plan-03 保留状态转移表的唯一正文；plan-06 只写「偏离该表时记哪一档」，不要再抄一遍 `suspend` / `suspended` 的映射。

### 3. 评分可信计算基排在了威胁核实之前

plan-01 写明：围栏 `local=ALL` 是否覆盖评测器、用例和期望输出，**未核实**。plan-06 §5.10 却已经规定六类命名面、import 闭包、按臂 diff、检查器自证、以及只含 `select_diverse_parent` 的封闭白名单。

这个函数默认不在搜索里。白名单因此给了一条走不通的实验口：要观察到效果，还得打开 `diversity_archive`，而那一步属于生效配置面，须另行授权。在核实「写核会话到底能不能改 `tasks/` 和 `tcenv/evaluate.py`」之前，这套基不是 Phase 0。

Phase 0 保持 plan-06 自己写的那句：离线攻击集，加上 `docs/security.md` 里围栏挡不住什么。评分面单独立项，入口条件是一次只读的可写性核实。

判定：阶段 0 和阶段 1 可以开工。攻击成功定义、solver 误拒不能被检出率抵消、`eligible` 不等于完整验收，这三句已经够用。

判定：缺口判断是对的。现有 runner 只会物化 `treatment.patch`；3 对上的零宽区间不能叫支持。近期交付应停在预测句、dry-run 和「伪支持 / 伪反驳不得出确认词」的状态机。
