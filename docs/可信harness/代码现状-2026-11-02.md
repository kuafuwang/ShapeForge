## 8. 改 plan 时的写作纪律

1. **符号 + 行号**：只写行号会在下一次提交后失效；写成 `taic/harness.py:975 validate_proposal 的 probe 门` 这种。
2. **标注 git 状态**：已提交 / 工作区未提交 / 未跟踪，三者不能混。
3. **不把 plan 里的名字当代码事实**：`inherit_prompt`、`developer_queue`、`route_proposal` 目前只是文档概念，代码零命中。
4. **不把测试文件名当既有基线**：先 `test -e`，再引用。
5. **区分"缺口"和"已实现但未接入"**：`confirm_batches`（已开）、秘密 holdout（已写未提交）、`plan_ledger`（有模块未接线）是三种不同状态。
6. **一个数字一个来源**：`pair_count`、`probe_verified`、`spent_usd` 这类词在不同文件里语义不同，引用时带字段全名。

## 9. 已拍板的决定（2026-11-02）

**决定原则：不为兼容旧数据/旧行为留包袱；只保留让未来更可靠、更可审计、更可实验的选择。** 因此明确不做这些“兼容性过渡”：旧指纹别名或自动迁移、在 `feedback.jsonl` 双写账单、把错误接收者的经验条目“加注后保留”、为让检查看起来有用而伪造 live 用例。
