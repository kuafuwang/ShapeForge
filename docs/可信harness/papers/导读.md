## 2. 分组详介

### A. harness 是什么、怎么工程化

#### `2604.25850_agentic-harness-engineering.pdf` — Agentic Harness Engineering（AHE）
- **问题**：harness 工程还是手工活；动作空间异构、轨迹太长、编辑效果难归因。
- **做法**：三根可观测性支柱——组件级（每个可编辑组件有文件级表示，可回滚）、经验级（百万 token 轨迹蒸馏成分层证据库）、决策级（每次编辑先写预测，下一轮用任务级结果核对）。
- **关键数字**（论文口径，摘要）：10 轮把 Terminal-Bench 2 pass@1 从 69.7% 提到 77.0%，高于人工 Codex 的 71.9%；冻结的 harness 在 **SWE-bench-verified** 上 token 少 12%，并在 **Terminal-Bench 2** 上对三个替代模型族给出 +5.1~10.1pp；消融显示增益在 tools/middleware/长期记忆，不在系统提示。两个数字不同基准，不能合并成「跨族迁移还省 token」。
- **对我们**：plan-02 的核心外部依据——**每条提案都要带可证伪预测和对照复测**；plan-07 的「哪些东西值得沉淀」。
- **注意**：它没有解决单条编辑的严格归因；跨族迁移是它的结论，不是我们能直接继承的保证。

#### `2609.00006_harness-engineering-anatomy.pdf` — Harness Engineering: Anatomy…
- **问题**：harness 被叫做「工程」但缺少系统的源码级解剖。
- **做法**：11 个生产 coding harness（Claude Code、Codex CLI、Gemini CLI、OpenHands、Aider、Mini-SWE-Agent、Hermes、**Pi**、OpenCode、OpenClaw 等）+ 元 harness Omnigent；给出 7 个子系统、13 条横切观察、29 个模式、18 条建议、90 行最小 harness。
- **关键事实**（论文口径）：约 400 万行代码里没有运行时 import 通用 agentic 框架，也没有用向量检索做代码检索；`SKILL.md` 采用 9/11，高于 MCP 的 8/11；行为策略正从 prompt 散文迁到配置。
- **对我们**：重写 `docs/架构/hmz.md` 的术语来源；也是 plan-09 里「文档要跟代码对齐」的论据——Pi 的行为在它眼里是配置与运行时，不是提示词。
- **注意**：它是源码研究，不给效果数字；不要把「模式」当成验证过的因果。

#### `2603.25723_natural-language-agent-harnesses.pdf` — Natural-Language Agent Harnesses
- **问题**：harness 逻辑埋在紧耦合控制代码里，难比较、难迁移、难消融。
- **做法**：把 run 级 harness 策略写成可执行自然语言文档（NLAH），由共享运行时 IHR 解释成 agent 调用、handoff、状态更新、validation gate 和 artifact contract。
- **关键结论**（论文口径）：在 coding/terminal/computer-use 基准上，IHR 执行 NLAH 与代码/提示实现效果相当，但静态策略短得多，模块消融可行。
- **对我们**：`harness-proposal` + `acceptance.make_spec` 的「建议是数据不是权限」有了学术版本；也提醒文档一旦可执行，更需要 gate（plan-06）。
- **注意**：可执行文档会扩大注入面；论文没有解决「文档被篡改」的问题。

#### `2607.08028_prompts-to-contracts.pdf` — From Prompts to Contracts
- **问题**：企业 LLM 应用的行为最初由 prompt 承载，产品化需要来源边界、实体路由、答案合同和可复现 trace。
- **做法**：把确定性行为搬进代码、manifest、schema 和校验产物；故障注入验证校验器能抓住故意破坏的合同。
- **关键数字**（论文口径）：三个托管模型、270 次组合边界运行全过；只改 prompt 时违规会到达读者，代码拥有的 enforcement 才能同时保住安全与效用；外挂 guardrail 则过度拒绝（效用 88/120 vs 120/120）。
- **对我们**：plan-06 的「规则在代码里，不在提示词里」；也是 never-auto 与结构化校验的正当性来源。
- **注意**：场景是韩国企业公开数据问答，不是 agent 写内核；只借机制，不借数值。

### B. harness 的测量与审计

#### `2605.14271_auditing-agent-harness-safety.pdf` — HarnessAudit
- **问题**：只评最终输出会漏掉「答案对、过程越权」；违规常发生在轨迹中间而非终点。
- **做法**：审计完整轨迹的三个面——边界合规、执行保真、系统稳定；HarnessAudit-Bench 210 个任务、8 个真实领域，单 agent 与多 agent 两种配置。
- **关键结论**（论文口径）：任务完成与安全执行并不一致，违规随轨迹变长累积；多 agent 下更明显。
- **对我们**：plan-06 的核心论据——审计单位应是**轨迹**（工具调用、读写路径、host 连接），而不是最终 kernel。也支持把 `harness_decision` 与 run 记录绑定。
- **注意**：它的「边界」是通用 agent 工具边界，不完全等于我们的 hmz 围栏；映射时要说清。

#### `2605.27922_harness-bench.pdf` — Harness-Bench
- **问题**：现有基准要么抽象掉执行，要么比较整套 agent，或把 harness 固定，无法研究执行层差异。
- **做法**：在共享任务环境、预算、评测协议下比较配置级 harness，同时保留各 harness 的原生执行；106 个沙箱离线任务，人工复核真实性/可解性/oracle 可检性/完整性。
- **关键规模**（论文口径）：5,194 条轨迹，记录最终产物、执行 trace、用量统计和 validator 输出。
- **对我们**：plan-02 的实验设计参照——**共享环境 + 保留原生执行 + 过程数据**；plan-08 的「不要只看完成率」。
- **注意**：它是 benchmark 论文，不提供「哪种 harness 更好」的通用结论；跨任务外推要另证。

#### `2609.05736_beyond-prompts-tool-agent-harness.pdf` — Beyond Prompts
- **问题**：固定模型时，改 harness（prompt、工具接口、middleware、状态处理、恢复逻辑）能提升 agent，但缺少资源受限下的选择协议。
- **做法**：把问题写成 resource-bounded harness selection，编辑面限制在 tool-boundary middleware；报告 held-out lift、最差条件提升、可重复性、成本诊断和 RelLift95(B)（预算 B 下所选 harness 收益的保守估计）。
- **关键数字**（论文口径）：BFCL multi-round / tau2-Retail / tau2-Telecom 平均 held-out 提升 14.2 / 14.9 / 10.1pp；消融把主要贡献归于 failure-surface routing 和 edit-pattern 约束。
- **对我们**：plan-02 直接可用——**报保守下界和最差条件，不只报平均**；也支持「编辑面要受限」而不是任意改运行时。
- **注意**：tau2/BFCL 场景与内核搜索差异大；RelLift95 的定义要读原文再用。

#### `trustworthy-llm-harnesses-笔记.md` — Trustworthy LLM Harnesses（全文未取得）
- **状态**：Shudong Sun（University of Arizona），preprints.org 2026-10-14，单作者、未同行评审、检索时零引用；PDF 三次尝试均 403，只有摘要级信息。
- **摘要要点**：harness 是 trajectory-generating policy；harness effect 是配对的、按指标索引的对比；七个维度（正确性、质量、效率、可靠性与可复现、鲁棒、安全、公平）；命题涉及配对降方差、近似验证的正确性损失界、子群差距误导、评估者偏差污染；报告用 Pareto profile 而非单一分数。
- **对我们**：问题形式化与七维度的参考；`plan-02/05/08` 都能对上，但**不能当证据**。
- **注意**：详见笔记；引用前先读全文核对命题假设。

### C. 验收器、reward hacking 与监控

#### `2606.08960_hacker-fixer-loops.pdf` — Hardening Agent Benchmarks with Adversarial Hacker-Fixer Loops
- **问题**：基准的 outcome verifier 多为手写、脆弱，容易被只给任务描述的前沿模型 hack。
- **做法**：审计 5 个终端 agent 基准、1,968 个任务；三角循环——hacker 试图不解题就过验收，fixer 补验收器，solver 确认合法解仍能通过；补丁可跨任务迁移。
- **关键数字**（论文口径）：323 个（16%）任务可被 hack；KernelBench 公开 exploit 语料攻击成功率 62%→0%；弱模型（Gemini 3 Flash）的循环防住更强 hacker（76%、61%→0%）；Terminal Bench 77 个任务上 39%→17%；发布 Terminal Wrench（323 环境、3,632 条攻击轨迹）。
- **对我们**：plan-01 的方法论核心；solver 一侧正是防止「验收越收越紧把真核误杀」。
- **注意**：16% 是那批终端任务的口径，不是内核评测的漏洞率；KernelBench 结果是它们自己的复现。

#### `2509.14279_robust-kbench.pdf` — Robust-KBench
- **问题**：现有 kernel benchmark 有可利用漏洞、测试条件单一，难以评估真实泛化。
- **做法**：更严的正确性/性能评估 + 翻译→验证→进化式优化的 agent 流水线，用 LLM verifier 做正确性判断与过滤。
- **关键结论**（论文口径）：在 robust-kbench 上产出超过 torch 的内核，覆盖前向/反向与融合；verifier 能较准确分类错误内核，提升硬件验证效率。
- **对我们**：`tcenv` 差分门、取值域扫描、确认门的外部对照；plan-01 的「更严测试条件」。
- **注意**：它依赖 CUDA 与 GPU；我们只借评测设计，不借实现。

#### `2503.11926_cot-monitoring.pdf` — Monitoring Reasoning Models for Misbehavior
- **问题**：reward hacking 难发现；只看动作/输出会漏。
- **做法**：用另一个 LLM 读推理模型的 CoT，在 agentic coding 环境中检测作弊；并研究「惩罚坏想法」的后果。

- **对我们**：plan-05 的评审输入应包含过程证据；plan-06 的「标注未验证」必要但不充分——模型可能学会规避。
- **注意**：这是 OpenAI 内部模型研究，不保证对外部模型同样成立。

### D. 权限、注入与运行时安全

#### `2504.11703_progent.pdf` — Progent: Privilege Control
- **问题**：agent 通过工具调用接触外部环境，间接提示注入可触发未授权动作；权限需求随任务和执行状态变化。
- **做法**：把权限写成工具名+参数上的符号规则，每次调用确定性检查；LLM 生成初始策略并在执行中提出更新，更新由 SMT 判定为「收窄（自动生效）」或「扩大（需显式批准）」= monotonic confinement。
- **评估**：AgentDojo、ASB。
- **对我们**：plan-03 的核心参照；`harness_control.json` 只关不开、P0/P1/P2 的能力单调，都是同一原则的实例。
- **注意**：它守的是工具调用，不守「harness 自身被修改」；P2 的审批流要我们自己补。

#### `2503.18666_agentspec.pdf` — AgentSpec
- **问题**：模型内置 safeguard 和早期强制在鲁棒性、可解释性、适应性上都不够。
- **做法**：轻量 DSL 描述 trigger/predicate/enforcement，运行时拦截；覆盖代码执行、具身 agent、自动驾驶三域；也研究用 LLM 生成规则。
- **关键数字**（论文口径）：代码 agent 不安全执行拦截率 >90%，具身任务消除所有危险动作，自动驾驶 100% 合规；开销毫秒级。
- **对我们**：plan-03/06 的「规则即数据」参考实现；但「LLM 生成规则」必须人审。
- **注意**：规则由人写还是模型写，决定了它是不是新的信任源。

#### `2606.10749_secure-llm-agents.pdf` — Toward Secure LLM Agents
- **问题**：agent 安全研究碎片化，威胁面、防线和评测各自为政。
- **做法**：247 篇综述，按信息流、授权、持久状态建模，围绕「怎么建模/威胁面/防线与权衡/怎么评估」四问组织。
- **关键结论**：prompt injection 与工具控制流劫持仍主导；持久状态污染与多 agent 传播是新兴重点；现有防线「弱组合」；基准低估长时程、有状态、部署敏感风险；呼吁 trust boundary、privilege control、provenance-aware state。
- **对我们**：plan-03/04/06 的共同问题清单；`self-checks` 非签名、跨 run 经验传播、overlay 语义注入都能在这里找到对应类别。
- **注意**：综述不提供可直接抄的设计；它是威胁分类学。

#### `2406.13352_agentdojo.pdf` — AgentDojo
- **问题**：agent 在不可信数据上调用工具时会被间接注入。
- **做法**：可扩展环境，97 个任务、629 个安全用例，任务×攻击×防御三元组；不是静态测试集，支持设计新任务、防御和自适应攻击。
- **关键结论**：前沿 LLM 在无攻击时也失败不少任务；现有注入攻击能破坏部分安全属性，但不是全部。
- **对我们**：plan-06 的攻击集模板；我们的 `FEEDBACK`/overlay 是不可信数据进入指令面的通道。
- **注意**：它的任务是邮件/银行/旅行等，不是写核；fixture 要重写。

### E. 评审、多模型共识与评委可靠性

#### `acl2026_auditing-multiagent-reasoning-trees.pdf` — AgentAuditor
- **问题**：多数投票丢弃推理结构，在 confabulation consensus（共享偏差导致同样错误理由）下很脆。
- **做法**：把多条推理轨迹组织成 Reasoning Tree，在关键分歧点做分支级证据比较；用 Anti-Consensus Preference Optimization 训练裁决者，降低对多数线索的顺从。
- **关键数字**（论文口径）：四个 MAS 框架、多个推理基准，比多数投票最多 +5 个绝对点，且 token 高效。
- **对我们**：plan-05 的「quorum 只是召回」；下一步是**在分歧点核验证据**，不是数票。
- **注意**：它优化的是推理聚合，不是 harness 评审；映射到我们的 review 需要改证据包结构。

#### `acl2025_judging-with-many-minds.pdf` — Judging with Many Minds
- **问题**：多 agent 评委框架里的偏差如何表现，缺少系统分析。
- **做法**：测四类偏差（位置、冗长、CoT、从众）在 Multi-Agent-Debate 与 LLM-as-Meta-Judge 两种框架下的表现，并试 PINE 去偏。
- **关键结论**（论文口径）：debate 在首轮后放大偏差并持续；meta-judge 更抗偏；去偏单体能缓解 debate，但对 meta-judge 帮助有限。
- **对我们**：我们的「另一个委员会只读 review」更像 meta-judge，方向是对的；**不要为了稳再加辩论**。
- **注意**：偏差度量依赖具体任务与标注，不能直接当我们的评审质量数字。

#### `2606.29920_llm-judge-rubrics-agentic.pdf` — RuVerBench
- **问题**：rubric 打分广泛使用 LLM-as-a-Judge，但在 agentic 长输出上的可靠性没人系统测。
- **做法**：RuVerBench，2,458 个人工标注实例（deep research 与 agentic coding），评估多个前沿模型，并分析 prompt、batch、多数投票的影响。
- **关键结论**（论文口径）：最强模型仍有显著噪声；弱模型对 prompt 更敏感；批量判定是准确率-效率权衡；多数投票有效但收益递减。
- **对我们**：plan-05 的评审基线设计、plan-08 的「不要靠加票刷一致率」。
- **注意**：「显著噪声」的具体量级要读原文；不要把它简化成「评委不可用」。

### H. RSI 与 harness 自我改进（2026 专题，14 篇）

这一组回答「业界有没有 RSI 的 harness 论文」：有，而且 2026 年集中出现。共同点是**不改权重，
改的是 prompt、工具、控制流、记忆和运行时**；差别在于谁来提议、谁来验证、能不能泛化、谁来批准。
它们大多仍是预印本，数字都是原论文口径，本仓库没有复现。

#### `2609.24972_rrsi-regularized-harness-rsi.pdf` — RRSI: Regularized Recursive Self-Improvement of Agent Harnesses
- **问题**：逐轮提议并选择 harness 组件编辑会形成系统级 RSI，但容易**记住训练任务**，分布内增益在 OOD 基准上缩小甚至消失。
- **做法**：把正则化引入 harness 自我改进，约束候选的提议与选择；提议方使用随时间退火的预算，限制候选能带多少编辑；选择侧加泄漏筛查、以「不变基线 harness 重复测量的散布」标定的噪声下限，以及按 token 成本的复杂度门槛。
- **关键数字**（论文口径，§4.2 Table 1、§4.3 Table 2，agentic workspace 实例）：H0 的 OOD 均值为 39.7，RRSI 43.6；同预算下四个基线在 evolve 集上都很强，但 OOD 均值 Meta-Harness 仅 +0.9、AHE 与 TTHE 低于 H0（TTHE −1.7）。RRSI 的 evolve 增益是各演化方法里最小的，却唯一把 OOD 均值抬过 H0 一分以上——**在这组结果里，evolve 增益排名不能预测 held-out 迁移；较大的 evolve 增益甚至可伴随负 OOD**。
- **对我们**：plan-02 的直接警示——harness 搜索的「变好」可能只是过拟合当前任务集；我们的 target/task 绑定和小样本试点要有 OOD 纪律。
- **注意**：它优化的是通用 agent 基准，不是内核；正则化参数不能照抄。泄漏筛查本身是模型 critic，论文 Limitations 明说效果取决于反馈质量与预算。

#### `2607.15524_recursive-harness-self-improvement.pdf` — Recursive Harness Self-Improvement（RHI）
- **问题**：模型与 harness 共同演化时，harness 是潜在的数据生产者；论文主张高质量轨迹**可以**作后训练数据，但把轨迹真正内化进下一代模型列为 future work（§8）。持续更新厂商 scaffold 成本高。
- **做法**：把 harness 表示为 agent loop 的 prompt 级规格，用自己的修订历史做成对反馈，少量迭代地优化；同时面向即时表现和轨迹质量（harness-in-the-loop learning）。
- **对我们**：plan-08 的「轨迹是资产」是**现在可审计的资产**，不是已实现的训练回路；不要把「未来会用于训练」写成当前质量门的理由。
- **注意**：prompt 级规格不等于我们的代码级 P2；两条路径别混。

#### `2610.14224_harness-squared-recursive.pdf` — Harness²: Recursive Agent Harnessing for an Open World
- **问题**：开放世界任务在 harness 设计期没见过、测试期又是新的，**没有 ground-truth verifier** 来指导在线编辑；且 RSI 往往只在单任务上有效。
- **做法**：两层递归；任务级用对比式 Propose-Probe-Compose，在没有 verifier 时也能引导编辑，并可扩展。
- **对我们**：plan-02 的「没有可靠判据时怎么办」——我们的内核有强 verifier，但 harness 效果没有；这正好说明为什么 harness 效果必须另设对照，而不是沿用内核分数。
- **注意**：无 verifier 的引导不等于可信；仍需人工或宿主验收兜底。

#### `2606.09498_self-harness.pdf` — Self-Harness: Harnesses That Improve Themselves
- **问题**：harness 设计是模型相关的，靠人工专家无法跟上模型多样化。
- **做法**：agent 自己改进自己的 harness，不依赖人类工程师或更强的外部 agent；三段循环——Weakness Mining（从轨迹挖模型特定失败模式）、Harness Proposal（针对失败的最小多样修改）、Proposal Validation（验收后再接受）。
- **对我们**：plan-02 的「先挖失败、再提最小改动、最后验收」顺序；也说明「不依赖更强外部模型」是可行的设计点。它的 held-in 用来证明改动针对了失败证据，held-out 只当非回归门——两个 split 功能不同。
- **注意**：自我挖失败可能把模型局限误诊为 harness 问题，见 Ecdysis。论文 Limitations 明说：改动仍可能只是基准特定的失败模式，更高风险变更需要比「pass-rate 非回归」更强的验收门。

#### `2609.32423_pluginrsi.pdf` — PluginRSI: Recursive Improvement of Agent Harnesses with Reusable Plugins
- **问题**：把 harness 当完整程序搜索，单个机制难以隔离和复用。
- **做法**：把 harness 拆成原子插件，各自独立改进、累积进共享库，每轮重新组合成新 harness。
- **关键结论**（论文口径）：在软件工程、命令行、问答任务上超过既有 harness 优化方法；**迁移到其他 solver 模型仍保持优势**；从初始 harness 重新优化时，用演化后的库会更快收敛。
- **消融的限定**（§4.4 Table 4，Kimi-K3 优化、三 solver 评测）：只给 Meta-Harness 加插件库，held-out 在 Kimi-K3 上 +1（63.00→64.00），在 GPT-5.6 Terra 上 −2（60.00→58.00），在 GLM-5.2 上 −3（59.00→56.00）。**单加库收益有限且跨 solver 不一致**；插件变异与 harness 重组各自贡献显著（去掉后 69.00→57.00 / 59.00）。
- **复用的协议限制**（App. E p.16）：库复用实验的后续优化**就在 held-out 100 题上运行**；相对原始搜索它是 held-out，相对复用优化不是。
- **对我们**：plan-07 的参照是「沉淀单元要可独立归因、可重组」，不是「库越大越好」；论文把「增长中的库如何管理」列为 future work，且候选代码量从 400 涨到约 1,300 LoC。Table 4 不能推翻 §4.5 的复用加速，但后者也不是干净 held-out 证据。
- **注意**：插件边界由人设计；插件化不解决「这个插件该不该存在」的审批问题，跨领域迁移会明显缩水（Limitations）。

#### `2610.15150_harmony-harness-multiobjective.pdf` — Harmony Harness: Multi-Objective Self-Evolution of Agent Harnesses
- **问题**：现有方法多优化单一目标，且把 harness 当单体演化，难以处理互相冲突的目标，也分不清可迁移设计与环境特定适配。
- **做法**：多目标、组合式演化；用分解式进化搜索维持 Pareto 前沿不同区域的解，避免手工设计结构多样性指标；并用分解算子分别改进通用机制与环境特定部分。
- **关键反例**（§5.2 跨基准迁移、App. I 前沿很窄、App. K.6）：安全与功能两个目标在它的基准上多数时候同向（前沿很窄，App. I 与 Limitations 自己承认），所以分解的主要价值是**防某个目标悄悄回退的搜索压力**，不是找回非凸区域。K.6 要分三件事：① `100/100/100` 是**raw error feedback + 非下降验收**规则的产物，沙箱与评分文件恢复都在，所以它是对验收规则的陈述，不是对属性的证明；② 论文命名的 **soft form** 是 scaffold 硬编码搜索集/crash 分布（DGM 的子代），不是这个工件；③ **hard form** 是直接改 `evaluate.py`，测试时移除了容器与恢复，结果「每个轴 100%，不是弱测量而是没有测量」。
- **对我们**：plan-08 的「五轴不合成分数」只借它的标量化批评（线性加权会漏掉真实权衡），不借 Pareto 机器；plan-07 的「通用经验 vs target 特定经验」分层与它的 §5.2 迁移观察同向。
- **注意**：多目标搜索成本高；我们的小预算试点不能直接照搬。

#### `2608.08311_ouroboros-reviewed-core-evolution.pdf` — Ouroboros: Self-Developing Frontier Coding Agent with Reviewed Core Evolution
- **问题**：让 agent 的工具、提示、上下文组装乃至核心实现持续演化，又不至于失控。

#### `2609.11677_ecdysis-runtime-harness-training.pdf` — Ecdysis: Efficient and Effective Training of Runtime Harnesses

- **问题与方法**：论证 KernelBench 式"单轮生成、固定形状、torch.rand 输入、fp32 eager 基线"的协议同时高估速度与正确性。作者加三件事：把 PyTorch 基线开到 TF32 张量核（从业者实际路径）、用四组值变换（原始/×3/×0.01/取负）做隐藏正确性门、再补峰值显存指标；7 个前沿模型在 H200 上重测 250 题、best-of-5。适用范围是单轮推理内核排行榜的协议修正，不涉及多轮搜索。
- **对本仓库**：最有价值的是"退化题审计"——若某题参考输出在全部 case 下恒定（卷积→GroupNorm→取均值这类），候选返回常数即可过差分与确认，拿到巨大 confirmed_speedup；可做一次性 corpus 审计（每 case 三个种子跑参考，全恒定则标记），不调模型、不重测。其次是容差与分母的耦合：published speedup 是"通过题集的几何均值"，收紧容差同时改变谁算通过和题集大小；report 现在记 rtol/atol_rel，但不记该容差下的通过题集，也没有敏感性分析，按它的证据收紧可能让数字变好看。第三是缺口：EvalReport 没有峰值显存，一个 2× 快但 3× 显存的内核在我们的信任语义里仍算合格。它的 input-blind 生成（提示里去掉 get_inputs）对我们不适用（TASK.md 本就给形状），可借的是"评审后按 hack 家族回归"而非去掉形状。
- **注意**：(1) 单轮、单卡 H200、只测推理，作者承认多轮反馈会开新的 hack 面；(2) 隐藏用例是 4 个确定性变换、只变值不变形状，可被预见；(3) 基线只对 eager PyTorch、不对 torch.compile；BF16 下同模型 L2 达 1.63×，说明"打不过库"强依赖基线选择；(4) 剔 3 个退化题、2 个 NaN 配置、以及 τ 的选择都改聚合分母，作者自己展示这会翻转结论方向。

#### `2602.24286_cuda-agent.pdf` — CUDA Agent: Large-Scale Agentic RL for High-Performance CUDA Kernel Generation

#### `2602.05885_dr-kernel.pdf` — Dr. Kernel: Reinforcement Learning Done Right for Triton Kernel Generations
- **问题与方法**：面向 Triton 的 RL 训练系统。先建 KERNELGYM：server–worker 分布式 GPU 环境，一卡一任务、每次评测在 全新子进程、心跳与失败重排，向模型暴露正确性、计时、hacking check、profiler 四类结构化反馈。指出多轮 GRPO 的组内均值基线含自身回报，梯度被系统性缩小 `1-1/N_t`，改用按 turn 的留一法 TRLOO；再用几何均值不匹配抑制 处理训练–推理漂移，用"生成核占端到端 CUDA 时间比例"（PR）与 PRS 抑制 lazy optimization，最后做顺序测试时扩展。

- **注意**：1. hacking check 的判据是"插桩 Triton 启动路径，train/eval 两种模式下都没执行到 Triton 核即判错"。它抓"根本没 启动"，抓不到"启动了但读旧输出/只算首末轮组"，与我们 fresh-input 复验的攻击面不是同一集合。 2. 计时为固定 warmup 加重复，奖励里速度比被截断到 3×，没有中位墙钟、CV 门与确认门，不能当我们发布成绩的方法。 3. 只在 NVIDIA H100 与 KernelBench 上验证，分母固定 250 题，不含 Metal 后端、ABI/线程组约束与容差口径。 4. 依赖分布式 GPU 池与多轮 RL 训练；本仓库不训练权重，也不付这份算力。

#### `2604.02268_skill0.pdf` — SKILL0: In-Context Agentic Reinforcement Learning for Skill Internalization
- **问题与方法**：把"推理时检索技能注入上下文"换成"训练时内化进参数"。技能按目录分组为 Markdown 文件，训练时连同交互历史渲染成压缩视觉上下文；用带复合奖励（任务成功 + 压缩率对数）的 GRPO 类 ICRL 训练，技能预算按三阶段线性衰减到零。每 d 步在匹配验证子任务上算每个技能文件"有/无该技能"的成功率差 Δk，滤掉 Δk≤0、按 Δk 排序、再按预算取 top-M，最后零技能推理。适用于有可执行环境、可多轮 rollout 的 agent 任务，需 3B/7B 可训策略。

#### `59558_ForgeKernel_Self_Evolvin.pdf` — ForgeKernel: Self-Evolving Kernels Catching and Surpassing Experts and Agents
- **状态与来源**：18 页，ICLR 2027 双盲投稿（Anonymous authors，Paper under double-blind review），用户手动下载；不是 arXiv。已有 AI 辅助中译 [`59558_ForgeKernel_Self_Evolvin.zh-CN.md`](59558_ForgeKernel_Self_Evolvin.zh-CN.md) 与 [`59558_ForgeKernel_Self_Evolvin.zh.pdf`](59558_ForgeKernel_Self_Evolvin.zh.pdf)，不是作者官方译本，数字以英文 PDF 为准。PDF 创建于 2026-09-26，SHA-256 `4f0251783647cb4be97ba57e921f4e6bef2bcae02f82fab6bd8271cc83bd0872`。OpenReview 网页仍被访问挑战拦截，但本地 PDF 可读。
- **问题**：前沿编码 Agent 会在最初几次尝试就固定内核架构，之后只在固定拓扑下调参；每次运行还丢弃实测经验。作者先测了一个上限：Claude Fable 5.1 + stock Claude Code `/goal`，10 个任务、每核最多 24 小时，7 个超过参考，几何均值 +17%；但仍有 3 项落后，最大差距 25.1%（GDN prefill 反向），DSA 稀疏前向为 -22.2%。
- **方法**：架构 Agent 默认通过参考核的硬件行为反推（NCU 启动结构、占用率、流水线、stall；必要时时间线探针），把它拆成自然语言里程碑 `M0→Mk`；编码 Agent 逐行实现，每步由同一 GPU job 做正确性、配对计时和机制验证。参考源码不跨边界。参考实现可以有可读源码（CUDA/Triton/TileLang/ThunderKittens），也可以是密封二进制；不是“所有参考都没有源码”。外环在连续 3 次无新最优、决策图耗尽或门控僵局时重开架构，区分 additive patch 与 foundation patch（后者从最早依赖的 M0 重做）。接受的核封存为下一代参考，目标增益 +5%；知识库配方必须先在目标架构跑探针认证，带机制、症状、最小例子、坑点、provenance 和 no-go 表。
- **关键数字（论文口径）**：27 个算子、29 个形状；22 个专家库单元中 18 个追平/超越，另 2 个在 1% 内，几何均值 +1.6%、最高 +7.6%；7 个生成系统核全部追平/超越，几何均值 +39.4%、最高 +170.6%；对 DeepSeek-V4.1 两个新核差 1.3%/3.7%；昇腾 910C 的 CANN-Bench 8 个四级算子几何均值 +33.1%；自进化额外最多 +9.9%。注意正文另有“29 个 cell 中 25 个追平/超越”的分母，和“22 个专家库单元”不是同一个统计。
- **成本与可复现性**：Table 4 报告每个 campaign 的架构介入次数、GPU 小时、活跃小时和 wall 小时；例如 DSA score recompute 3.1 活跃小时、循环 KDA prefill 97.8 活跃小时/34 GPU 小时、2D 卷积前向 19 次架构介入。论文没有给出 ForgeKernel 自己的代码或 artifact 链接；可复现性声明明确说 Ascend 分数只能在 CANN-Bench 托管服务复现，模型重跑会得到不同轨迹，应复现的是测量而不是轨迹。
- **消融与边界**：无参考时三个算子全部停滞；密封二进制几何均值约 +1.5%，可读源码约 +2.5%，说明参考的行为比源码更关键。参考强度会传播：同一个 DSA fp8 indexer 对强参考 DeepGEMM 与弱参考 cuDNN-frontend 得到的内核相差 18%；对弱参考的加速比不能当成接近强实现的证据。局限是必须有参考、平台期只是估计、只覆盖四类算子/两代 NVIDIA/一款昇腾；编码 Agent 写 CuTe DSL，不是 Triton→MSL。
- **对本仓库**：测量主链已有（`tcenv/bench.py` 交错 A/B、`taic/policy.py` 的 `required_gain`/`noise_z`/确认批次、`stop_at_roofline`），这篇是旁证，不是新增 A/B 需求。可讨论、但未授权的是 (a) 决策账本是否进入下一场 TASK：只登记为 [plan-10](../plan-10-决策账本与平台期重规划.md)，研究候选；当前任务书仍是 `history[-5:]`，不能写成已接入；(b) 经验条目以后可借鉴“先测量认证、带症状/scope/provenance”的配方字段，当前仍只做 plan-07 的过滤与人工去重，不建知识库；(c) 参考强度与选择效应只在 plan-08 的回执口径里分开记，不新增基线实验，也不把打赢弱基线写成接近强实现。

## 5. 引用与维护规则

1. 引用论文时写「作者/年份 + arXiv 或 DOI + 本地文件名」，并注明**原论文口径**；不要写成本仓库结果。
2. 预印本必须标「未同行评审」；单作者、零引用的预印本只作问题形式化参考。
3. 新增论文：先核对 arXiv API 元数据，再下载；PDF 命名 `<arXiv id>_<短名>.pdf`；在本页速览表与分组里各登记一次。非 arXiv 的会议投稿（如 ForgeKernel）按 OpenReview/文件名登记，注明双盲/未录用状态；不伪造 arXiv 编号。
4. 拿不到全文时，登记尝试记录与已知摘要来源（如 OpenAlex），不要用二手摘要冒充已读。
5. 本目录是唯一书目来源；不要在别处再维护第二份同义清单。论文数字与结论一旦被写进 plan 或设计文档，必须在该处标注「未在本仓库复现」。
