# 合理性审核：plan-01 至 plan-09

核对日期：2026-10-26。对象是当日修改后的九份 plan、两份另纸、相关代码，以及 `runs/apple-m4-max/` 下 40 个 run 的落盘记录。没有运行测试、模型或 GPU；下文的计数都来自读文件。

上一份[审核意见](审核意见-plan-01至09.md)看的是施工图：每份 plan 本批该做什么、哪里互相卡住。这一份看的是**该不该建**：每份计划要管的东西在本仓库里实际有多少，机制和代码对不对得上，钱和人工花得值不值。

有一处要纠正上一份的判断。上一份说评分可信计算基要等「写核会话能不能改评分文件」核实之后再立项。读 hmz 源码后，这个问题基本有答案：写核会话只能写自己的工作目录和临时目录，改不了仓库里的评测器、`tasks/`、`trust.toml` 或评测缓存（证据见 §2.5）。所以评分 TCB 不是「延后」，而是在当前威胁模型下大部分不需要。

## 结论

九份计划在边界和措辞上很谨慎，但多数在治理一条几乎没有流量的通道。40 个 run 里只有 12 条结构化提案，全部来自 first 委员会的 deepseek-flash；没有一条 `premise`，没有一条 `trusted_record=true`，quorum 从未成立，overlay 从未真正送到任何一场写核会话。同期真正把代理反馈变成改进的，是「自由文本 → 人审 → P2 提交」这条路：已审 claim 有 201 条，其中 26 条标 done，对应约 7 个提交和 1 个 patch。

要记住三件事：

1. **P1 自动通道的对象定错了。** 代理实际写的「提案」大多是给 harness 开发者的需求：加子命令、多打印一项指标、修一处文档示例。现在的路由把它们当成给下一场写核 agent 的提示注入 TASK，而那个 agent 既改不了 `tcenv`，也用不上这些话。先修路由；P1 相关的大部分机制在有流量之前冻结。
2. **plan-01 是唯一不依赖 P1 的计划，但本批排错了先后。** 有一种计时期攻击能骗过当前全部检查，修法恰好是 plan-01 自己推到「后续」的计后换输入复验。它应该进第一批。
3. **好几处机制和代码互相矛盾：** overlay 只在 `harness_auto` 打开时渲染，plan-02 的送达设计照写做不出来；信任指纹包含 `experience.md`，经验库每次晋升都会让全部授权失效；自动暂停依赖的「被推翻」标签一条都没有。

## 2. 跨计划的五个问题

### 2.1 提案的对象错了

`acceptance.kind_of` 把这类提案分成 `tool` / `reporting`，`record_proposals` 只拦它们改评测、预算、信任、协议的字样，然后照样允许 `surface=tip` 进入 P1（`taic/harness.py:340-356`）。两条进了 overlay 且 `shadow=false`：

- `b4131be13c4750c8`：「Add a tcenv.cli ab subcommand that compiles several kernel files, times them interleaved…」
- `43c462b0b4f70803`：「在评测报告里打印每个 stage 的编译器寄存器用量（或 spilled 标志）…」

如果送达成功，下一场写核 agent 会在标题「以下条目由两个模型在本硬件上各自提出并经人授予的信任放行」下读到这两句（`taic/harness.py:1139-1140`）。标题本身就不对（两条都是单来源加评审），内容它也执行不了：写核会话只能写 `agent_work/<label>`（§2.5），加不了 `tcenv` 子命令，改不了评测报告。试点把「overlay 没进 TASK」当成要修的送达故障，实际上这次省略挡住了一个路由错误。

合理的做法是分流：`tool`、`reporting`、文档修正一律进开发者队列（和 `# 需要帮助` 一样上看板，或直接生成 P2 草案），永远不进 overlay；overlay 只收下一场 agent 在自己工作目录里能用上的陈述，例如一条 MSL 用法或一个已测的设备事实。这是收窄，不需要新授权。

这一条改了，plan-02 的 `paired_required` 档就没有现存样本：观察到的提案全部落在 `offline_only`，靠宿主离线测试和人审就能判断「改动是否做到了」，用不上搜索 A/B。

### 2.2 自动收窄依赖的信号不存在

plan-03、plan-06 和评分另纸反复把「自动收窄」当安全阀，而现实中唯一的自动收窄是 `sync_trust_status`：同一 target/task/provider/model 至少 8 条已审 claim、来自至少 2 个 run，且 `status='rejected' AND verification='refuted'` 至少占 25%，才暂停授权（`taic/harness.py:1058-1072`）。201 条已审 claim 里 rejected 是 0。这个阀门不是阈值偏高，是输入恒为零。

同一事实也影响 plan-05 和 plan-08：评审参考集没有任何人工负例，测不出误报率；plan-08 质量轴里的「人工采纳率 reasonable/reviewed」会接近 100%，但它反映的是 10-22 的两次批量审计，不是建议质量。

### 2.3 quorum 在结构上到不了

quorum 要求两个委员会、不同模型提出同一个 `proposal_key`（`taic/harness.py:856-884`）。key 是 `sha1(target, task, surface, 归一化 action, dtype)`，归一化只去掉控制字符和 Markdown、压缩空白、转小写（`taic/harness.py:160-172, 219-233`）。两个不同模型必须写出同一句话才算同一提案。flash-attention 试点里同一个模型对同一事实写了两条几乎一样的句子，就已经是两个 key。何况 second 委员会至今没有写过一条结构化提案。

plan-05 用了很大篇幅分析 quorum 的证据独立性（探针 SHA、共享 NOTES、共享上下文），分析的是一条从未触发、也几乎不可能触发的路径。要么承认 P1 的唯一入口就是「单来源 + 评审」，要么重新定义 quorum 为语义一致，而语义一致需要人或模型判断，那它就变成了一次评审。

### 2.4 实验单位选错了

plan-02 的基本单位是「一条提案、一组 seed 配对的搜索 run」。这个单位在本仓库里有三个问题。

- **配对没有配上主要方差。** seed 只决定评测输入；搜索的主要随机性来自 LLM 采样和搜索路径，两臂之间不共享。按 seed 配对后，两臂的差仍然接近两次独立搜索之差，配对带来的方差缩减很小。
- **成本与可检测效应不相称。** 一个 cell 就是一次完整搜索，历史花费 $0.76–15.22。要从两次独立搜索之差里分辨一条提示的小效应，需要的配对数是几十到上百，单条提案的确认费用会到数百美元以上。flash_attention 这类已经停在平台的任务，最终加速比几乎没有可动空间，能动的只有到达平台的轮数或花费。
- **基线不稳定。** 人几乎每天在改 harness，远端模型也会漂移；冻结在某个 base commit 上的确认实验，做完时基线可能已经过期。

更贴合本仓库的单位是 **harness 版本**：在一个固定的小任务集上，每隔一段时间或每次较大改动，跑少量 seed，比较版本 N 与 N−1。成本按版本摊，测的正是 conv2d 从 0.8 到 1.7 那种真正发生过的变化。单条提案只需要回答「是否按预期起作用」，用离线测试和近端行为（新工具有没有被调用、目标失败类型有没有减少）即可；plan-02 现在把近端指标降级为「只报告、不改判」，在这个场景里方向反了。

### 2.5 机制与代码的三处矛盾

**overlay 渲染被 `harness_auto` 门住。** `_session_brief` 只在 `self.search.harness_auto` 为真时才调用 `harness.overlay_text`（`taic/orchestrator.py:2861-2869`）；settle、自动评审和 `sync_trust_status` 也在同一个开关后面（`taic/orchestrator.py:2600-2608`）。plan-02 要求「两臂除这一条 overlay 外逐字段相同」，又禁止「只给 treatment 开 `--harness-auto`」。两臂都关，预置的 overlay 不渲染；两臂都开，两臂会各自 settle 新提案、各自花钱评审，差量不再单一。照现在的写法做不出来，需要新增一个「只渲染冻结 overlay、不 settle、不评审」的运行模式。那是 orchestrator 的行为改动，plan-02 把它写成了 runner 里的一个「宿主送达函数」。

**信任指纹包含知识库。** `current_prompt_sha1` 除提示函数和模板外，还哈希 `experience.md`、`device.md`、后端 skills 和 `taic-tools/SKILL.md`（`taic/trust.py:96-98, 128-148, 172-181`）。后果是：harness 反馈环的预期产物（一次 P2 经验晋升）会让该 target 的全部授权变成 stale prompt；plan-07 第一批给旧条目分配 `entry_id` 只要改写 `experience.md`，同样如此。环跑成功一次，自己就关掉了。重签于是会变成例行公事，人工批准的意义被稀释。plan-03 和 plan-07 都没有写这个耦合。

**写核会话改不了仓库。** `kernel_once` 声明 `local=ALL, user=READ, system=READ`（`taic/flows/kernel_once/__init__.py:38-43`）。hmz 的围栏把 `local` 映射到会话的 workdir，`all` 只把这个根和临时目录放进可写集（`humanize/src/hmz/coganchor/fence/__init__.py:347-407`，`humanize/src/hmz/runtime/flowing/harnessing.py:249-283`）；taic 以 `cwd=agent_work/<label>` 启动 `hmz exec`（`taic/kernel_agent.py:1222-1224`）。仓库、评测缓存 `~/.cache/ai_lowerling/evals`（`tcenv/evaluate.py:989`）和 self-check 授权日志都在家目录下，只读。只要围栏生效，Harmony 那种「agent 去改 `evaluate.py`」在写核会话里走不通。plan-01 §5.2 和 plan-06 §5.9 把 `local=ALL` 写成可能覆盖仓库，与源码不符。

真正还开着的评分改写路径在 P2：code agent 在 detached worktree 里工作（`taic/code_agent.py:359`），动态验收在打过补丁的临时目录里跑 pytest（`taic/code_agent.py:747-759`）。`SECURITY_CRITICAL` 已经包含 `tests/`、`tcenv/evaluate.py`、`tcenv/backends/`，但不含 `tasks/`、`tcenv/task.py`、`tcenv/distributions.py`（`taic/code_agent.py:43-87`）。一个改 `tasks/<task>/task.py` 容差或 cases 的补丁不会被判 `human_gated`。补上这几个路径是一行改动，比整套 TCB 便宜得多，也更直接。

## 3. 逐份判断

**plan-01 验收器抗作弊：做，但换掉本批的头号任务。** 下面这个攻击按代码逻辑能通过当前全部检查，尚未在 GPU 上复现。

正确性阶段对每个用例启动三次：输出先毒化成 `0xFF`，再清零，再毒化（`tcenv/backends/metal/testing.py:377-404`）。一颗核如果只在某个哨兵输出元素是 `0xFF` 图案或 0 时才计算、否则直接返回，三次都会计算，三次输出一致，判正确。计时阶段，每组轮转缓冲只在准备时毒化一次（`tcenv/backends/metal/backend.py:527-532`），随后背靠背启动 `iters=k` 次（`:574-578`）；每组第一次启动后输出已经是正确值，之后的启动全部早退，中位数墙钟接近空核。计后 `spot_check` 只查安全违例，并用同一份 `data0` 核对首末两组输出（`:615-626`），输出是对的，通过。确认阶段复用同一计时协议，发布数字也会被抬高。

修法就是 plan-01 自己写在「后续阶段」第 1 条的计后换输入复验：计时结束后，往已启动的缓冲里装另一组输入、**不重新毒化**，再启动一次并按新输入核对。用 CPU fake launcher 就能复现和回归。这条应进第一批。

相比之下，本批写的「按原始字节判未写」收益窄：浮点输出没写的元素会留着 NaN 图案，现有数值比较本来就判错，只有参考值恰好是 NaN 或整数 −1 的位置才漏，可以排到后面。另外，「派生种子可预测」的担忧偏重了：派生种子包含候选源码的 SHA-256（`taic/orchestrator.py:107-109`），想为派生输入硬编码答案就要找哈希不动点；分布拟合类的结构化 fixture 仍然有价值，种子预测本身不必作为风险驱动。

**plan-02 可证伪预测与效果实验：缩到两件事，其余冻结。** 第一件，修现有代码里 plan-02 自己找出的两个 bug：按数组位置 `zip` 配对（`taic/harness_experiment.py:493-505`），以及 `pair_count` 与 seeds/repetitions 的约束互相矛盾（`:232, 276, 296-300`）。这两处现在就可能产出错的实验结论，与要不要做确认实验无关。第二件，只有在决定要测 overlay 效果时，才设计 §2.5 说的冻结 overlay 运行模式。`predicted_observables`、`change_atoms`、`adoption_terms` 等新字段服务的是 `paired_required` 档，而那一档现在没有样本（§2.1）。评估单位建议改成 harness 版本（§2.4）。

**plan-03 信任与权限治理：只读 `--explain` 值得做，计划回避了两个更大的决定。** 一是授权粒度：三条 grant 都只覆盖 conv2d，最近的 run 有一半是 flash_attention，按 task 授权意味着 P1 在大多数 run 上永远关着。二是指纹范围（§2.5）。另外，自动暂停的输入恒为零（§2.2），v2 的 generation、policy digest、`control_plane_change`、proposer/approver 分记都在给一个没有输入信号、只有一位操作者、三条 grant 的系统加结构。四套身份字符串的现实解法是由人逐条决定授不授权，比维护别名表便宜；v2 冻结。

**plan-04 证据链：冻结。** 它的全部机制（E0–E4、E2H、绑定信封、freshness）服务 `premise` 路径；`premise` 提案至今为 0，`trusted_record` 全为 false。本批的只读审计会产出一条空链。现有代码已经要求 premise 有本场探针和匹配的宿主记录，保持这个 fail-closed 规则即可。重新启动的条件：出现 premise 提案。

**plan-05 独立评审与反共识：Phase 0 的答案已经知道，真正该问的是自动评审还要不要开。** 历史上 5 次评审、人工负例 0 条，「样本不足、停止」是确定结果。自动评审到目前的实际效果，是把两条开发者需求推成了 `reviewed_active` 并写进 overlay（§2.1）。在每周提案量远低于人能看完的数量时，自动评审花钱，还打开了一条绕过 quorum 的单来源激活路径，收益为负。建议先关掉 `harness_review`，或者把评审结论改成只给人看的建议；这是收窄。等提案量超过人能处理的水平，再谈参考集和轮换。quorum 那部分分析见 §2.3。

**plan-06 注入面与运行时安全：本批的声明和语料做，但按流量重排，评分 TCB 降级。** 默认开着、不经信任门、每场都进 TASK 的是 `peer_tips`（`taic.toml:21`）和 NOTES；默认关着、三道门、从未送达的是 P1 overlay。注入语料应先覆盖前者，再覆盖 IMPLEMENT.md，最后才是 overlay。「只读可写性核实」从源码已经能回答（§2.5），剩下的是一次运行期确认：记录每场实际生效的 hmz 版本与围栏，围栏不可用时 fail closed。评分可信计算基另纸在这个威胁模型下大部分不需要，换成 §2.5 末尾那条 `SECURITY_CRITICAL` 补丁，外加「P2 动态验收用基线 commit 的 `tests/` 和 `tasks/`，不用补丁里的」。

**plan-07 经验知识生命周期：盘点一次就够，三项行为里只有一项有用。** `targets/apple-m4-max/experience.md` 是 8.3 KB、9 节，全部 `Confidence: verified`，外加 1 条 harness bullet；「reported」只出现在文件头的说明里。所以「reported 不进 staging」今天过滤不掉任何东西，但作为守卫便宜、正确，可以做。给 10 个条目加不透明 `entry_id`、revision 和 CAS，和 git 历史重复，还会让全部信任授权失效（§2.5）；单 key 撤回只在 P1 打开时才有意义。数据里真实出现的问题是近似重复：同一事实的两条提案、`device.md` 与 `experience.md` 重复记载线程组上限。这在人审入库时顺手去重即可。

## 5. 需要你拍板的三个决定

- **信任指纹要不要包含知识库。** 现状最严格，代价是每次经验晋升都要重签。改成只哈希「怎么问模型」的提示和模板、知识库另行版本化，会让授权在更多情况下保持有效，属于扩大，按 plan-03 的规则要具名批准。
- **授权粒度要不要从 task 放宽到 target。** 同样是扩大。不放宽，P1 在 conv2d 以外的任务上永远不会生效，那就应该明说 P1 只是 conv2d 上的实验。
- **P1 overlay 还要不要作为独立通道存在。** `peer_tips` 已经在每场把同一 run 的经验带进 TASK；P1 overlay 在路由修正后剩下的内容，可能并入 `peer_tips` 的更严格版本，而不是再养一套信任、评审、证据和实验机制。
