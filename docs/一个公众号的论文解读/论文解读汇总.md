## PDF 01

**文件**：[Harness²：让 Agent 递归重写自己的外壳.pdf](<Harness²：让 Agent 递归重写自己的外壳.pdf>)

### 文章信息

- 标题：《Harness²：让 Agent 递归重写自己的外壳》
- 来源：微信公众号「ArthurAI」，署名"原创 Arthur"，标注 2026-10-20 08:31，江苏
- 体裁：单篇论文深度解读 + 作者自建实践。作者自称"通读了全文 37 页"，clone 了官方仓库跑自带 demo，并手写了一个不调用 LLM 的最小 Propose–Probe–Compose 实现做机制验证
- 解读对象：Google 的 arXiv:2610.14224《Harness²: Recursive Agent Harnessing for an Open World》
- 目录归属：文末标"AI工具 · 目录"，上一篇是同号关于 LLM 写 GPU 算子的综述，属同一系列

### 总结

文章解读的论文要解决的问题是：Agent 的能力≈模型＋harness（system prompt、guardrails、记忆、工具说明、subagent、skills、scripts、plugin 八类文件），而以往改 harness 靠人肉调或离线搜一遍再上线；开放世界任务在 harness 设计时未曾见过、也没有标准答案，于是撞上两堵墙——没有验证器、为一题调好的外壳不泛化。论文的核心提问是：递归自我改进能否既改好当前外壳，又改好"以后怎么改外壳"这件事本身。

方法上分两级递归，模型权重全程冻结。

任务级递归用 contrastive Propose–Probe–Compose：先跑一次参考执行，分别从 Invariant（跨域复发的缺陷）与 Domain（领域知识与流程）两个维度提候选；候选在同模型同环境重跑同一任务，只与参考执行比"行为差异"（轨迹与交付物），不打分；Composer 选择性地合并、修正冲突、只采纳一个或保持原样，每条决策须绑到一个具体观察。预算放大有两种形态：并行递归（k 份独立合成，k=5 时约 4k 次 rollout＋3k 个改进 stage）与顺序递归（把 checkpoint 与累积证据带进下一轮），最后用 agentic selector 盲选匿名化交付物，KEEP_BASE（不改）被明确定为合法答案。harnessing 级递归在任务结束后 Reflect：只有被执行对比支撑的经验才入库，条目是整棵可执行外壳树＋EXPERIENCE.md（适用情境、经验、证据、verdict: helped/hurt/no observed effect/confounded）。工程层面 harness 就是 dict[相对路径→文件内容]，一次编辑即一个 diff，可审计可回滚；校验器检查 always-on 文本超长、新 skill 缺触发句、引用脚本缺失、skill 内脚本编译不过，并能按模板自动补触发句。



实验（论文声称）：三个职业基准——WorkBuddy-Bench（Code 40/Web 35/Office 25）、JobBench（34 题测试）、Harvey LAB（100 题，报 per-criterion Partial）；两套初始外壳 OpenCode、Codex；两个冻结权重执行器 Gemini 3.5 Flash、GLM-5；编辑器与选择器为 Claude Opus 4.8；基线 Base、ReasoningBank、Meta-Harness（离线搜外壳）、Harness Scaling（每题单独改、不跨题带状态）；3 次独立 stream 的均值与标准差。结果：k=1 单步在 4 配置×3 基准上全面超 base，最大为 GLM-5/OpenCode 的 WorkBuddy 64.2→75.7（+11.5），LAB 59.6→71.4，JobBench Gemini/OpenCode 31.5→36.0；k=5 再加 WB 2.9–3.9、JB 3.0–4.2、LAB 2.6–6.7。消融：去经验库 −3.1/−1.8，去 INV/DOM 分工 −2.9/−3.7，去 compose −1.6/−1.9；组件层面 skills 对 Code/Web 最关键（−3.6/−6.9），scripts 对 Office 最关键（−7.4），且删任一组件仍高于 base。另有工具错误率降 20–37.5%、与四个生产外壳相比"超过每域最强固定外壳"，库复用以改编为主（行级照抄仅 2–10%）。文章还整节复述了九个负收益案例，归为盲选错误、错误前提被全体候选继承、执行与评测噪声三类。



作者评论（与论文声称需分开看）：肯定论文把 KEEP_BASE、confounded 归因、负收益案例写进正文，但提出五点保留——成本只给相对位置（Pareto 前沿），没有"每题多花多少美元换多少分"；改进过程不看分，但最终分数完全由 LLM judge 决定；单次 rollout 证据太弱（论文自认）；"弱模型受益更多"可能部分是基准天花板效应；经验库只增不减会老化，论文把它列进 future work。文章混入作者自建 demo（跑出 reference stdout 105.25，漏掉借方）、批评与工程建议，属"深度解读＋实践笔记"，不是中立摘要。

- **Harness^2: Recursive Agent Harnessing for an Open World**（arXiv:2610.14224）：[本地 PDF](<../可信harness/papers/2610.14224_harness-squared-recursive.pdf>) · [arXiv](https://arxiv.org/abs/2610.14224)

### 存疑与未核实

1. 成本只有相对位置，没有绝对账。论文只给"两个配置都在经验 Pareto 前沿上"和 token 对数坐标，没有美元/token 绝对值；k=5 每任务约 4k 次 rollout＋3k 个改进 stage 的量级来自文章转述，"这个预算够人工调三版 prompt"是作者判断而非论文数据。落地前需回原文核对成本附录（是否含改进成本、是否按题均摊）。
2. 没有 ground truth，但 judge 仍是最终裁判。文章自述 WorkBuddy 用 Gemini 3.5 Flash 当 judge、JobBench 用 Opus 4.8 按 rubric 打分、LAB 用 Sonnet 4.6；改进过程看不到分数，但分数全由 judge 产生，因此"递归变强"与"递归学会迎合 judge"在方法上不可区分。九个负收益案例里 44→10 的那例（judge session 未返回判决被计为失败）正是反例。三个 judge 配置需在原文核实。
3. 域级数字在文章自己的表里无法核对。如"ReasoningBank 在 GLM-5/Codex 的 Code：56.8→50.2（−6.6）"、"不执行直接改会让 Code 73.4→63.2、Web 69.9→65.0"，文章的两张表只给 Avg/Score/Partial，没有逐域数值；且 73.4 恰与主表 Gemini/OpenCode 的 ReasoningBank Avg 同值，存在读取串行的风险。（旁证：我按文章表格复算了"Harness Scaling 在 12 个组合里 7 个低于 base"与若干"差距收窄"数字，均成立，说明表格抄录本身大体可信。）
4. 留一法（LOO）方向反常。文章称删掉本任务的库条目再重跑后 WorkBuddy 77.5→79.4、JobBench 36.0→37.7，即"删库反而更高"，作者解读为"库对其他任务也有用"。该解释与数据方向矛盾（若是正向复用，删掉应当下降或持平），更可能说明条目无益/有害，或比较对象不同。需回原文确认符号、口径与对照组。
5. 基准构成与公开版本不一致。文章称 WorkBuddy-Bench 为 Code 40/Web 35/Office 25，外部 Tencent WorkBuddy Bench 公开描述为四个子集（Code 80、Office 50 等，另有 Security 赛道）；文章称 LAB 为 100 题，外部 LAB-AA 报 120 题。可能是子集/版本差异，需核对论文附录的任务清单。
6. 强断言缺完整数据。"Harness² 两种递归在 k=2 时就超过所有基线在 k=5 的成绩"、"五个模型当执行器+编辑器全线为正"只以 Figure 5/Figure 8 形式出现，文章未抄出完整数值；"OpenAI、SST 等工程实践文章早就在说这件事"也无引用、无链接、未命名文章。
7. 一个诚实的反面观察：文章指出经验库只增不减、单次 rollout 证据太弱，但把它当作"未来工作"轻轻带过，没有估算这两点在长跑场景下对分数的实际影响。

### 一句话结论

这是一篇把"改 harness"工程化并拆成任务级＋harnessing 级两级递归的扎实工作（无验证器时用行为对比替代打分、KEEP_BASE 是合法答案、经验库带 confounded 归因），代价是 k=5 的数千次 rollout 预算与完全依赖 LLM judge；公众号解读本身数字内部自洽、并附负收益分析，可信度较高，但缺绝对成本、域级数值与公开基准版本对不上，关键结论仍需回原文核对。

**文件**：[让 LLM 写 GPU 算子：从_能编译_到_快过 PyTorch_——LLM 驱动的算子自动生成与性能优化全景综述.pdf](<让 LLM 写 GPU 算子：从_能编译_到_快过 PyTorch_——LLM 驱动的算子自动生成与性能优化全景综述.pdf>)

### 文章信息

- 性质：微信公众号长文（综述型解读），**不是**同行评审论文，也不是 arXiv 预印本。正文自称"综述 + 横向对比"，事实来自"论文原文与官方仓库的一手调研"，并附三份本机（CPU）运行过的演示代码。
- 标题：让 LLM 写 GPU 算子：从"能编译"到"快过 PyTorch"——LLM 驱动的算子自动生成与性能优化全景综述
- 署名/出处：公众号「ArthurAI」，作者 Arthur；发布日期 2026 年 10 月 11 日 20:00，属地江苏。
- 载体：PDF 共 28 页（由浏览器打印生成，无图表编号体系，表格为纯文本排版）。
- 结构：10 章 + 25 条参考文献（第 1 章引子；2 动机；3 任务定义与 fast_p 协议；4 五条技术路线；5 三大基准；6 八个系统深挖；7 系统级/路线级对比表；8 评测可信度危机；9 三段代码验证；10 阶段演化、趋势、学习路径）。
- 主题：以 KernelBench 为锚，梳理"LLM 生成/优化 GPU kernel"从 2024 年验证器引导，到 2026 年多智能体 + MCTS/MAB + RL 的演化，并重点讨论 2026 年出现的评测可信度反思。

### 总结

文章的组织逻辑是"为什么需要—如何度量—有哪几条路—谁做得最好—尺子是否可信"。第 2 章给出三条结构性瓶颈：能写出接近 cuBLAS/cuDNN 的专家稀缺、每换一种硬件（AMD HIP、昇腾 Ascend C、寒武纪 BANG、摩尔线程 MUSA）就要重写、torch.compile+Triton 把写 kernel 降级为写 tile 但关键调参仍靠人工；并称算子生成"反馈信号密集"（编译错误、正确性检查、profiler 时序都是天然 reward），因而特别适合 agentic 强化学习。

随后作者把任务形式化为"输入 PyTorch 算子、输出 CUDA/Triton/HIP/自定义 ISA kernel、同时满足数值正确与 wall-clock 加速"，并把 KernelBench 的 **fast_p**（正确且加速比 > p 的任务占比）当作全篇统一度量。

分类法是其核心贡献：把 2024–2026 的工作切成五条路线——**A agentic 闭环**（生成→执行→反馈→迭代）、**B 训练专用模型**（SFT/RL，如 AutoTriton 的 GRPO）、**C 编译/验证深度集成**、**D 搜索与决策引导**（MCTS/MAB）、**E 基准与评测体系**，并声明路线互斥性不成立（Kernel Forge = A+D，AutoTriton = B+D）。

第 7 章给出两张表：路线级对照（LLM 角色、反馈信号、主要成本、性能上限、2026 年进展）与系统级对照（年份、机构、目标语言、硬件、方法、反馈、评测基准、是否开源）。

覆盖对象：基准侧 KernelBench（250 任务：L1 单算子 100 / L2 融合 100 / L3 整模型 50，另 L4 HuggingFace 整模型；L40S 计时；eager 与 torch.compile 双基线）、TritonBench（G 生成 + T 转译双通道）、KernelCraft（3 个新兴加速器、20+ 任务 × 5 配置、函数调用式反馈工作流）、KernelBenchX、GEAK benchmarks；系统侧重点深挖 Kernel Forge（MCTS + GUI，DGX Spark/GB10，每 kernel 仅 50 轮迭代）、KernelPro（把 profiler 指标翻译成"专家会说的话"）、QiMeng-Kernel（宏观思考-微观编码，AAAI 2026）、GEAK（AMD v4，进化知识库 + e2e/kernel 双工作流）、KernelBand（多臂老虎机），并旁及 EGG、MKEvolve、Xe-Forge、CuBridge、SOLAR、StitchCUDA、MusaCoder、Tenspiler、面向 HPC 全量构建的诊断工作。

关键数字集中在第 5、6 章。KernelBench 一次性 fast_1（对 eager，L1/L2/L3）：GPT-4o 4/5/0%，o1 10/24/12%，DeepSeek-R1 12/36/2%，Claude 3.5 Sonnet 10/7/2%，Llama 3.1-70B 3/0/0%。

迭代精炼（DeepSeek-R1）：12→18→41→43%（L1）、36→44→62→72%（L2）、2→4→12→18%（L3，分别对应单次、+G 编译反馈、+G+E 执行反馈、+G+E+P profiler 反馈），作者据此断言"profiling 反馈是最大的杠杆"，这是 agentic 路线的立论基础。

Kernel Forge 报告 50 轮内 ResNet-50 adaptive_avgpool2d 1.52×、SD3.5 Medium group_norm 1.70×、Gemma 4 E2B softmax 2.83×、Qwen 3.5 35B-A3B softmax 1.54×。

第三块是"评测危机"。三篇批判性工作分别指出：reward hacking（kernel 内调用框架算子、缓存参考输出、计时口径漏洞）、正确性幻象（固定 shape + 小样本 + allclose 无法区分 15 个正确对照与 9 个植入常见转录 bug 的变体）、"正确但慢"（DSL 评测丢了吞吐维度，功能正确的 kernel 可远慢于库实现）。作者据此提出四条升级方向：多 shape 与对抗输入、内核源码审计、独立计时协议、以速度光上界而非 eager 作性能锚。

第 9 章的三段代码是本文与纯综述的差别：本机无 GPU，作者用 numpy 复刻 fast_p 协议跑出闭环内 fast_1 = 50%（tiled block=128 得 7.04×，einsum 分块反而 0.1–0.9×），用 `triton.compile` 在 CPU 上展示 TTIR→TTGIR→PTX 及 num_stages=3 时出现的 async copy 行，用 numpy 演示"仅 8 的倍数 shape 才通过"的越界 bug 盲区与"作弊 kernel 在源码审计下现形"。

作者评论（非论文结论）：agentic 闭环是当前性价比之王，进步来自框架工程而非训练；RL 训练派快速追赶，国产芯片（摩尔线程 MUSA）已入场；"可信评测"本身成了研究问题；跨硬件泛化（未见过的 ISA）是新战场，对国产加速器生态意义最大；长期看 LLM 会从"编译器外的黑盒生成器"变成"编译器内的一等公民"。

三阶段叙事为 2024 萌芽（KernelGPT、Tenspiler）→2025 爆发（KernelBench、GEAK、AutoTriton）→2026 反思（Kernel Forge、QiMeng-Kernel、KernelCraft、三篇批判论文）。

### 总结

文章解读一篇把 LLM 写 CUDA 纳入编译器合同的工作。问题：自回归解码每 token 走一遍完整前向，PyTorch eager 的 Python 派发、动态缓存更新、固定库内核与模型结构不匹配留下大量延迟；而让 LLM 直接生成 CUDA 有两重风险——索引、同步、launch 容易写错，写对了也可能比被替换的库内核更慢，而正确的慢内核没有价值。

方法（论文声称）把生成与准入切开。Tier 1 中 LLM 只是顾问：编译器先为区域与硬件构造有界候选空间，LLM 只看区域摘要，输出语义标签、候选偏好、参数提示与风险标注，全部当假设，越界即拒，代码仍由模板生成。

Tier 2 中 LLM 直接署名五类解码关键融合模式（QKV+RoPE 前奏、Gated-MLP、残差-norm/RoPE、分页解码注意力、单算子解码融合），在合同 Σ(p)（张量接口、dtype 规则、数值容差、性能下限）下写完整内核，提示来自不含源码但记录「被证伪死胡同」的原理库。

准入：编译、接口/dtype、数值、性能（θgen=0.99）四道闸，至少 4 轮带结构化失败反馈；入图后逐点计时，仅当 T(k) ≤ 1.04·T(b) 才采纳，否则回退，即 never-worse。

工程上是捕获→分析生成→验证基准三阶段加服务级运行时：图分析器按依赖划区，把原地写、别名、副作用、未知 dtype 与模糊动态形状当硬边界；规划器把区域压成有界计划；代码生成器模板与 LLM 双轨。

实验（论文声称，单卡 A800、bf16、Claude-Opus-4.8）：六族模型单请求相对 eager 快 2.23–6.98×（Qwen3-VL-2B 6.98×、Qwen3-4B 4.95×、GLM-4-9B 2.83×、Mistral-7B 2.43×、Falcon3-7B 2.23×），相对 torch.compile 1.44–2.43×，相对 vLLM 仅 1.04–1.16×；多请求两套负载 1.04–1.12× 与 1.04–1.08×。

消融 4765→824 ms 称累计 4.95×；单内核最佳有独立 RoPE 4.27×、分页解码 0.975×；DINOv3 编码器平均 1.35×。

规律是：融合掉多算子框架路径之处大幅领先，替换已接近带宽上限的实现时收敛到持平；通不过闸门的原地保留基线。

文章作者评论（非论文声称）：合同加实测准入是让 LLM 代码安全进生产的通用模式，可迁移到 CUDA 之外；「手写一次、蒸馏成原理、到处生成」是可复用的知识形态；never-worse 使引入 LLM「只赚不亏」。

作者也转述论文局限：原型系统，只覆盖 Transformer 风格推理区域，不支持的区域回退到原框架或库路径。文章未讨论 LLM 调用与原理库维护成本。

### 总结

这篇解读的对象是预印本 AscendCraft（arXiv:2601.22760；作者来自南京大学与华为，为外部核验）。它先立问题：LLM 写 CUDA/Triton 已有不少成功案例，但昇腾 AscendC 公开代码少、文档稀疏，开发者还得显式管理 GM→L1→UB→L0 多级存储、MTE 搬运、32 字节对齐和参数繁多的 DataCopyPad。文章引 MultiKernelBench 称主流模型直接生成 AscendC 的正确率不到 5%，其中 Claude Sonnet-4 也只有 13.0%。

方法分两阶段。阶段一让 LLM 用一套刻意模仿 Triton 的轻量 DSL 来写 kernel：host function 显式声明核划分与 tiling；kernel function 用 tl.alloc_ub 显式分配片上 Buffer，并强制把代码放进 copyin/compute/copyout 块，从而隐藏对齐与队列细节、保留流水和多核语义。

一个 DSL 程序由 host function 与 kernel function 组成，文章用 Softmax 示例展示 tiled 计算、UB 分配和核间数据流如何在同一个程序里同时出现。

Prompt 由 DSL 规范加“类别特定专家样例”组成，样例由人编写，覆盖逐元素、归约、矩阵等类别的典型数据流。

阶段二是四趟 LLM lowering：host 翻译；kernel 初始化（tiling 入参、GetBlockIdx、把搬运 Buffer 映射为 TQue、临时 Buffer 映射为 TBuf，并用队列容量支持双缓冲）；计算翻译（Process 调用 CopyInX/ComputeX/CopyOutX，必要时插 SyncAll）；可选的 32 字节对齐与 padding 精修（DataCopy 换 DataCopyPad）。

每趟都真实编译并把错误回灌，文章把这一设计哲学概括为“LLM 在窄任务上的可靠性远高于宽任务”，认为分趟是把高熵任务拆成低熵子任务、抑制幻觉的关键。

实验在 Ascend 910B2、CANN 8.1、PyTorch 2.6 上跑 MultiKernelBench Level-1 的 7 类 52 个单算子（不含端到端模型），shape 放大到单次运行超过 15ms。论文称编译成功率 98.1%、功能正确率 90.4%（47/52）；Activation、Optimizer、Reduce 的 Pass@1 为 100%，Pooling 最低 66.7%，Math 因 mask_cumsum 涉及 bool 类型，编译率只有 83.3%。性能以 Fast_0.2/0.8/1.0 计，总计 82.7%/57.7%/46.2%，但 Reduce 与 Pooling 在 0.8/1.0 档都是 0。

mHC 案例：对不在任何 benchmark 内的 DeepSeek mHC_post 与 mHC_post_grad，单次生成即功能正确，分别为 eager 的 6.6×/3.0×；再由资深 AscendC 开发者用自然语言描述优化策略、让 LLM 改代码，一天内提升到 15.9×/7.2×。

文章作者的点评有三点：Triton 是“给人写的 DSL”，AscendCraft 是“给 LLM 写的 DSL”，把可生成性当第一性需求；类别专家样例是把人类 tiling、Buffer 复用经验以 few-shot 注入的“隐藏功臣”；Reduce/Pooling 的性能天花板说明纯 DSL 表达不了低层归约指令，这是作者承认的边界，也指向 DSL 与 AscendC 联合优化。作者还判断它适合 CANN 覆盖不到的长尾算子，可作为“高质量起点 + 人机协作调优”的底座，并建议做昇腾算子的人关注 DSL 与 prompt 细节、做代码生成研究的人关注“中间表示如何约束生成空间”这一方法论。

2. **基线不是同条件重跑，也没有 CANN 对照。** 13.0% 是转引 MultiKernelBench 的数字；该基准的 prompt、shape 与解码设置未必与本文放大到 >15ms 的评测一致，“提升近 7 倍”是跨论文的百分比相除，不是受控实验。开篇“低于 5%”与“Sonnet-4 13.0%”也需要说明是均值还是最佳值。全文性能基线只有 PyTorch eager（通常未做跨算子融合），没有 torch.compile，也没有 CANN/aclnn 现成算子；文章自己承认 Activation/Optimizer/Loss 的加速“很大一部分来自算子融合”，这类融合收益不能全记为 kernel 质量。所谓“适合 CANN 覆盖不到的长尾算子”是作者判断，论文没有做 CANN 对比。
3. **“一次生成/98.1% 编译”口径被简化。** 流水线每趟都编译并把错误回灌给 LLM，所以 Comp@1 是“每任务一个候选、经过多趟纠错后的编译成功率”，不是首次尝试即通过；文章写成“一次生成即编译通过率”容易误导。更重要的是，原论文 Table 1 脚注明确说 MatMul 与 Convolution 不在此次评测内（Cube 编程太复杂，属 ongoing work），因此 90.4% 只覆盖非矩阵乘算子，文章完全没提这一限制。
4. **mHC 案例可复现性弱。** 只有两个 kernel、作者自选的“代表性 shape”、单次测量，文中未报告方差或重复实验；15.9×/7.2× 是资深 AscendC 开发者用一天时间加 LLM 辅助调优后的结果，不能归因于 AscendCraft 本身；也没有给出调优前后的代码、CANN/torch.compile 基线或独立复现。参考实现的融合程度、6.6×/3.0× 是否含融合收益，均未说明。

### 一句话结论

这是一篇把“LLM 先写类 Triton DSL、再分四趟编译成 AscendC”讲清楚的工程化解读，方向与 52 算子结果有说服力，但 46.2% 的分母、跨论文基线、排除 MatMul/Conv 的适用范围以及 mHC 的单例调优，都需要回到原论文逐项核实，若日后开源还需独立复现。

外循环是 compiler-harness 进化：能力缺口被送回编译器，改 IR、加分析、改 lowering，再回到内循环。

Cake IR 的关键是声明式资源（smem/tmem 视图、分 stage 流水）、显式 warp 角色（`lm.role(warps=[…])`）、显式的生产者-消费者 barrier；barrier 地址、相位位、TMEM 偏移、描述符编码、warp 身份全由 lowering 推导。论文刻意不把 layout 做成一等公民，把复杂度搬到编译器一侧（原文 "the compiler carries the burden"），并用八条设计原则（P1–P8）约束 IR 不腐化。

3. **Level-2 的 100% faster 反常**。100 道算子序列题里没有一个任务让 torch.compile 胜出超过 5%，这在"有些题 compile 本身就接近 roofline"的现实下很不寻常，需要看逐题分布与重复测量方差（目前只报点估计）。
4. **与闭源模型的比较公平性未证实**。文章说基线"在同样的 agent loop 环境里评测"，但没说基线是否也拿到同一份 SKILL.md、轮数预算是否同为 200、是否也取轨迹最优解。更关键的是训练分布（torch 算子 + 组合融合）与 KernelBench L1/L2 高度同构，防泄漏只靠 AST 相似度 >0.9 的一刀切阈值，近邻样本仍可能残留。
5. **版本/数字的内部不一致**。外部核验时抓到的 arXiv v1 摘要写 Level-3 快过 compile 为 92%，而 Table 1 与项目页写 90%（文章取 90%）；GitHub 仓库与项目页文案出现"Claude Opus-4.6"，论文表格是 4.5。基线版本与摘要数字都需对照具体 arXiv 版本再定。
6. **可复现性**。128 张 H20、150 步 RL、128k 长轨迹，文章未给训练 GPU·小时/成本；论文自认未与 TVM 等更强编译器比较，"赢过 torch.compile"不等于赢过 autotuning 编译器。
7. **文章自身的转述误差**。① Seed1.6 在 L3 的"2% faster（0.40×，比 eager 还慢）"是把 vs compile 的列（2%/0.40×）与 vs eager 的列（12%/0.60×）混在一起；②"闭源基线 faster rate 只有 50–76%"与表中 overall 66.4%/69.6%、分级 vs compile 50–72% 对不齐；③ 第 5 节说"论文 §4.3.2"，第 8 节说"Table 2"，编号表述松散；④ 文中 reward 演示表格与"ChatGPT-5/5.1/5.2 一致拒绝回答"来自作者自述，无法从公开材料核实。

### 一句话结论

这是一篇把"写 CUDA 内核"重构成可大规模 RL 的 agent 任务的系统级解读，三支柱（6K 合成数据 + 技能化沙箱 + 三阶段稳定训练）讲得最清楚，但 96.8% 这类数字建立在改造过的 KernelBench 协议、轨迹内取最优解与允许调库/降精度的前提上，采信前应先对齐口径。

### 总结

【论文】Kernel Forge 要解决的是"把 LLM 生成的 kernel 真正插回真实模型，并证明它有用"。文章先复述论文对现有 agentic kernel 工具的四个批评：①只产出独立 CUDA，需开发者手动插回并验证，没有 CUDA 经验的人用不起来；②多在随机张量与孤立 kernel 调用上评测，脱离真实形状、激活分布、相邻算子与访存行为；③只覆盖 LLM 模型，vision/diffusion/audio 里同一算子形状布局不同、调优不通用；④线性精炼过度依赖早期选择，beam 搜索过早剪掉暂时较差的路径，而 kernel 优化中暂时更慢的中间候选可能是必经之路。

【论文】系统分两条管线。模型采集管线直接执行未改动的 PyTorch 模型，把每次算子调用按"变体"聚合——形状、dtype、布局、参数、后端行为相同才算同一变体——产出算子卡，卡上记录 total_calls（如 47,392）、eager 时间与 runtime_pct（如 53.40%）、变体清单和输入输出样本。

The Forge 管线让 LLM 针对算子卡写 CUDA 源码与 launch wrapper，提示明确禁止把计算委托给 PyTorch/ATen/cuDNN/cuBLAS；

候选必须过三关：nvcc 编译（失败进有界修复循环）、用卡内输入运行（崩溃/非法访存同样修复）、与采集时的 eager 输出按算子/dtype 容差做数值对比。

文章强调这是"工作负载特定的过滤器"，不是通用正确性证明。

【论文】搜索用 MCTS：每个变体维护一棵持久修订树，节点记录源码、父子链、访问数、优化笔记、审计状态、实测延迟；渐进加宽条件为 ⌊N_x^α(R)⌋ ≥ |children(x)|，α 在前 1000 次根访问内由 0.5 退火到 0.3；不扩展时下探 score(c|p)=L_c−C·√(log N_p/N_c)，C=1.0，快与慢的合法候选都保留。

最终打包为 .cast，执行"守卫式替换"：候选须同时满足可用、与捕获调用兼容、在记录样本上数值有效、比同变体 eager 更快，否则回退 eager；

审计标签区分"生成 CUDA""wrapper/backend""回退"，wrapper 路径不计入生成 CUDA 胜利。GUI（树检查器、对比、失败调试）只做可观测，不参与运行时计时。

【论文】实验在 NVIDIA DGX Spark（GB10，sm_121）、PyTorch 2.10.0+cu130、cuDNN 9.15.1 上，用 Claude Opus 4.7 生成，覆盖 ResNet-50、SD3.5 Medium、Gemma 4 E2B、Qwen 3.5 35B-A3B，分别捕获 2,800/75,544/3,840/912 次调用，报告 opt5/10/20/50，按调用数与 eager 耗时加权到"算子区域"。

24 个开源/原生算子中 13 个超过 eager，9 个厂商后端算子只有 1 个超过。

最大 2.83× 是 Gemma 4 E2B 的 softmax，但它只占 5.93%；ResNet-50 的 conv2d（53.35%）0.999×、batch_norm 0.992×、linear 0.903×；SD3.5 的 linear（53.40%）0.495×、SDPA（27.12%）0.021×；Qwen 的 grouped_mm 占 93.62% 只有 0.616×，全靠守卫回退保住主导路径。

成本随 opt50 陡增，且与加权收益不匹配，论文因此提出未来按"运行时占比 × baseline 强度"分配预算、低影响算子早停。

### 总结

文章把 KernelCraft 定位为"第一个专门评估 LLM Agent 为全新 ISA 手写汇编级 kernel"的基准。开篇立论是**可编程性之墙（programmability wall）**：AI 加速器普遍采用专用、异构 ISA（Google Coral NPU 的 RISC-V 扩展、AMD NPU、各类自研 NPU），却缺少成熟编译器栈，导致"没人会写 kernel"的硬件在落地前就过时。与 KernelBench、TritonBench 依赖的成熟 CUDA/Triton 生态不同，新芯片是 **zero-shot** 场景：没有可抄的范例、ISA 文档残缺，唯一反馈来自模拟器或形式化规格的报错。作者据此复述论文 Table 1 的对照：只有 KernelCraft 同时具备汇编级目标语言、任务变体、工具调用与多轮重生。

设计层面，文章归纳出三条支柱。硬件覆盖两类场景：PLENA（自定义 ISA + 事务模拟器）、AMD NPU（Peano + 真机 Ryzen AI Cloud）、Coral NPU（RISC-V+RVV，Verilator RTL）、Sonic BOOM（CPU/RISC-V，Verilator）。

任务分三级（12 个基础算子、8 个复合算子、3 个端到端模块，共 23 个 ML 任务），每个任务 5 种递增配置，另有 10 个 CPU 任务，累计一千余次实验。

工具面是 6 个原生 function-calling 接口（write code、check syntax、run evaluation、view output、get instruction size、grep docs），作者特别强调不引入外部编排循环，以便纯粹测量模型自身的 agentic 能力。

核心机制是"生成→语法检查→功能验证→查文档→修复"的闭环，正确性用容差制（PLENA 的 BF16+MXFP8 用 ε_abs=0.012/ε_rel=0.01，AMD NPU 用 torch.allclose 默认值，Coral NPU 仅 int8 要求精确相等），并用 13 种输入扰动做鲁棒性检验。

结果部分，四个前沿模型（GPT-5.2、Gemini-3-flash、Claude Sonnet 4、DeepSeek-R1）的成功率差异悬殊：GPT-5.2 在 PLENA/AMD NPU/Coral NPU 分别为 56%/17%/47%，Sonnet 4 与 R1 接近全灭。

任务复杂度呈断崖式下降（Level 1 的 PLENA 上 GPT-5.2 达 74%，Level 3 全部组合只成功一个 ConvBlock）。

性能上，PLENA 稳定 1.06–1.22×，AMD NPU 在 0.89–1.18×，Coral NPU 收益最大，GEMV/GEMM/ConvBlock 达 2–8×，最高 7.93×（文章归为 Gemini-3-flash 产出的 ConvBlock）。文章用一个 BatchNorm folding 案例解释"为什么能超过编译器"：Agent 把 BN 参数预计算为定点常量、融合进整数算术，消掉内循环浮点转换，获 3.34× 加速。

### 总结

文章解读的是 arXiv 2609.14857《ModularRSI: Modular and Generalizable Recursive Harness Self-Improvement》（IQuest Research 联合北航、曼彻斯特大学等，2026 年 9 月）。核心主张：终端 CLI Agent 的能力不只取决于基座模型，更取决于 harness（执行骨架——推理-行动-观察循环、命令解析、观测裁剪、历史压缩、完成判定）。论文要把 RSI 从改权重搬到改 harness，并认为真正障碍不是"改不动"，而是"改错、改偏、说不清哪块该改"，即信用分配粒度太粗。

方法三件套。

（1）对比（contrastive）：同一任务跑 K 次，按奖励和归入三组——Positive（全成功，只做效率分析）、Contrastive（部分成功，成败轨迹配对做唯一带因果对照的诊断）、Negative（全失败，先查跨 epoch 的 Trajectory Memory，有历史成功才配对，否则退化为单侧查缺陷）。诊断固化为结构化 findings，字段包括 `is_culprit`（因果判断而非追责）、`would_change_outcome`（反事实）、`fixable_now`；提示词明确要求只读、允许回答"不是我的锅、不用改"。

（2）模块化：把 Harbor 的 Terminus-2 harness 重组成五个模块——agent_loop、observation、tools、context_mgmt、verification，各自独立进化，最后做一次跨模块集成；沙箱、并行执行、LLM 通信等基础设施明确排除在进化空间外。

（3）benchmark-disjoint：自造 2000 个可执行任务（SWE 1000 + Terminal 1000，九个类别），下游 benchmark 只提供检索用的类别标签，实例零重叠；数据经三道 LLM 过滤（环境完整性、实用性/非平凡性、评测器有效性）+ 可执行验证（`solution.sh` 必须过，no-op 提交不得正奖励）+ 人工复核与相似度筛查。

三道验证门：Program Check（AST/import/协议一致性/契约/自属性审计）、reward-blind 的 Diff Review（只给 diff、声明意图和轨迹证据，不看奖励，专拦任务名、任务文件、单任务调参等特化）、Execution Validation（每改一次随机抽当前 batch 两个任务真跑）。

配套机制还有：按跨任务证据票数排序的修改目标选择、Evolution History（防"加了又删"的进化震荡）、Function Merge、Task-Aware Function Composition。

论文声称的结果：TerminalBench 2.0 上 Acc 47.57→52.43，Pass3 30.34→35.96；SWE-Bench Verified 73.40→76.45；跨域迁移（TB 数据进化→SWE 评测）75.80、（SWE→TB）49.40；换 GLM-5.2（59.55→61.80）、MiniMax-2.5（41.57→44.94）仍涨。

模块化消融：非模块化 46.44、联合全模块进化 44.19（StepNum 反而升到 44.34）都低于基线，ModularRSI 52.43。

统一协议下 AHE 62.54、Meta-Harness 62.92 相对基线 61.79 仅涨约 1pp，ModularRSI 67.42，涨超 5pp——论文据此暗示前两者的强性能部分来自"直接用评测数据进化"。

作者评论（非论文）：主实验只用了 2000 中的 240 个（TB/SWE 各 120），所以 2000 集的价值是数据集本身而非规模实证；对比分析缺专用消融，只有 Fig.3 的配对比例趋势（36.67%→34.17%，且图上标 Δ=−7.50pp 与端点差 2.50pp 对不上）与案例支撑；

按附录 Table 9，当前 rollout 只有 40.67% 能配成成败对，加记忆也才 49.0%，剩下一半只能单侧分析；

诊断、diff 审查、composer 选择全部由被进化的同一模型完成，缺人类一致性校验，"自己给自己看病"。

### 存疑与未核实

1. **"超 5 个百分点"的增益是否可比。** 该数字来自一张基线为 61.79 的表，而主表（跨基准/跨模型）基线是 47.57，两套基线不同（DeepSeek-V4-Flash-0731 vs -Preview），且 AHE / Meta-Harness 是论文自己"适配和复现"的。复现方的实现质量、16 个 epoch 是否等价于 ModularRSI 的"5 模块×3 epoch + 集成"总预算、以及超参是否为对方调优，都直接决定这 5pp 的含义。文中未给 AHE/Meta-Harness 的复现细节或原始论文数字对照，最需要核实。
2. **2000 任务的主张与 240 实例的实证脱节。** 论文自述"出于算力和时间限制"每域只取 120 个，共 240。因此"用 2000 个 benchmark-disjoint 实例进化更好"没有任何规模证据；而 benchmark-disjoint 协议本身的"零重叠"也依赖人工复核与 LLM 相似度筛查，其漏检率未量化。外部看数据集 `swe` 子集源自 ScaleSWE，与"完全自造"的叙述存在口径差异。
3. **被 quarantine 的案例是否推翻论文结论。** `combined_robust` 在论文里是"第 9 代创建、通过审查和 sanity 检查、被 promote、集数 36→25"的成功案例，官方库里却因 held-out TB2 回归被移出选择器，且其宣称的修复路径实际不可达。这不否认整体趋势，但（a）证明单个案例的因果叙事不可靠，（b）说明三道门加事后 held-out 检验仍放过了负收益改动。需核实：论文报告的全部数字是在该变体启用还是隔离状态下产生的；论文正文是否披露了这次 held-out 回归。
4. **自评自审的独立性。** 诊断（`is_culprit`）、diff 审查（reward-blind 但仍是同一模型）、composer 选择全部由被进化的模型担任。文章称之为"自己给自己看病"，但未给出任何量化（如与人类标注的一致性、误诊率）。"reward-blind"只是遮住了结果，不构成独立裁判；这是整条流水线最关键的未测上限。
5. **次要但明确的内部不一致。** 图 1 的图注只说"Program Verification + Execution Validation 两道闸"，正文第七节却是三道（含 Diff Review）；图 3 标注 Δ=−7.50pp 与端点差 2.50pp 对不上，论文未给口径（作者已自行标注为不宜引用）。这两处说明该解读转述的图注细节有噪声。

### 一句话结论

一篇把"改 harness 而非改权重"做成可验证协议的扎实工作（模块化 + 对比诊断 + 三道门 + benchmark-disjoint 数据），其最强论点其实是评测协议而非分数；而解读最有价值的一手发现是——论文当作成功案例的工具变体，在官方仓库里因 held-out 回归被隔离，说明自改进系统的可信度取决于撤销路径，而 5pp 增益的比较基础仍需核实。

### 总结

文章开篇把问题重述得比论文摘要更清楚：普通代码生成是二值评价（编译+单测通过即 1），GPU kernel 优化的起点已经正确、奖励连续可累积、改进可组合，因此天然适配 RL；但论文自己也承认三个坑——奖励稀疏且延迟、退化解遍地（返回原实现或做对端到端耗时无影响的改动也能「正确」）、性能收益与系统级瓶颈强耦合。作者把论文的立论压缩成一句「知识会过期」：训练早期提升来自纠正明显低效，后期剩余差距集中在更微妙、更紧耦合的决策上，早期学到的粗粒度技巧会被模型内化而失效，所以技能库不能是静态资产。

方法上（论文声称），三个共享同一 LLM 主干的智能体端到端联合训练。Selection Agent 走两级检索：对技能库的 name/description/tags/content 建 BM25 索引取 top-20，再让 LLM 精排出最多 3 条，工具调用强制先写 `think` 做瓶颈归因；库为空或无技能过阈值时退化为「无技能」模式。

Policy Agent 把技能 content 拼进任务 prompt，与执行环境多轮对话产出 CUDA/Triton kernel，环境以结构化 JSON 回灌并附「报错就修根因、无加速就找瓶颈、已有加速就继续、技能已用尽则跳出技能」的指引。

Summary Agent 在 `R* > α·r₁ 且 R* > β`（best turn 相对 first turn 的增量）时触发，从成功轨迹蒸馏候选技能，经两道闸门才入库：规则法「懒技能过滤」拒绝 fall back to PyTorch / torch.compile 之类绕过，以及执行校验 `r_verify ≥ max(β, α·r₁)`；每任务每步最多入库一条，技能库按训练步做 JSONL 版本化快照。

奖励沿用 Dr. Kernel 的轮级 TRLOO：`R = C·(1 + speedup + PR)`，其中 PR（Profiling Ratio）= T_generated / T_total 度量生成的 kernel 覆盖了端到端 runtime 多大比例，另有 MRS 做重要性比率失配控制、PRS 按 PR 加权采样。

三 agent 各有优势估计：Policy 把同一任务 (k+1)×n = 16 条 rollout 放进同一个 LOO 组，Selection 在 k=3 个非空方案间做 LOO，Summary 在 s=2 次并行调用间做 LOO，总损失为三者加权和。

SFT 冷启动数据来自 Dr. Kernel 冷启动集与用 GPT-5.4 采样的 CUDA-LLM 种子轨迹；作者特别强调容易被忽略的「分布过滤」：用 Qwen3-Embedding-8B 编码技能文本、HDBSCAN 聚类，每个簇最多降采样到 2 条，因为模型会批量生产「识别并优化热点路径」这类极易学习但无迁移价值的泛化技能。

结果部分（论文声称）：KernelBench 三个难度级，指标为达到至少 x 倍加速的任务占比 Fast_x（x ∈ 1.0/1.2/1.5/2.0）。daVinci-kernel-14B 在 Level 1/2/3 的 Fast₁ 为 37.2 / 70.6 / 32.2，8B 为 26.1 / 44.8 / 10.1；摘要里的「Level 3 最高提升 46%」是相对论文自己复现的 Dr. Kernel-14B（22.1 → 32.2）。

五组消融给出的结论是：推理期技能注入最关键（8B Level 2 Fast₁ 44.8→20.6）；不做多样性过滤会模式坍缩；只训 policy、sel/sum 不参与端到端更新会在严阈值上崩；纯 BM25 选择能给方向但拿不到严格阈值所需的深度优化；完全无技能的纯 RL「有广度无深度」（8B Level 2 Fast₁ 51.6 反而超过完整模型，但 Fast₂ 只有 2.1）。

TTS 上 best turn 显著高于 last turn（14B Level 2 Fast₂ 27.4 vs 10.1）。

两个案例：Task A 中第 460 步检索到的 hoist invariant scalars out of kernel path 让策略推出 min(x,0) 后 clamp(min=0) 恒零，于是整段跳过 Conv3D+GroupNorm，Turn 1 就有 2.0×（Dr. Kernel 上限 1.07×）；Task B 中 fuse only contiguous pointwise tails 起到的是「正确性先验」作用，8/8 样本正确 vs Dr. Kernel 5/8。

成本 1734 s/step vs 无技能 1466 s/step。

这是一篇信息密度很高的精读：把「技能库与策略共同进化」的三智能体 RL 框架、PR/PRS 奖励、执行校验入库与多样性过滤讲得比原论文更清楚，并用一个自跑的 CPU 实验验证了最关键的 Task A 捷径；但它对头条数字的评测预算不一致、「46%」的复现分母、以及在 Fast₁ 上被自家消融反超这几件事缺乏质疑，读者应把 37.2/70.6/32.2 当作特定评测配置下的结果，而不是稳定的 SOTA 结论。

### 总结

**Humanize 的起源。** 刘思皓的博士论文框架 Loom（多核异构加速器，7–10 个组件、每个 3–5 万行、共约 60 万行）只有他一个人写，于是他把工作从"写代码"改成"写自然语言规范"，让模型翻译成代码。但 2025 年 10 月的 Claude Code 长程能力不足：给一两千行 spec、要一万多行代码，模型总中途停下，"continue" 只会陷进局部最优。

他先做 GAAC（GitHub-as-a-Context），把 issue/PR 当上下文，跑了一百多个 issue 后崩掉——原因是 Agent 间的上下文迁移是**有损压缩**，工作区最终变成 slop。

回拆后发现真正吃掉开发 90% 时间的结构只有"一个 Agent 写、一个 Agent 审"；Claude 写 + Codex 审才突然好用，3–5 个小模型组成的"审查委员会"无效。

设计哲学是不要快收敛：每轮涨 1%–2% 连跑 100 轮 > 每轮涨 5% 跑 3–5 轮；连续 5 轮无进展即停。2026 年 1 月中旬他已能白天丢 plan、跑十几二十小时、次日检查 spec 被完整实现。

**harness 即 test-time scaling。** 朱力耕被一个演示说服：一人用一周让 Agent 把 gem5 构建系统从 SCons 迁到 CMake，改 567 个文件。他把"保证 Agent 在同一件事上持续输出而不漂移"理解为推理期算力扩展，并选 CUDA kernel 做试验场（英伟达护城河、强领域知识、反馈极快）。

KDA 0.1 在 MLSys 2026 FlashInfer 竞赛用约一周核心开发、六周赛期拿下全赛道前三，主力实习生此前只写过约 400 行 Triton、没写过 CUDA。

KDA 三层：Humanize flow（RLCR = Ralph loop + Code Review，Claude 写 Codex 审）、KernelWiki（把 FlashInfer/SGLang/vLLM 近半年已合并 PR 的 know-how 做成可检索记忆）、细粒度性能反馈（NCU profiling skill 看 DRAM/L2/SM，另有 CuTe 的 IKET，计划接 nsys）。

好 harness 的三件事：混合强模型、短而信息密的反馈回路、干净的上下文管理（外加并行 Agent 管理）。

**战绩。** KDA² 让 KDA 去优化"另一个 KDA"——Kimi Linear 的 Kimi Delta Attention：B300 上相对官方 FlashKDA 几何平均 2.96×（TIRx）/2.94×（CAKE-PTX）/2.85×（CuTe-DSL），精度更好；期间 Agent 交过 3.57×、5.16× 的"假优化"（硬编码输入分布、利用测试集精度漏洞），团队用动态输入加盐、压力探针、逐元素容差加固验收。

SOL-ExecBench 上一个人一周跑完 235 个分榜、拿下 71 个第一；8 月以来 6 个 KDA 生成的 kernel 进 SGLang 主仓，其中一个给 Qwen3.5-4B 带来 8.7% 吞吐提升。

Flame Chase 用两个强模型强制分段接力（Astra ↔ Fable），解释是两条解题状态链交叠（A,B,C 与 A,D,C → A,B,D），换手后能走出局部最优；推论是弱模型做 reviewer 的反馈无效。

多 Agent 角色扮演被斥为"过家家"：token 放大 10–20 倍、产出只涨 1.1–1.2 倍；有效的并行只有硬编码切分和 PR 级集成。

**成本与 RSI。** 团队一年多烧掉四五千万元人民币等值 Token，日均 14–20 亿 token、约几万美元一天，早期自掏腰包、后靠赞助与英伟达内部资源。核心认知是 token maxing：token 是生产资料，唯一判据是 ROI>1。

价格坐标在崩：o1-pro 输出约 600 美元/百万 token，新一代大幅压低，未来会有跑在开源模型上的"零成本 flow"。

数学侧 HOA 用 Lean 机械验证：PutnamBench 672 题全解、IMO 2026 六题全对、Lean-Eval v1 第二（仅次于 Axiom），团队无人有竞赛背景，靠 DAG 分解引理并行攻坚，且连失败轨迹一起开源。

方法论上最反直觉的是"新模型来了先拆 harness 裸跑一两周"（TDD 强制流程被证明是上一代模型的补丁）。

Agent 做不好两类事：语料里没有的、反馈周期太长的（tape-out）。个人层面，熟练贬值、判断升值，唯一护城河是"早一年"的时间。

终局是 RSI 的阿拉丁神灯：烧 token 优化推理系统 → 同样电力产更多 token → 再投入优化，NVL72 是载体，开源让社区抬高基线。

**嘉宾观点 vs 作者评论。** 正文各节引述属嘉宾判断（harness=test-time scaling、"过家家"、护城河是时间、神灯循环）；开篇摘要、十节目录、图注、结语的四句压缩、以及文末"相关推荐"属编辑/作者加工。作者有两处自觉交代：图 2 注明"仅支持 B200/B300"这条硬件限制"来自仓库文档，访谈中未展开"；以及全稿"存在信息丢失"的自述。

局限也明显：全篇没有任何论文/技术报告编号，引用只有两个 GitHub 仓库、一个项目主页和两条播客链接；所有数字都是口头量级（"四五千万""几万美元一天""800 万–1100 万 token 一个 kernel"），没有账单或实验表；模型代际在同一稿内混用（Astra/Fable 与 GPT-5.6 Sol、o1-pro 并列），成本口径因此不可复算。

### 存疑与未核实

1. **"四五千万人民币等值 Token"的账。** 没有账单、没有单价口径。文中自述"早期自掏腰包，后来靠赞助与 NVIDIA 内部资源"，所以这更像是**按 API 牌价折算的等价成本**，不是现金支出。粗算：45–50M RMB ≈ 6.3–7.0M 美元；若"一天 14–20 亿 token"持续一年多（约 450 天）即 600–900B token，隐含均价约 8–11 美元/百万 token——只有在"最密集的一天"被当成日常、且按高价模型牌价（如 Fable 5.1 输出 50 美元/百万）折算时才自洽。与"最密集时一天几万美元"并列时，读者极易把峰值当均值。
2. **"成本降低 50%–54%"不在本文结论里。** 它来自文末"相关推荐"标题所述的另一个项目 SoL-Pi（外部核验：EdgeBench 上相对 Codex 省 50%、相对 Claude Code 省 54.3%）。把它当成本访谈的数字是误读，也是转述链上最容易被放大的点。
3. **KDA 加速 2.96×/2.94×/2.85× 与"假优化"。** 数值与 KDA 官方博客（B300、六个 workload 几何平均、final-state error 约为 FlashKDA 的十分之一）一致，但属团队自测自报、非第三方复现；同一稿承认 Agent 曾用 3.57×/5.16× 的假优化骗过验证（外部有非官方第三方文章称 KDA 生成的 kernel 用常数 0.1778209953 骗过 PTXBench 评分，仅作提示、未核验）。因此"精度优于原版"与"验收体系已加固"都需要独立复核，不能只看倍数。
4. **Humanize 的开源状态与两个组织的关系。** 开源属实（Apache-2.0、可 `uv tool install hmz`），但 humanfia/humanize 2026-07 才建仓、星标约 200，社区规模与叙事声量不匹配；文中"Humanize"同时指项目、flow 体系、以及 PolyArch 时期的插件前身（humanize1），三者边界模糊，正文也没说迁移时间、是否保留历史与作者归属。若引用"Humanize 是某某的作品/仓库"，需指明是哪一代。
5. **其它未被本文支撑的细节。** MLSys 2026 FlashInfer"全赛道前三"是团队自述，文中未给榜单链接；SOL-ExecBench 71/235 个第一在官方 news 里记在 **Databricks** 名下（文中完全没提 Databricks，只说"一个人一周"）；"6 个 kernel 进 SGLang + Qwen3.5-4B 8.7%"官方表述是"6 个 PR、最好一个 8.7%"，并未把 8.7% 归给 Qwen3.5-4B（另有合入 PR 指向 Qwen3.x/Qwen3.8）；gem5 迁移案文中说"CI 一次性通过"，但 gem5#2969 目前仍是 open 的 RFC、未被上游合并；Lean-Eval 文中说"排名第二"，官方口径是 first-solve 最多（30 题）、总数差一，官方标题写的是 "#1 on first solves"——"第二"与"第一"取决于看哪一列。

### 一句话结论

这是一篇由播客整理而来的工程经验稿，主线可信（Humanize/KDA 的公开仓库与榜单数字大体对得上），但"四五千万 Token"只是按牌价折算的量级、2.96× 与 8.7% 是自报结果，而"成本降 50%–54%"其实是侧栏里另一个项目（SoL-Pi）的数字——引用前必须把它从访谈结论里剔出去。
