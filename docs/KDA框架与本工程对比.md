# 新人说明：现在的 KDA 怎样跑，本工程怎样公布加速比

这篇写给刚打开本仓库的新人。KDA 指 Kernel Design Agents，用编程代理写显卡内核的那条线。2026 年 9 月以后公开的跑法，是 Humanize 上的轮流，加上已经放出的内核。`NVlabs/kda` 的 `main` 仍是更早的薄说明，本文不把它当成现在的流程。

## 1. 看完这一页就可以停

**要做成的事：** 你能分清两套已经公开的做法。现在的 KDA 用 Humanize 的 `flame_chase` 只排轮次：两个已经登录的编程代理轮流改同一份工作区，写代码和跑测试在代理自己的循环里；每一轮新开会话，预算花完就停；对不对、快不快由流程外面的判卷器决定。本工程的搜索程序自己编排：直接调模型接口，从回复里抽出 Metal，再决定留不留。加速比（最快厂商实现的耗时除以这份程序的耗时，大于 1 表示更短）只有在确认绑上源码指纹、并且计时安静时，才进入对外汇总。

**怎样算读懂：** 合上本节能说出下面三句。

## 2. 现在的 KDA：两个角色轮流，判卷在外面

第 1 章的三句已经够用。这一章只写 2026 年 9 月博客和随后开源的那一版，不写更早那份「先写草稿再收成计划」的薄说明。

2026-09-27 的博客把这次搜索叫做 KDA²：用 Kernel Design Agents 去优化 Kimi Delta Attention。博客把过程归到四样东西：他们称为 Humanize2 的流程（含 `flame_chase`、迭代改写、隔几轮清理工作区）、CAKE 这种给代理写的中间表示、TIRx 的诊断，以及一份会更新的内核知识。公开仓库里没有单独名叫 Humanize2 的项目。能克隆到的运行时是 `humanfia/humanize`。`flame_chase` 在它的 `src/hmz/flows/builtin/flame_chase/__init__.py`。

循环本身很短，而且不编排模型。两个角色 `first_chaser` 和 `second_chaser` 在流程外面各绑一个已经登录的编程代理，例如 Claude 或 Codex。绑成同一个模型也可以。`flame_chase` 只做三件事：选出这一轮的角色，为它新开一次会话，把开任务时的那一句任务交给它。工作区是双方共用的目录。拼提示、从回复里抽出内核、跑评测，都不在这几十行里。代理用自己的终端编译和跑测试。公开的流程里没有名叫 `quick_check` 的函数调用。

| 步骤 | 谁做 | 留下什么 | 谁决定下一步 |
| --- | --- | --- | --- |
| 1 | 开任务的人 | 一句任务，外加两个角色各自的命令行和模型，以及这次运行的预算 | 开任务的人 |
| 2 | 轮到的那个角色 | 它在工作区里改过的文件。这一轮的对话随会话结束丢掉 | 流程开一个新会话，把同一句任务再交给它 |
| 3 | 同一份流程 | `state` 里的 `turn`，记下下一位是谁 | 这一轮正常结束就轮换。`--resume` 从记下的那一位接着来 |
| 4 | 预算或这一轮的启动 | 运行结束 | 预算花完时，正在进行的那一轮抛出花费超限。测试写明：这一轮若是登录失败这类启动拒绝，整次运行停下，另一位不会上场 |

下一位看到的是工作区里的文件，不是上一轮说过的话。流程代码不要求写一份 `NOTES.md`。工作区里有什么，取决于那个代理自己留下了什么。

同一仓库里还有两种相邻的循环，博客没有把它们写成 KDA² 的主路径，这里只作对照：

| 循环 | 和 `flame_chase` 的差别 |
| --- | --- |
| `ralph_loop` | 还是每轮新开会话、只留下仓库，但自始至终是同一个角色 |
| `rlar` | 做事的人留在同一次对话里；每一轮另来一个审查者，交一份带类型的结论，并专门找把测试改弱、把工作做成空壳的情况 |

判卷不在这几十行里。博客写：CuTe 用 IKET 看核里的流水线，TIRx 在 CPU 上做数值仿真和静态检查。这些工具服务英伟达 GPU。TIRx 的诊断外壳后来公开在 `mlc-ai/TIRx-harness`（2026-10-17 仍可克隆），里面有 IKET 和 Nsight Compute 的采集脚本。CAKE 的论文是 arXiv 2608.12629。编译器仓库没有找到。

已经放出的核在 `NVlabs/kda` 的分支 `260927-kda-for-kda`（说明在 2026-10-01 更新过）。三份前向实现和一份 TIRx 反向核。README 写明来源提交曾放在 `humanfia/kda-for-kda` 和 `humanfia/kda-tirx`，这两个地址目前是 404。能克隆的是整理进 NVlabs 分支之后的核。

你读这一章不必做的事：不必安装 `hmz`，不必把 Humanize 接到本仓库，不必在苹果显卡上复现 B300 的倍数。2026-10-19 起，新搜索默认用计划账本记下每条尝试的测法结果；模型仍不自己测、不自己写笔记、不自己决定留不留。差别和理由在 [外部框架经验.md](外部框架经验.md) 的「从 KDA 的笔记学了什么」。

## 3. 本工程已经有自己的一轮

本工程的程序自己推动生成、规划、补丁和确认。每次搜索都由 first 与 second 两个委员会轮流写方案和 Metal 源码，每个委员会恰好一名成员。换不换种子、公布不公布加速比，由编排器 `taic/orchestrator.py` 按评测报告决定。Humanize 不在这条循环里。

| 现在的 KDA | 本工程里相应的做法 | 谁写 | 谁决定 |
| --- | --- | --- | --- |
| 两个角色各绑一个模型，轮流改工作区 | 每次搜索恰好两个委员会，名字是 first 和 second，轮流接手。每个委员会恰好一名成员，一名是一个供应商加一个模型。人数不是 1 就在调用模型之前拒绝，名单也不会被收成第一名。模型只交回方案和一颗完整的核，不自己改仓库 | 模型写在回复里；编排器把核存进候选目录 | 编排器按报告换种子 |
| 每轮新开会话，不传对话 | 规划和补丁都是新的用户消息，里面有当前核和评测反馈；规划另有最近 24 条结果。第 2 轮起开头另有交接句，两名成员是同一个模型时也写。上一轮的助手回复不在这条消息里。一颗候选的修补留在开出它的那条对话里 | 编排器挑选写进下一次提示的内容 | 编排器 |
| 交接物是工作区里的文件 | 下一位读到的是这条新用户消息里的当前核和评测反馈。反馈在 STATUS 之后先是数字头，再是其余段落。规划还带最近 24 条结果。候选目录里仍有 `kernel.metal` 和 `report.json` | 评测进程和编排器 | 评测报告 |
| 预算花完或一轮启动失败就停 | 还会因为连续多轮没有更好的种子、轮数用尽、或贴近估计下界而停。一次连接失败在 `taic/llm.py` 里重试，不会因此换委员会。两个委员会共用一本账、一份转录、一份预算 | 编排器 | 编排器 |
| 判卷在流程外面，工具面向英伟达 GPU | 判卷就是这次评测：编译、接口、安全、数值、墙钟。发布还要源码指纹和安静的计时 | 评测进程 | `taic/policy.py` 与发布闸门 |

默认两名成员都是 deepseek 的 deepseek-flash。`--model` 把这一个模型设到两个委员会上，交接照样发生。不写 `--model` 时，配置里要正好是 first 和 second，各一名，不能重复，也不能多一个或少一个。要两个不同的模型，就在 `taic.toml` 里把两行 `model` 写成不同的名字。初始稿和第 1 轮是 first。第 r 轮（从 1 数）用 `(r - 1) % 2`：0 是 first，1 是 second，所以第 2 轮是 second，第 3 轮回到 first。换委员会不新开预算。公布仍走下面第 4 拍的确认和指纹。

### 已经跑完的数字

本工程这一组来自 `runs/menu/fa-20261007-210204/summary.md`。测量机器在本仓库文档里写成 Apple M4 Max。

这次菜单比较 `flash_attention` 的三套启动配置。预设是 base，每次搜索的预算是 3 美元，九次合在一起的上限是 27 美元。`default` 用题目自带的配置：查询块和键块都是 32，线程数 128，名字是 `32x32t128`。另外两套在搜索之外选定，名字是 `32x16t128` 和 `64x32t256`。菜单让每一套各自成为一次搜索。

| 启动配置 | 发布次数 | 中位数 | 最小 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| default（32×32，128 线程） | 3 | 0.547 | 0.448 | 0.813 |
| 32x16t128 | 2 | 0.761 | 0.633 | 0.888 |
| 64x32t256 | 2 | 0.646 | 0.565 | 0.726 |

汇总的结论是无结论，原因是发布数字的范围重叠。表中每个数都小于 1，也就是都长于这台机器上更快的库实现。这七次里更快的库是 MLX，同一次对照里还有 PyTorch-MPS。

`32x16t128` 和 `64x32t256` 的第 3 次，`result.json` 里花费是 0 美元，停止原因是初始请求重试后仍为 APIConnectionError。这两次的发布加速比为空。

KDA 这一组来自分支 `260927-kda-for-kda` 的 README，测在 NVIDIA B300 上，对照 Moonshot 的 FlashKDA 前向。几何平均是六组工作负载（两种头数，固定长度和两种变长），每组一共 8192 个 token。博客把同一档结果写成约 2.85、2.96、2.94 倍。下表用 README 里的三位小数。

| 实现 | 语言 | 几何平均 |
| --- | --- | ---: |
| `kda-cake-cute` | CuTe | 2.786 倍 |
| `kda-tirx` | TIRx | 2.950 倍 |
| `kda-cake-ptx` | 静态 PTX | 2.914 倍 |

README 写这三份在它的验收里都是 24/24。博客写沿途还出现过大约 3.28 倍、3.57 倍、3.74 倍，事后判定为钻了验收的空子；留下的是上表这一档。

两边的倍数不能合成一个「谁更快」：

| 要看的差别 | 本工程 | 现在公开的 KDA |
| --- | --- | --- |
| 芯片 | 文档中的机器是 Apple M4 Max | B300。愿望清单页面写目前支持 B200 与 B300 |
| 比的对象 | 同一算子上更快的 MLX 或 PyTorch-MPS | 另一颗内核 FlashKDA 的前向 |
| 一轮里能看见的反馈 | 编译结果、数值差、耗时、耗时上界、流水线里的占用、计时波动 | 博客写 CuTe 用 IKET 看核内流水线，TIRx 在 CPU 上做数值仿真和静态检查。这些计数器这台苹果机器没有 |
| 模型能改什么 | 默认用题目自带的网格和线程数。gemm 和 flash_attention 可以在搜索之外另选一套，上面的菜单就是这次选择 | 代理改的是工作区里的核。三份前向核用了三种写法 |
| 一次优化的规模 | 上面每次搜索预算 3 美元 | 博客没有给这次 KDA² 的美元账单。公开的是跑完之后的核 |

启动配置在这里是选出来的。默认搜索用题目自带的一套。gemm 和 flash_attention 可以在单次搜索之外另选切块和线程数，写成 `任务@变体`，或交给契约菜单，让每个选中的配置各自跑一次搜索。上面的表就是这次已经做完的选择。其余题目只用题目自带的那一套。

### 本工程第 1 拍：先得到一颗能当种子的核

系统提示要求模型直接把这颗 Triton 核写成一颗 Metal 核。Triton 在这里是规格文本，主 Python 环境不执行它。这次搜索用的网格和每组线程数，默认就是题目自带的那一套。gemm 和 flash_attention 若在搜索开始前另选了变体，这次搜索就用那一套。

first 委员会按 `initial_user` 交出第一颗核。评测失败时，修补把编译、接口、安全或数值错误喂回这条对话，留在 first 上，默认最多 3 次。初始生成最多做 2 次。每颗评过的核写入：

```text
runs/<一次搜索>/candidates/<序号>_<标签>/
  kernel.metal
  report.json
  feedback.txt
```

第一颗安全并且数值合格的核可以成为种子，这时还不要求它快过厂商实现。仍然没有合格核时，这次搜索停，原因是 `no_valid_initial_kernel`，后面的轮次不开始。

运行配置 `run_config.json` 写失败时，进程退出且不发送模型请求。非空目录上不能另起一次新搜索，要续跑或换一个目录。

### 本工程第 2 拍：诊断之后再写几份方案

轮到的委员会阅读当前种子的源码和评测反馈，从耗时上界、流水线统计和源码指出主要瓶颈，再给出互不相同的方案。这是 `plan_user`。编排器把阶段记为规划。

每一轮的规划都是一条新的用户消息，里面是当前核、评测反馈，以及最近 24 条尝试的结果，用来避开已经失败的假设。评测反馈在 STATUS 之后先是数字头（上界、离下界或基线时间、利用率、计时波动、线程组内存；基线更快不是改算法的理由），再是其余段落。第 1 轮没有交接句，也不接初始稿里的助手回复。第 2 轮起，这条消息开头先写交接句：点明这一轮是哪个委员会，并写明上一轮的对话不在这次请求里。两个成员是同一个模型时，这句也要写。上一轮助手写过的话不附在里面。方案文字记入这次搜索唯一的一份 `runs/<一次搜索>/transcript.jsonl`。

规划请求失败，或两次都抽不出可用方案时，编排器用三份固定改法把这一轮继续做完：按 16 字节读写并让多笔读取同时在路上；数据尽量只读一遍，归约先在一小束一起执行的线程里做；有矩阵乘时改用苹果显卡上的矩阵指令。搜索不因为这次规划失败而结束。

### 本工程第 3 拍：每份方案写一颗核，显卡上逐份评测

每一份方案单独一次补丁请求，这是 `patch_user`：只落实这一份方案，已经能工作的部分保持不动，回复仍是一颗完整的核。每一轮的补丁都是新开的用户消息，不接规划那条对话里的助手回复。第 1 轮没有交接句。第 2 轮起，这条消息先写交接句，再给当前核、评测反馈和这一份方案。评测反馈的数字头在 STATUS 之后，不在交接句后面再抄一份。最近 24 条结果在规划里，不在补丁里。评测失败后的修补是这条对话里的下一条用户消息，留在开出这颗候选的委员会上，不写交接句。

几路模型请求可以重叠。进入评测时排队，一次只用显卡测一份，避免两份核抢时间。每份结果仍写入上一拍那个候选目录。

编排器调用 `taic/policy.py` 更新种子。安全且数值合格、并且快过门槛的候选，换成下一轮种子。门槛默认至少是 1.005 倍，同时还要盖过这次测量的波动，两道里取更严的一道。只是略快，记为噪声内的并列，种子不变。更慢或不合格的核仍留在目录里，种子保持原样。

这台机器的显卡同时负责画面。源码里写明停不下来的循环，会在提交到显卡之前被拒绝。单次启动过久，评测子进程会被杀掉。默认一次超时就停止后面的显卡工作。

一轮里没有换种子，算这一轮停滞。默认连续 4 轮如此就停。也可以因为轮数用尽（默认 12 轮）、下一次请求会超过预算、或已经贴近估计下界而停。预算在下一次模型请求前检查。

### 本工程第 4 拍：确认之后，才谈对外的加速比

搜索过程中的加速比写在候选目录和 `result.json` 里，供下一轮使用。对外汇总另走确认。

确认取当前种子，以及至多再加一名噪声范围内的合格候选（默认池子大小是 2）。用确认阶段单独派生的输入，重复次数是搜索阶段的 2 倍，模式是完整评测。复测里状态正常且最快的那一颗，写成确认胜者。搜索过程里较快的一次留在搜索记录中。

确认会写下：

| 文件 | 里面有什么 |
| --- | --- |
| `confirm_report.json` | 胜者这次复测的报告 |
| `best.metal` | 有合格种子时写下当前胜出源码 |
| `result.json` | 含确认状态；确认成功时含 `confirmation_source_sha256`，即这份源码的 SHA-256 指纹 |
| `ledger.json` | 这次搜索的花费账本 |

有合格种子时，`best.metal` 和 `result.json` 都会留下。汇总里要把某个数展示成确认加速比，下面每一条都成立：结果里有源码指纹；确认状态正常；`confirm_report.json` 正常；`best.metal` 和胜者那份 `kernel.metal` 的指纹都等于该字段；胜出标签指向这份候选；计时安静。少一条时，汇总里的确认加速比为空。搜索过程中的加速比仍记在结果文件里，和确认加速比分开存放。

计时安静指：确认报告未把计时标成嘈杂，并且候选和最强基线的变异系数都不高于 0.05。变异系数是几次计时之间的相对波动。候选没有可用的变异系数时，同样算不安静。不安静时，汇总把这次标成「不确定」。这篇说的「公布」，就是汇总里展示这个确认加速比。

### 本工程每次都带着的笔记

`taic/prompts.py` 拼系统提示。同一次搜索里这份提示保持不变。始终放进提示的两篇是：

| 文件 | 模型用它做什么 |
| --- | --- |
| `taic/skills/apple_gpu_optimization.md` | 按这台苹果显卡来写。笔记依次讲机器概况、选定的启动配置怎样决定写法、搬数据为主的核、计算为主的核、分支与同步、数值安全、建议的改动顺序 |
| `taic/skills/metal_profiling.md` | 读本工程自己的评测反馈：状态、正确性、耗时、上界、流水线统计。笔记写明这条路径把本机能稳定测到的量交给模型 |

规划时若耗时上界的类别是搬数据（memory）或计算（compute），对应的那一节放进这一次规划请求。可选的 Instruments 痕迹默认关着。打开后，慢于最强基线的种子才可能附上痕迹，每次搜索至多 4 次。

### 你读这一章不必做的事

不必改 `taic/prompts.py`，不必把 Humanize 或 CAKE 接进这次搜索，不必为了读懂对照再跑一次搜索，不必把搜索过程中的加速比当成已经公布的结论。

### 确认用的输入种子怎样派生（实现者可跳过）

同一次运行里，同一标签、同一源码、同一阶段的输入可以复算。搜索、确认、复查、取值域扫描使用不同的阶段名。

有运行种子时，评测种子来自一段固定格式的 JSON 文本的 SHA-256。原文是拼接契约头之前的源码。阶段名是 `search`、`confirm`、`recheck`、`domain` 之一。这篇的公布条件不依赖你记住这段格式。

取值域扫描在确认选出胜者之后另做，只看正确性，写入 `domain_report.json`。扫描失败不改已记下的确认状态。

另有一个更严的标记，代码里叫 primary。它在确认加速比已经可以展示的前提下，还要求加速比不低于默认改进门槛，并且取值域扫描通过、扫描绑的是同一份源码和同一道题目。架构说明写明这次真机扫描还没有跑。本文只解释这个标记的条件。第 3 章说的「公布」指汇总里的确认加速比。
