# 外面的搜索框架，搬走哪几件

这篇写给还没读过这些论文的人。CUDA 是英伟达显卡上写内核的一种语言。内核是显卡上跑的一小段计算。本仓库把一道 Triton 题译成苹果显卡上的 Metal，在这一台机器上检查、计时。观测上采纳了哪些记法，写在 [架构/可观测.md](架构/可观测.md)。

每一节先讲那个系统在解决什么、循环怎么转、一个人会看见什么，再写已经定下的判断。判断沿用现成结论。这篇不新加一条，不改搜索代码，不填写 [`实验批准单-搜索开关.md`](实验批准单-搜索开关.md)，也不批准一次新的付费搜索。

文中的数字都注明出处：要么是这次已经写明的判断，要么写在节末链接的页面上。

| 词 | 白话 |
| --- | --- |
| 加速比 | 对照实现的耗时除以这份核的耗时。大于 1，这份更短 |
| fast_1 | 一批题里，算对并且至少达到 1.0 倍的题占多少 |
| 档案 | 留下的多份核。按写法分格，一格通常只留目前最好的一份 |
| 种子 | 这次搜索接着改的那一版。现在一次搜索留一条，下文称为单一种子爬山 |
| 交接 | 下一位拿到的材料。本仓库是一句交接，加上当前核和评测反馈 |

下表是全文地图。各节再写可迁移、不可迁移、约束。合上之前读文末三句。

| 系统 | 已定：搬走的是 |
| --- | --- |
| KernelBench | 多报一个比例：又对、且至少 1.0 倍的题占多少。和每题加速比并排 |
| GEAK / v2 | 由小到大的过滤；用 `taic/hwfeatures.py` 的静态指纹做多样性档案 |
| KernelFoundry | 一次运行里留 2–3 条轨迹，外加一份经验库。显卡串行排队，按美元记分 |
| K-Search | 有结构的计划账本。已接进搜索，开关 `plan_ledger`，默认关 |
| KDA² / flame_chase | 本仓库已经有两个委员会的交接。历史写成有结构的短记录 |
| AlphaEvolve 这一类 | 有界的档案加变异，并且事先登记、同一预算、对照现在的单一种子爬山 |

## KernelBench：先数有多少题又对又至少一样快

斯坦福 Scaling Intelligence 实验室做了一套考卷，名叫 KernelBench。题目是一段 PyTorch（一种常用的深度学习写法）。模型要交出一份更快的显卡核。考卷一共 250 道，分成单算子、几步融合、整段模型三档。论文页面写明这个规模。

一个人看见的循环很短。模型读参考程序，写一版核。环境编译、对答案、计时，也可以把编译错误、对错和性能分析喂回去，让它再写一版。指标叫 fast_p：既算对、又比对照快过门槛 p 的题目，占全部题目的比例。p 取 1，就是至少一样快，记作 fast_1。

论文 HTML 的摘要写：开箱即用时，最强的推理模型在不到 20% 的题目上能追上 PyTorch。同一页的表 1 有一格是 43%：DeepSeek-R1、第 1 档、把上一次的核、执行结果和性能分析都喂回去（表里记作 G+E+P）、10 次调用的预算，fast_1 为 43%。同一格的单次尝试是 12%。已定判断把这件事记成：一次生成不到 20%；迭代加上执行和性能分析，大约到 43%。43% 是这一格，摘要里的不到 20% 是开箱即用的总述。

| | |
| --- | --- |
| 可迁移 | 汇报时并列两个数：每题加速比，以及一个 fast_1 式的比例（算对并且至少 1.0 倍的题占多少） |
| 不可迁移 | 它在 CUDA 上铺开多种后端、上百道题的那种规模 |
| 约束 | 这个比例跟在每题数字旁边。对外加速比的规则不变：确认测量绑上源码指纹之后，才进入汇总 |

出处：论文 [arXiv:2502.10517](https://arxiv.org/abs/2502.10517)，正文页 [2502.10517](https://arxiv.org/html/2502.10517)。代码：[ScalingIntelligence/KernelBench 的 v0.1](https://github.com/ScalingIntelligence/KernelBench/tree/v0.1)。

## GEAK：四个角色改一版核，v2 再留一架子不同写法

GEAK 是 AMD 的内核代理，全称是 Generating Efficient AI-centric GPU Kernels。它要的是：给 AMD 的 Instinct 显卡写出又对又快的 Triton 核。Triton 是一种比较好写的显卡语言，本仓库也从 Triton 题目出发，再译成 Metal。

第一篇论文里的循环是四步，一个人能对上号：

1. 生成者按题目写一版核。
2. 评估者先查能不能跑对。对了才量快慢。
3. 写错了，反省者读报错，指出问题。
4. 优化者针对已经算对的核，再想怎么变快。

论文摘要写：正确率最高到 63%，执行加速最高到 2.59 倍。测在 AMD 的卡上。

v2 的博客把「优化已有的核」写成另一套循环，名叫 GEAK-OpenEvolve。它留一张多样性的地图：同一种写法的格子里放目前最好的核，不同写法可以并存。博客把格子定成 9 个轴：融合、自动调参覆盖、显存访问、算法复杂度、波前利用率、软件流水、数值稳定、正确与可移植、优化范围。坐标由另一个模型打 0 到 1 分。评测则先跑小输入，再跑中等输入，最后才跑全尺寸，差的早停。博客写多个后代在不同显卡上同时跑。

| | |
| --- | --- |
| 可迁移 | 由小到大的过滤；一份多样性档案。档案的坐标用本仓库 `taic/hwfeatures.py` 的静态指纹。该文件头写明只做静态检测，不向显卡派发。指纹标的是源码里已有的特征，例如向量访问、线程组暂存、双缓冲 |
| 不可迁移 | 多张显卡同时评测；写给 ROCm（AMD 显卡软件栈）的那些提示 |
| 约束 | 档案坐标来自读源码，费用是零次显卡派发。不照搬博客里那 9 个由模型打分的轴。`diversity_archive` 已接进搜索，默认关：最多 4 个签名，连续两轮没有新种子时才让最后一条未开始的分支改其中一颗 |

出处：论文 [arXiv:2507.23194](https://arxiv.org/abs/2507.23194)，正文页 [2507.23194](https://arxiv.org/html/2507.23194)。这篇论文的 HTML 里没有代码下载地址。v2 的九维格子和由小到大过滤写在 [AMD 的 GEAK-Triton v2 博客](https://rocm.blogs.amd.com/artificial-intelligence/geak-agents-family/README.html)。OpenEvolve 这一支的代码：[AMD-AGI/GEAK-agent 的 geak-openevolve](https://github.com/AMD-AGI/GEAK-agent/tree/geak-openevolve)。

## KernelFoundry：几群核一起进化

KernelFoundry 要解决的是：只沿一条核往下改，很快会挤进同一种写法。它维护一份档案，用核的行为特征分格（论文写这些坐标来自对源码的静态分析）。每一轮选父母、让模型改出后代、编译、对答案、计时，一格里只留下更快的那份。

选择父母的办法里有一种叫岛：几群核各自演化。论文 HTML 写，每隔若干代，把每座岛上最好的几份送到下一座岛。写核的模型和改提示词的模型是分开的。过去哪些改动让成绩变好，会收成下一次提示里的一句方向。项目页把 KernelBench 上的结果写成 SYCL 核平均 2.3 倍。论文 HTML（v2）把同一项写成平均 2.32 倍。已定判断记作平均 2.3 倍。SYCL 是一种跨平台的显卡语言。本仓库交出的是 Metal。

| | |
| --- | --- |
| 可迁移 | 岛的缩小版：一次运行里留 2–3 条轨迹。再加一份经验库，用来记下哪类改动曾经有效 |
| 不可迁移 | 已定判断没有另列整套多岛或分角色提示词。可搬走的就是上面两件 |
| 约束 | 这台机器的显卡是串行的。这几条轨迹共用一条评测队列。记分用每一美元换来的加速 |

出处：论文 [arXiv:2603.12440](https://arxiv.org/abs/2603.12440)，正文页 [2603.12440v2](https://arxiv.org/html/2603.12440v2)（平均 2.32 倍写在这一页）。项目页（平均 2.3 倍写在这一页）：[isl-org.github.io/kernelfoundry](https://isl-org.github.io/kernelfoundry/)。代码：[isl-org/kernelfoundry](https://github.com/isl-org/kernelfoundry)。

## K-Search：想法留在树上，写坏一次不把想法丢掉

K-Search 是伯克利的内核搜索。它针对的情况是：一条优化思路要分好几步才成立，中间一步可能编译失败，或者暂时变慢。若系统只保存「当前这份源码」，这次失败会把整条思路一起扔掉。

一个人看见的是一棵计划树，循环分三拍：

1. 树上每个待试节点是一个意图，例如「用填充解决存储体冲突」，挂在某一份父程序上。世界模型给它一个优先分，论文记作 V，范围 0 到 1。选优先分最高的那个。
2. 然后才让模型把这个意图写成具体程序，交给评测。评测返回对错、耗时和编译或性能日志。
3. 世界模型根据这次结果更新树：可以加新意图，也可以改优先分。论文的提法是：高层计划和底层实现拆开，暂时的实现缺陷不会让系统丢掉这条思路。

论文摘要写平均 2.10 倍、复杂 MoE 核上最高 14.3 倍。正文写明比较对象是 OpenEvolve。公开仓库的说明里列了 MLX（苹果芯片上的一个机器学习库）后端。

这和本仓库的 `plan_ledger` 对得上。开关默认关。打开后，一次方案记成四类结果之一：赢、噪声内并列、写对了但没有变快（方向已否定）、接口错误或编译失败或没有内核（方向还没有被计时否定）。节点不带模型自己填的分数或置信。

| | |
| --- | --- |
| 可迁移 | 计划账本：实现失败之后意图还在。这一条已经在 `taic/plan_ledger.py`，默认关 |
| 不可迁移 | 论文里的优先分和置信不进本仓库的账本。相对 OpenEvolve 的倍数留在原文，不当作本仓库的目标 |
| 约束 | 默认搜索仍用最近 24 条文本历史。打开账本不构成一次新的付费搜索 |

出处：论文 [arXiv:2602.19128](https://arxiv.org/abs/2602.19128)。代码（说明里列了 MLX 后端）：[caoshiyi/K-Search](https://github.com/caoshiyi/K-Search)。

## KDA²：两个人轮流，下一位只看见工作区

KDA² 是英伟达 Kernel Design Agents 在 2026 年 9 月公开的一轮：用这套代理去优化另一个也叫 KDA 的算子。一个人看见的循环是 Humanize 里的 `flame_chase`。Humanize 是一个驱动已经登录的编程代理的运行时。两个角色轮流上场。每一轮新开一次会话。交给下一位的是工作区里的文件。上一轮的对话不带走。对不对、快不快由这个循环外面的判卷决定。

本仓库已经有对应的一轮：每次搜索恰好两个委员会，名字是 first 和 second，各一名成员；第 2 轮起有交接句，两名成员是同一个模型时也写；编排器根据评测决定留谁。细节、已经公开的倍数和仓库地址写在 [`KDA框架与本工程对比.md`](KDA框架与本工程对比.md)。这篇不把那一页再抄一遍。

已定的教训是：交接的质量决定下限。本仓库要把已有历史写成有结构的短记录。Humanize 留在它自己的仓库里。

| | |
| --- | --- |
| 可迁移 | 把现有交接的历史写得更有结构，篇幅保持短 |
| 不可迁移 | 把 Humanize 接进本仓库；英伟达那套判卷工具 |
| 约束 | 判卷仍由编排器做。两个委员会、交接句、一次预算，维持现在的分法 |

出处：博客 [KDA²，2026-09-27](https://nvlabs.github.io/kda/blog/2026-09-27-kda-for-kda/)。内核分支 [NVlabs/kda 的 260927-kda-for-kda](https://github.com/NVlabs/kda/tree/260927-kda-for-kda)。`flame_chase` 目录 [humanfia/humanize 下的 flame_chase](https://github.com/humanfia/humanize/tree/main/src/hmz/flows/builtin/flame_chase)。本仓库对照：[KDA框架与本工程对比.md](KDA框架与本工程对比.md)。

## AlphaEvolve：档案里留着好程序，再让模型改一版

AlphaEvolve 是 Google DeepMind 的进化式编程代理。它要解决的问题更宽：凡是能自动打分的程序，都可以一轮轮改好。一个人看见的循环是：

1. 你给一份初始程序，并标出允许改的区域，再给一个自动评分函数。
2. 程序库里存着以前的版本和分数。抽样器抽出若干份，拼进提示。
3. 模型交出修改（一段查找替换）。套上去得到新程序。
4. 评分函数打分。有希望的版本登记回程序库，成为以后的父母。

DeepMind 公开了论文、公告，以及一份数学结果笔记本。结果仓库的说明写明：里面没有用来运行 AlphaEvolve 的代码。能克隆来跑的公开再实现是 OpenEvolve。

已定判断：档案加变异这个框可以搬。在一台串行显卡和美元预算上，它必须是有界的一版，并且是事先登记的、同一预算的对照，对象是现在的单一种子爬山。

| | |
| --- | --- |
| 可迁移 | 档案加变异。代码里的档案最多 4 个签名，而且只在停滞之后换最后一条分支的亲本 |
| 不可迁移 | 已定判断没有把 DeepMind 的全套流程或 OpenEvolve 整仓接进来 |
| 约束 | 代码里的上界是 4 个签名，不是早先记下的 8。论文里没有这个数字。对照必须事先登记、预算相同、对着单一种子爬山。这篇不填写 [`实验批准单-搜索开关.md`](实验批准单-搜索开关.md) |

出处：论文 [arXiv:2506.13131](https://arxiv.org/abs/2506.13131)，正文页 [2506.13131v1](https://arxiv.org/html/2506.13131v1)。公告：[DeepMind 博客](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)。结果仓库的 README 写明不含运行 AlphaEvolve 的代码：[google-deepmind/alphaevolve_results](https://github.com/google-deepmind/alphaevolve_results)。公开再实现：[algorithmicsuperintelligence/openevolve](https://github.com/algorithmicsuperintelligence/openevolve)。

## 剖析放在哪：他们怎么教，本仓库怎么做

上面各节写的是搜索怎么转。这一节只写「性能分析」这一件事：谁去测量，模型怎样被教会去读。

他们都不把剖析器做成模型自己发现、自己调用的协议。测量在循环外面做完，再把结果交回下一次提示，或写成一份给编程代理看的技能。

| 系统 | 谁跑剖析 | 模型怎样读到 |
| --- | --- | --- |
| KernelBench | 考场编译、对答案、计时，并可以做性能分析 | 下一轮提示贴上上一次的核、执行结果和分析。论文表 1 把这一格记作 G+E+P |
| GEAK / KernelFoundry | 评测角色或评测队列打分 | 分数和错误写回生成者或进化档案，不由模型临时决定去 profile |
| K-Search | 低层实现跑完留下轨迹 | 轨迹更新计划树。失败的实现不把「还想试什么」删掉 |
| KDA² | `flame_chase` 不跑剖析。CuTe 用 IKET，TIRx 用 CPU 上的数值仿真和静态检查；采集脚本在 TIRx harness 里 | 一份技能告诉代理先测量、再对症状、再改。代理用自己的命令行去执行脚本。判卷仍在循环外 |
| AlphaEvolve / OpenEvolve | 登记好的评分函数打分 | 分数回到程序库，成为下一轮的父母。模型交出的是程序修改，不是「请再 profile 一次」 |

本仓库把「教模型读」和「谁去测」分开。`taic/tools.py` 里没有剖析。那里只有 `lookup_msl`（查一节 MSL）和 `quick_check`（编译和正确性，不返回耗时）。

| 本仓库的一件事 | 放在 | 默认 |
| --- | --- | --- |
| 每次评测写出耗时上界、占用 | `tcenv/profile.py`，进评测报告 | 开 |
| 这些字段是什么意思 | `taic/skills/metal_profiling.md`，在系统提示里 | 开 |
| 规划时只附上访存或计算那一节 | `taic/symptom.py`，看报告里的 `roofline.bound` | 开 |
| 种子慢于库基线时用 Instruments 抓痕迹，文字贴进下一轮 | 编排器调用 `tcenv/xctrace.py`；说明在 `taic/skills/profiler_evidence.md` | 关（`profile_poor`） |

模型不能自己决定去抓 Instruments。编排器在完整评测之后把数字放进反馈；可选的那次抓取也要先拿到和评测同一把显卡锁。

### 这一块还有没有改善空间

有，而且不在「把剖析搬进工具模块」或「让模型自己跑 Instruments」。

评测反馈在截到约 6000 字之前，STATUS 后面就是数字头：上界类别、离下界几倍或「基线已经快过这个界，目标是基线时间」、对应利用率、计时波动、线程组内存。截断砍的是后面的正确性散文，这几行留得住。基线已经快过下界时不写离界倍数，避免把「已经到峰值的 94%」说成目标。

`profile_poor` 仍关着。打开它是一次对照，不是这篇的改动，也不填写 [`实验批准单-搜索开关.md`](实验批准单-搜索开关.md)。Metal 不把 Nsight Compute 那类计数器交给程序，所以不把 KDA 的 Nsight 技能接进来。

## 若只记三句

1. K-Search 的计划账本已经在搜索里，开关 `plan_ledger`，默认关。接口错误或没有内核不算这条方向已经被否定。
2. fast_p 式的汇报是测量口径的改动：和每题加速比并排，写出算对并且至少 1.0 倍的题占多少。
3. flame_chase 在本仓库已经是两个委员会的交接。
