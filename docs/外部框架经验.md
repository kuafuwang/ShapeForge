# 外面的搜索框架，搬走哪几件

这篇写给还没读过这些论文的人。下面各节先讲别人的系统在解决什么。已经进本仓库默认搜索的，主要是计划账本：下一轮能看见每条尝试是被计时否定了，还是根本没测到。多样性档案、经验索引、硬件提示默认关着。不要把论文里的循环当成现在就要这样操作。

CUDA 是英伟达显卡上写内核的一种语言。内核是显卡上跑的一小段计算。本仓库把一道 Triton 题译成苹果显卡上的 Metal，在这一台机器上检查、计时。观测上采纳了哪些记法，写在 [架构/可观测.md](架构/可观测.md)。

每一节先讲那个系统在解决什么、循环怎么转、一个人会看见什么，再写已经定下的判断。2026-10-19 把笔记这一层写进默认搜索，理由、差别和不照抄的部分在 [从 KDA 的笔记学了什么](#从-kda-的笔记学了什么)。这篇仍不填写 [`实验批准单-搜索开关.md`](实验批准单-搜索开关.md)，也不批准一次新的付费搜索。

文中的数字都注明出处：要么是这次已经写明的判断，要么写在节末链接的页面上。

| 词 | 白话 |
| --- | --- |
| 加速比 | 对照实现的耗时除以这份核的耗时。大于 1，这份更短 |
| fast_1 | 一批题里，算对并且至少达到 1.0 倍的题占多少 |
| 档案 | 留下的多份核。按写法分格，一格通常只留目前最好的一份 |
| 种子 | 这次搜索接着改的那一版。现在一次搜索留一条，下文称为单一种子爬山 |
| 交接 | 下一位拿到的材料。本仓库是一句交接，加上当前核和评测反馈 |

下表是全文地图。各节再写可迁移、不可迁移、约束。合上之前读文末三句。

| 系统 | 已定：搬走的是 |
| --- | --- |
| KernelBench | 多报一个比例：又对、且至少 1.0 倍的题占多少。和每题加速比并排 |
| GEAK / v2 | 由小到大的过滤；用 `taic/hwfeatures.py` 的静态指纹做多样性档案 |
| KernelFoundry | 一次运行里留多条改法（本仓库默认 3 条，评测排队）。经验库默认不读。按美元的增益只出现在汇总里，不决定留哪一版 |
| K-Search | 有结构的计划账本。已接进搜索，开关 `plan_ledger`，默认开。留不留仍由评测决定 |
| KDA² / flame_chase | 本仓库已经有两个委员会的交接。历史写成有结构的短记录 |
| AlphaEvolve 这一类 | 有界的档案加变异，并且事先登记、同一预算、对照现在的单一种子爬山 |

## KernelBench：先数有多少题又对又至少一样快

斯坦福 Scaling Intelligence 实验室做了一套考卷，名叫 KernelBench。题目是一段 PyTorch（一种常用的深度学习写法）。模型要交出一份更快的显卡核。考卷一共 250 道，分成单算子、几步融合、整段模型三档。论文页面写明这个规模。

一个人看见的循环很短。模型读参考程序，写一版核。环境编译、对答案、计时，也可以把编译错误、对错和性能分析喂回去，让它再写一版。指标叫 fast_p：既算对、又比对照快过门槛 p 的题目，占全部题目的比例。p 取 1，就是至少一样快，记作 fast_1。

论文 HTML 的摘要写：开箱即用时，最强的推理模型在不到 20% 的题目上能追上 PyTorch。同一页的表 1 有一格是 43%：DeepSeek-R1、第 1 档、把上一次的核、执行结果和性能分析都喂回去（表里记作 G+E+P）、10 次调用的预算，fast_1 为 43%。同一格的单次尝试是 12%。已定判断把这件事记成：一次生成不到 20%；迭代加上执行和性能分析，大约到 43%。43% 是这一格，摘要里的不到 20% 是开箱即用的总述。

| | |
| --- | --- |
| 可迁移 | 汇报时并列两个数：每题加速比，以及一个 fast_1 式的比例（算对并且至少 1.0 倍的题占多少） |
| 不可迁移 | 它在 CUDA 上铺开多种后端、上百道题的那种规模 |
| 约束 | 这个比例跟在每题数字旁边。对外加速比的规则不变：确认测量绑上源码指纹之后，才进入汇总 |

出处：论文 [arXiv:2502.10517](https://arxiv.org/abs/2502.10517)，正文页 [2502.10517](https://arxiv.org/html/2502.10517)。代码：[ScalingIntelligence/KernelBench 的 v0.1](https://github.com/ScalingIntelligence/KernelBench/tree/v0.1)。

## GEAK：四个角色改一版核，v2 再留一架子不同写法

GEAK 是 AMD 的内核代理，全称是 Generating Efficient AI-centric GPU Kernels。它要的是：给 AMD 的 Instinct 显卡写出又对又快的 Triton 核。Triton 是一种比较好写的显卡语言，本仓库也从 Triton 题目出发，再译成 Metal。

第一篇论文里的循环是四步，一个人能对上号：

1. 生成者按题目写一版核。
2. 评估者先查能不能跑对。对了才量快慢。
3. 写错了，反省者读报错，指出问题。
4. 优化者针对已经算对的核，再想怎么变快。

论文摘要写：正确率最高到 63%，执行加速最高到 2.59 倍。测在 AMD 的卡上。

v2 的博客把「优化已有的核」写成另一套循环，名叫 GEAK-OpenEvolve。它留一张多样性的地图：同一种写法的格子里放目前最好的核，不同写法可以并存。博客把格子定成 9 个轴：融合、自动调参覆盖、显存访问、算法复杂度、波前利用率、软件流水、数值稳定、正确与可移植、优化范围。坐标由另一个模型打 0 到 1 分。评测则先跑小输入，再跑中等输入，最后才跑全尺寸，差的早停。博客写多个后代在不同显卡上同时跑。

| | |
| --- | --- |
| 可迁移 | 由小到大的过滤；一份多样性档案。档案的坐标用本仓库 `taic/hwfeatures.py` 的静态指纹。该文件头写明只做静态检测，不向显卡派发。指纹标的是源码里已有的特征，例如向量访问、线程组暂存、双缓冲 |
| 不可迁移 | 多张显卡同时评测；写给 ROCm（AMD 显卡软件栈）的那些提示 |
| 约束 | 档案坐标来自读源码，费用是零次显卡派发。不照搬博客里那 9 个由模型打分的轴。`diversity_archive` 已接进搜索，默认关：最多 4 个签名，连续两轮没有新种子时才让最后一条未开始的分支改其中一颗 |

出处：论文 [arXiv:2507.23194](https://arxiv.org/abs/2507.23194)，正文页 [2507.23194](https://arxiv.org/html/2507.23194)。这篇论文的 HTML 里没有代码下载地址。v2 的九维格子和由小到大过滤写在 [AMD 的 GEAK-Triton v2 博客](https://rocm.blogs.amd.com/artificial-intelligence/geak-agents-family/README.html)。OpenEvolve 这一支的代码：[AMD-AGI/GEAK-agent 的 geak-openevolve](https://github.com/AMD-AGI/GEAK-agent/tree/geak-openevolve)。

## KernelFoundry：几群核一起进化

KernelFoundry 要解决的是：只沿一条核往下改，很快会挤进同一种写法。它维护一份档案，用核的行为特征分格（论文写这些坐标来自对源码的静态分析）。每一轮选父母、让模型改出后代、编译、对答案、计时，一格里只留下更快的那份。

选择父母的办法里有一种叫岛：几群核各自演化。论文 HTML 写，每隔若干代，把每座岛上最好的几份送到下一座岛。写核的模型和改提示词的模型是分开的。过去哪些改动让成绩变好，会收成下一次提示里的一句方向。项目页把 KernelBench 上的结果写成 SYCL 核平均 2.3 倍。论文 HTML（v2）把同一项写成平均 2.32 倍。已定判断记作平均 2.3 倍。SYCL 是一种跨平台的显卡语言。本仓库交出的是 Metal。

| | |
| --- | --- |
| 可迁移 | 一次运行里留多条改法。再加一份经验库，用来记下哪类改动曾经有效。经验索引的代码在 `taic/experience.py`，默认不读任何文件。`gain_per_usd` 在汇总里，不参与留种子 |
| 不可迁移 | 已定判断没有另列整套多岛或分角色提示词。可搬走的就是上面两件 |
| 约束 | 这台机器的显卡是串行的。这几条轨迹共用一条评测队列。记分用每一美元换来的加速 |

出处：论文 [arXiv:2603.12440](https://arxiv.org/abs/2603.12440)，正文页 [2603.12440v2](https://arxiv.org/html/2603.12440v2)（平均 2.32 倍写在这一页）。项目页（平均 2.3 倍写在这一页）：[isl-org.github.io/kernelfoundry](https://isl-org.github.io/kernelfoundry/)。代码：[isl-org/kernelfoundry](https://github.com/isl-org/kernelfoundry)。

## K-Search：想法留在树上，写坏一次不把想法丢掉

K-Search 是伯克利的内核搜索。它针对的情况是：一条优化思路要分好几步才成立，中间一步可能编译失败，或者暂时变慢。若系统只保存「当前这份源码」，这次失败会把整条思路一起扔掉。

一个人看见的是一棵计划树，循环分三拍：

1. 树上每个待试节点是一个意图，例如「用填充解决存储体冲突」，挂在某一份父程序上。世界模型给它一个优先分，论文记作 V，范围 0 到 1。选优先分最高的那个。
2. 然后才让模型把这个意图写成具体程序，交给评测。评测返回对错、耗时和编译或性能日志。
3. 世界模型根据这次结果更新树：可以加新意图，也可以改优先分。论文的提法是：高层计划和底层实现拆开，暂时的实现缺陷不会让系统丢掉这条思路。

论文摘要写平均 2.10 倍、复杂 MoE 核上最高 14.3 倍。正文写明比较对象是 OpenEvolve。公开仓库的说明里列了 MLX（苹果芯片上的一个机器学习库）后端。

这和本仓库的 `plan_ledger` 对得上。开关默认开。一次方案记成四类结果之一：赢、噪声内并列、写对了但没有变快（方向已否定）、接口错误或编译失败或没有内核（方向还没有被计时否定）。节点不带模型自己填的分数或置信。留不留种子仍由评测决定。

| | |
| --- | --- |
| 可迁移 | 计划账本：实现失败之后意图还在。这一条已经在 `taic/plan_ledger.py`，默认开 |
| 不可迁移 | 论文里的优先分和置信不进本仓库的账本。相对 OpenEvolve 的倍数留在原文，不当作本仓库的目标 |
| 约束 | 账本默认开。它不构成一次新的付费搜索。已经在跑的搜索仍用启动时写在 `run_config.json` 里的开关 |

出处：论文 [arXiv:2602.19128](https://arxiv.org/abs/2602.19128)。代码（说明里列了 MLX 后端）：[caoshiyi/K-Search](https://github.com/caoshiyi/K-Search)。

## KDA²：两个人轮流，下一位只看见工作区

KDA² 是英伟达 Kernel Design Agents 在 2026 年 9 月公开的一轮：用这套代理去优化另一个也叫 KDA 的算子。一个人看见的循环是 Humanize 里的 `flame_chase`。Humanize 是一个驱动已经登录的编程代理的运行时。两个角色轮流上场。每一轮新开一次会话。交给下一位的是工作区里的文件。上一轮的对话不带走。对不对、快不快由这个循环外面的判卷决定。

`flame_chase` 只排轮次。写代码、跑命令、读终端是那场编程代理自己的循环。对不对、快不快仍由循环外面的判卷决定。

本仓库已经有对应的一轮：每次搜索恰好两个委员会，名字是 first 和 second，各一名成员；第 2 轮起有交接句，两名成员是同一个模型时也写；编排器根据评测决定留谁。细节和已经公开的倍数写在 [`KDA框架与本工程对比.md`](KDA框架与本工程对比.md)。这篇不把那一页再抄一遍。

### 我们做了什么，调用了什么，模型在哪一层

本工程不只有出题、限预算和判卷。它还准备上下文，并定义工具。`hmz` 和 `pi` 不是本仓库写的。模型不在每一层都出现。

| 层 | 谁的程序 | 这一层做什么 | 模型在不在 |
| --- | --- | --- | --- |
| 搜索 | 本工程 `taic` | 两个委员会轮流。准备上下文：契约、苹果 GPU 笔记、当前内核、成绩单、这一轮方案、交接句、计划账本。定义 `lookup_msl` 和 `quick_check`。管预算、换种子、确认和公布 | 规划时在。搜索程序直接调用模型接口 |
| 写内核，不用 `pi` | 本工程 `taic` | 同一条聊天。两个工具注册成函数。搜索程序执行它们，再从回复里抽出 Metal | 在。模型就在这次聊天里 |
| 写内核，`--kernel-agent pi` | 本工程只交任务。调用 `hmz`，`hmz` 再调用 `pi` | 上下文写成 `TASK.md` 和 `msl_reference.md`。工具写成技能 `taic-tools`：查资料是读笔记，自查是跑 `tcenv eval --quick`。`hmz` 提供代理会话、权限围栏、epic，并把技能放进这场的虚拟家目录。`pi` 用自己的 `read`、`write`、`bash` | 在 `pi` 里面。搜索程序不直接跟这个模型说话。模型由当前委员会指定，经 `pi/<provider>/<模型>` 交给 `pi` |
| 判卷 | 本工程 `tcenv` | 编译、ABI、内存安全、对答案、计时。一把显卡锁。噪声门和确认指纹 | 不在 |

`hmz` 是别人写的 harness，不进本仓库的源码。`--kernel-agent pi` 才调用它。省略或 `--kernel-agent off` 时，走上面第二行。这一行的请求从 2026-10-20 起按流接收，空闲、空回复和截断的收法写在 [架构说明.md](架构说明.md) 的 §2.4。

### 用了 hmz 的什么，不用什么

| | 用 | 不用 |
| --- | --- | --- |
| 命令 | `hmz exec`。流程是本仓库的 `taic/flows/kernel_once`：一个角色 `assistant`，写完一颗内核就停 | `flame_chase`。那是 hmz 自己排 `first_chaser` 和 `second_chaser` |
| 谁写内核 | 本机已经安装的 `pi`。模型写成 `pi/<委员会的 provider>/<模型>`。初稿和第 1 轮是 first，第 2 轮是 second。`kernel_once/skills/taic-tools/SKILL.md` 由 hmz 放进这场 `pi` 的家目录，说明 `lookup_msl` 是读 `msl_reference.md`，`quick_check` 是 `TASK.md` 里那条 `tcenv eval --quick` | hmz 带的其它代理：Claude、Codex、Kimi Code，以及直接调模型的 litellm。也不把这两个名字注册成 `pi` 的函数 |
| 这一场的上限 | `-p budget.cost` 用搜索还剩的美元封住这一场。`--json` 里解析到的花费记进搜索账本 | 把整次搜索的预算和停止交给 hmz |
| 看板 | 读这一场 `pi` 会话的末尾约 256KB，网页只留最近 40 行 | 用 `hmz web` 当搜索看板。逐条原文仍在 `~/.pi/agent/sessions` |
| 判卷 | 代理可以跑 `tcenv eval --quick` 自查。搜索读它留下的 `kernel.metal`，再做完整评测、换种子和确认 | 让 `pi` 或 `hmz` 决定留不留、公布不公布 |

两个角色的轮流已经在搜索里：first 与 second，每轮新开一段消息，从第 2 轮起有交接句。`kernel_once` 一场只有一个 `assistant`，是因为轮换不需要 hmz 再排一次。

### 技能怎么把工具教给代理

KDA 没有把剖析器注册成 `hmz` 里的函数工具。`flame_chase` 自己也不跑剖析。教模型的是一份技能文件，代理再用自己的终端去执行里面的命令。

本机 KDA 仓库里的 `skills/ncu-report-skill/SKILL.md` 就是这样。文件头只有名字和一句「什么时候用」。正文规定顺序：先测，再对症状，再写计划。下面是可以照抄的 `ncu` 命令、报告目录，以及 `helpers/` 里的脚本。Claude 启动时只读这份 `SKILL.md`；真正要剖析时，它按正文用终端去跑，不是调用一个叫 `profile` 的函数。

`hmz` 把技能交给 `pi` 的方式写在它的 `skills.py` 里。流程目录下的 `skills/*/SKILL.md` 会放进这次进程的虚拟家目录，不放进工作区。因为 `pi --mode rpc` 不信任工作区里的 `.pi/skills`，放在那里等于没装上。工作区里的 `.pi/mcp.json` 在这种启动方式下 `pi` 也不会加载。

本仓库照这条路做了 `taic/flows/kernel_once/skills/taic-tools/SKILL.md`。文件头点名 `lookup_msl` 和 `quick_check`。正文写明：前者是用 `read` 读工作区里的 `msl_reference.md`；后者是用 `bash` 跑 `TASK.md` 里那条带 `--quick` 的 `tcenv eval`。这条不计时，也不许去动显卡锁。`TASK.md` 再把这一场的具体命令写一遍。这两个名字没有注册成 `pi` 的函数。聊天那条路（不用 `--kernel-agent pi`）仍然把它们注册成函数工具。

不用它的全部，是因为全部里有两类东西。一类是这个搜索不缺的产品功能：网页、备份、ssh 或容器上的环境、别的编程代理、把一场对话接着聊下去。一类会拆掉现在的考场：由 hmz 排整次搜索，由代理自己计时并自己留下一版。KDA² 博客里那次 3.74 倍就是后一类：随机输入上看着很快，归一化被写成常数，真实输入失败。他们最后仍把验收放在循环外面。

和 `flame_chase` 比，写内核的那一场不弱：上场的仍是 `pi`，它有终端，能改文件、看报错、再改。两个角色的轮换也不弱：交接的是当前内核和成绩单，不只是目录里代理自己留下的文件。判卷比它多。`flame_chase` 不判卷。

不把「hmz 这个产品的每一个界面、每一种代理」都做进本仓库。那些不参加这次搜索。少了它们，搜索并不更弱。

### 和 flame_chase 比过的代码

2026-10-19 对过三处。装上的发布包是 PyPI 的 `hmz` 0.2.0，也是当时的最新发布。本机检出 `e2013a4`（2026-10-18）里的 `src/hmz/flows/builtin/flame_chase/__init__.py` 和这个发布包里的文件相同。当天 GitHub `main` 又多了 `737f438`，那个提交不改这个文件。

这份流程到 `while True` 为止：取出下一位，`spawn` 一场新会话，把开任务时的那一句交给它，在同一个工作区里 `run`，然后换人。预算花完或这一场失败就停。`--resume` 记住下一位。文件里没有抽内核，没有评测，没有换种子。

排班这一层因此不比我们的搜索循环强。我们多出来的是成绩单交接、修补留在原对话、噪声门和确认。它强在任意流程外面的运行时。写内核时下面三样已经在用，不是以后再接。

| 运行时 | 是什么 | 现在 |
| --- | --- | --- |
| 代理会话 | `pi` 的一场对话。它说的话、调用的工具、工具结果写在 `~/.pi/agent/sessions` 里 | 用。看板「pi 输出」读的就是这一场的末尾 |
| 权限围栏 | `hmz` 启动 `pi` 时套上的 `hmz internal fence`。它限制这场能读哪些路径、能写哪些路径、能连哪些主机 | 用。每次 `hmz exec` 已经套上，不是待做的功能 |
| epic | 一场 `hmz` 运行的目录，在 `~/.hmz/epics/<工作区>/<时间>-<编号>/`。`epic.jsonl` 一行一件事：开始、打开了哪个会话、花费、结束。它记下这场的形状，不另抄一份 `pi` 说过的话 | 由 `hmz` 自己写。搜索看板不拿它当成绩单 |

已定的教训是：交接的质量决定下限。历史要写成有结构的短记录，这一条已经落到默认打开的 `plan_ledger`。Humanize 的源码留在它自己的仓库里。模型自己测、自己写笔记、自己决定留不留，不照抄。理由在下一节。

| | |
| --- | --- |
| 可迁移 | 两个委员会轮流，下一位不读上一轮对话。试过什么写成短记录。写内核的那一场用 `pi` 的终端 |
| 不可迁移 | 把 Humanize 源码搬进本仓库；用 `flame_chase` 排整次搜索；英伟达那套判卷工具；让模型自己跑计时并自己留下一版 |
| 约束 | 判卷仍由编排器做。两个委员会、交接句、一次预算，维持现在的分法 |

出处：博客 [KDA²，2026-09-27](https://nvlabs.github.io/kda/blog/2026-09-27-kda-for-kda/)。内核分支 [NVlabs/kda 的 260927-kda-for-kda](https://github.com/NVlabs/kda/tree/260927-kda-for-kda)。`flame_chase` 在本机 Humanize 仓库的 `src/hmz/flows/builtin/flame_chase/__init__.py`（`main`，`e2013a4`）。教程 [Beat a benchmark](https://github.com/humanfia/humanize/blob/main/docs/user/tutorials/take-home.md)。本仓库对照：[KDA框架与本工程对比.md](KDA框架与本工程对比.md)。

## 从 KDA 的笔记学了什么

2026-10-19 起，新的搜索默认打开 `plan_ledger`。下一轮规划看到每条尝试的测法结果。留不留种子仍由编排器按评测报告决定。`--no-plan-ledger` 改回原来的 24 条文本。已经启动的搜索不改。

学了两处，没有合成第三套循环。

| 学自 | 他们怎么做 | 我们取了哪一层 |
| --- | --- | --- |
| KDA² 的 `flame_chase`，以及 Humanize 教程里的任务书 | 每一轮新开会话。先测，改一处，再测。变快且测试仍通过才提交。试过什么和测到的数写进 `NOTES.md`。下一轮只读仓库 | 下一位不靠上一轮对话。试过什么必须留下短记录，下一轮规划读得到 |
| K-Search 的计划树 | 高层意图和这一次写成的程序分开。编译失败不把这条意图删掉 | 编译失败、ABI 不对、没写出核，记为「还没有被计时否定」，可以按提示再试。写对了但没有变快，才记为这条方向已否定 |

四类结局由 `taic/plan_ledger.py` 从评测报告和历史行算出，不由模型填写：变快、噪声内并列、写对了但没变快、尚未被计时否定。节点没有优先分，也没有置信。

和他们的差别，以及不照抄的理由：

| 他们的做法 | 我们不照抄 | 理由 |
| --- | --- | --- |
| 模型自己跑测试，自己读终端 | 编译、对答案、计时由评测进程做。同一条分支的下一次修补收到截到约 6000 字的成绩单 | 这台机器同一时刻只有一个评测。模型自己挑一次碰巧很快的数，会绕过噪声门槛。成绩单由程序写，行号和误差不会被模型改写 |
| 模型把笔记写进 `NOTES.md` | 笔记是编排器写下的历史行和计划结局。看板详情里的「计划结局」表就是它 | 模型可以在笔记里把失败写成成功。记录必须和 `report.json` 对得上 |
| 任务书让模型自己决定这一版留不留 | `taic/policy.py` 决定替换、并列和耐心。续跑回放同一组函数。对外加速比还要确认测量绑上源码指纹，并且计时安静 | KDA² 博客写过：随机输入上 3.74 倍，是把归一化写成常数；拿掉之后是 2.48 倍，真实输入失败。他们最后仍把验收放在循环外面。把留不留交给模型，会拆掉现在能复现的替换规则 |
| 代理用自己的命令行跑 IKET、TIRx 或 Nsight | 不接入这些工具。`profile_poor` 仍关着 | 那些计数器在这块苹果芯片上没有。打开 Instruments 是一次对照，不是这次改动 |

同一条分支上，编译错误、ABI 违例和对答案失败会进下一次修补，这是我们比 `flame_chase` 多做的：他们的运行时不把成绩单格式化成下一条消息，靠代理自己去读终端。下一轮规划看不到旁边失败分支的全文，只看到上面的四类短记录。

看板上，候选表和 `candidates/<序号>_<标签>/feedback.txt` 是每一次评测。`run_config.json` 里 `plan_ledger` 为真的运行，详情才有「计划结局」。这次改动之前启动的搜索没有这个开关，那一表是空的。

这次改动不批准一次新的付费搜索，也不填写实验批准单。

## AlphaEvolve：档案里留着好程序，再让模型改一版

AlphaEvolve 是 Google DeepMind 的进化式编程代理。它要解决的问题更宽：凡是能自动打分的程序，都可以一轮轮改好。一个人看见的循环是：

1. 你给一份初始程序，并标出允许改的区域，再给一个自动评分函数。
2. 程序库里存着以前的版本和分数。抽样器抽出若干份，拼进提示。
3. 模型交出修改（一段查找替换）。套上去得到新程序。
4. 评分函数打分。有希望的版本登记回程序库，成为以后的父母。

DeepMind 公开了论文、公告，以及一份数学结果笔记本。结果仓库的说明写明：里面没有用来运行 AlphaEvolve 的代码。能克隆来跑的公开再实现是 OpenEvolve。

已定判断：档案加变异这个框可以搬。在一台串行显卡和美元预算上，它必须是有界的一版，并且是事先登记的、同一预算的对照，对象是现在的单一种子爬山。

| | |
| --- | --- |
| 可迁移 | 档案加变异。代码里的档案最多 4 个签名，而且只在停滞之后换最后一条分支的亲本 |
| 不可迁移 | 已定判断没有把 DeepMind 的全套流程或 OpenEvolve 整仓接进来 |
| 约束 | 代码里的上界是 4 个签名，不是早先记下的 8。论文里没有这个数字。对照必须事先登记、预算相同、对着单一种子爬山。这篇不填写 [`实验批准单-搜索开关.md`](实验批准单-搜索开关.md) |

出处：论文 [arXiv:2506.13131](https://arxiv.org/abs/2506.13131)，正文页 [2506.13131v1](https://arxiv.org/html/2506.13131v1)。公告：[DeepMind 博客](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)。结果仓库的 README 写明不含运行 AlphaEvolve 的代码：[google-deepmind/alphaevolve_results](https://github.com/google-deepmind/alphaevolve_results)。公开再实现：[algorithmicsuperintelligence/openevolve](https://github.com/algorithmicsuperintelligence/openevolve)。

## 剖析放在哪：他们怎么教，本仓库怎么做

上面各节写的是搜索怎么转。这一节只写「性能分析」这一件事：谁去测量，模型怎样被教会去读。

他们都不把剖析器做成模型自己发现、自己调用的协议。测量在循环外面做完，再把结果交回下一次提示，或写成一份给编程代理看的技能。

| 系统 | 谁跑剖析 | 模型怎样读到 |
| --- | --- | --- |
| KernelBench | 考场编译、对答案、计时，并可以做性能分析 | 下一轮提示贴上上一次的核、执行结果和分析。论文表 1 把这一格记作 G+E+P |
| GEAK / KernelFoundry | 评测角色或评测队列打分 | 分数和错误写回生成者或进化档案，不由模型临时决定去 profile |
| K-Search | 低层实现跑完留下轨迹 | 轨迹更新计划树。失败的实现不把「还想试什么」删掉 |
| KDA² | `flame_chase` 不跑剖析。CuTe 用 IKET，TIRx 用 CPU 上的数值仿真和静态检查；采集脚本在 TIRx harness 里 | 一份 `SKILL.md` 告诉代理先测量、再对症状、再改，并用终端执行里面的命令。`hmz` 把流程目录下的技能放进 `pi` 的虚拟家目录。判卷仍在循环外。本仓库的 `taic-tools` 按同一条路教 `lookup_msl` 和 `quick_check`，见上面「技能怎么把工具教给代理」 |
| AlphaEvolve / OpenEvolve | 登记好的评分函数打分 | 分数回到程序库，成为下一轮的父母。模型交出的是程序修改，不是「请再 profile 一次」 |

本仓库把「教模型读」和「谁去测」分开。`taic/tools.py` 里没有剖析。那里只有 `lookup_msl`（查一节 MSL）和 `quick_check`（编译和正确性，不返回耗时）。

| 本仓库的一件事 | 放在 | 默认 |
| --- | --- | --- |
| 每次评测写出耗时上界、占用 | `tcenv/profile.py`，进评测报告 | 开 |
| 这些字段是什么意思 | `taic/skills/metal_profiling.md`，在系统提示里 | 开 |
| 规划时只附上访存或计算那一节 | `taic/symptom.py`，看报告里的 `roofline.bound` | 开 |
| 种子慢于库基线时用 Instruments 抓痕迹，文字贴进下一轮 | 编排器调用 `tcenv/xctrace.py`；说明在 `taic/skills/profiler_evidence.md` | 关（`profile_poor`） |

模型不能自己决定去抓 Instruments。编排器在完整评测之后把数字放进反馈；可选的那次抓取也要先拿到和评测同一把显卡锁。

### 这一块还有没有改善空间

有，而且不在「把剖析搬进工具模块」或「让模型自己跑 Instruments」。

评测反馈在截到约 6000 字之前，STATUS 后面就是数字头：上界类别、离下界几倍或「基线已经快过这个界」、对应利用率、计时波动、线程组内存。基线已经快过下界时，同一行写明这不是改算法的理由，含 ieee 在内的每个用例仍要跟参考对上。截断砍的是后面的正确性散文，这几行留得住。基线已经快过下界时不写离界倍数，避免把「已经到峰值的 94%」说成目标。

`profile_poor` 仍关着。打开它是一次对照，不是这篇的改动，也不填写 [`实验批准单-搜索开关.md`](实验批准单-搜索开关.md)。Metal 不把 Nsight Compute 那类计数器交给程序，所以不把 KDA 的 Nsight 技能接进来。
