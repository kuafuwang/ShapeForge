# 论文价值评估：面向 ai_lowerling

本评估覆盖 56 篇论文。12 个 DeepSeek 子代理按主题读取本地全文（abstract、方法、实验、结论/局限），再由主代理按本仓库需求统一校准。没有运行论文代码、GPU/NPU 或模型实验；数字均为原论文口径。

> **仓库快照说明**：下文“当前”“现有”“我们”及 `tcenv/task.py`、`tasks/*/task.py` 等对照，记录的是本次评估时的仓库状态（含已退役的 v1/Triton→MSL 路线），不是现行实现说明；当前任务与后端边界以 `AGENTS.md` 和当前代码为准。

## 评级口径

- **S**：优先精读，能直接改变当前 `taic`/`tcenv`/可信 harness 的设计或离线验收。
- **A**：高价值，提供可迁移机制、NPU/DSL 参考或关键反例，但需要裁剪后才能落地。
- **B**：选择性参考，主要提供背景、特定技巧或评测反例。
- **C**：与当前工程直接关系较弱，保留作完整资料。
- 评级不是论文质量分，也不是模型初评的简单平均；代码可用性、证据口径和对 Metal/NPU 的可迁移性都会影响最终层级。

### 2604.25850 Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses

- 本地 PDF：`docs/可信harness/papers/2604.25850_agentic-harness-engineering.pdf`
- 讲了什么：把 coding agent 的 harness 变成可学习对象。七个组件拆成固定挂载点的文件（系统提示、工具描述与实现、middleware、skill、子代理、长期记忆），轨迹蒸馏成分层可钻取的证据库；每次编辑在 manifest 里写下"预计修好哪些任务、哪些任务有回归风险"，下一轮用任务级 delta 核对并按文件回滚。适用于有稳定 benchmark、可重复 rollout 的长程任务；代价是每轮 k 次 rollout 再加一个 evolve agent。
- 关键证据：Terminal-Bench 2 全 89 题、10 轮，pass@1 69.7%→77.0%（人工 Codex 71.9%、ACE 68.9%、TF-GRPO 72.3%）；冻结 harness 迁到 SWE-bench-verified 500 题，75.6% vs seed 75.2%，token 461k vs 526k（−12%）；跨五个底座 +2.3~+10.1pp。组件消融：memory/tool/middleware 单加 75.3/73.0/71.9，system_prompt-only 67.4（比 seed 低 2.3pp）；单加之和 +11.1pp、整体只 +7.3pp，非加性。自归因：fix precision/recall 33.7/51.4（随机 6.5/10.6），regression precision/recall 11.8/11.1（随机 5.6/5.4）。
- 局限与不可直接外推：(1) 只在 TB2 上驱动演化，SWE 只是迁移，别的语言、仓库规模、human-in-loop 未测；(2) 步预算与超时按 GPT-5.4 high 调，跨 reasoning tier 非单调（med +2.3、high +7.3、xhigh +2.3）；(3) 回归预见基本失效，作者自称受控原型而非完整护栏栈；(4) 单次 campaign 约 32 小时、每题 k≥2 次 rollout，我们付不起同规模搜索。
- 对本仓库的具体价值：decision observability 正是 plan-02 缺的另一半——我们有 action/evidence/rationale，却没有"预计修好哪些 task、哪些 task 有回归风险"字段，也没有下一轮核对后按文件回滚，这两项可直接进结构化提案 schema。它的 controllability 三条（只写 harness workspace、runs/tracer/verifier/LLM 配置只读、seed prompt 不可删）与我们的 never-auto、P1 不碰评测门同构，可当 plan-03/plan-06 依据。非加性结果警告：多条 tip 塞进同一份 12KB TASK 会互相抵消，不能把单条增益相加预测 overlay 效果。11.8% 的回归召回说明"单来源 tip + 人审"看不见副作用，at-risk 应写成必填项。
- 初步价值：高，5 分。与本仓库 plan-02/plan-03 最贴，并给出我们缺失字段的具体形状与失败率。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。直接讨论编辑可归因、写入权限边界与自归因盲区，属评测有效性与权限治理。

### 2609.14857 ModularRSI: Modular and Generalizable Recursive Harness Self-Improvement

- 本地 PDF：`docs/可信harness/papers/2609.14857_modularrsi.pdf`
- 讲了什么：把 harness RSI 表述成"机制级 + 行为级"两层信用分配。harness 拆成 Agent Loop、Tool Use、Observation Management、Context Management、Task Completion Detection 五个模块，每条 lineage 只在目标模块内改代码；同一任务内对比成功/失败轨迹、跨任务投票选出反复出现的缺陷；改动必须过三道门（静态程序检查、diff 审查、抽两个任务执行验证），失败按 diff 回滚，最后做一次跨模块整合。为避开在评测集上演化，另建 2,000 条与下游 benchmark 不相交的可执行任务。
- 关键证据：DeepSeek-V4-Flash-Preview 上 TB 2.0 准确率 47.57→52.43，SWE-Bench-Verified 73.40→76.40；跨域迁移 TB→SWE 75.80、SWE→TB 49.44；Pass₃ 30.34→35.96。跨模型 GLM-5.2 59.55→61.80、MiniMax-2.5 41.57→44.94。消融：去 CTA 50.56、去 FLM 49.81、去 VG 48.31。同预算下 joint all-module 44.19、非模块化 46.44，都低于 47.57 基线；与 AHE 49.81、Meta-Harness 49.44 对比时用同一 seed、同一演化数据与预算。
- 局限与不可直接外推：(1) 2,000 条里各取 120 条演化、每模块 3 epoch，"预算匹配"是设定而非等价；(2) execution validation 只抽两个任务，远弱于它声称的可执行验证；(3) 主实验只有单一 backbone 与 Terminus-2 一个 seed harness；(4) 全文无 limitations 章节，五模块划分来自作者对 Terminus-2 的一次人工归纳。
- 对本仓库的具体价值：模块受限演化 ≈ 我们的 scope(target/task/dtype)，但它多一层"机制归属"：建议须先声明落在哪个 surface/component 才允许改，这补上 plan-06"按接收者/可执行性分流"缺的机制维度。三道门可对位：程序检查≈我们的代码测试，diff 审查≈plan-06 的可执行性判断，执行验证≈plan-01 的计后 fresh-input 复验（我们覆盖面更强，不必借它的弱门）。"no-op 提交不得得分"与我们"文件与 seed 完全相同则不计"同构。最要紧的是负面结果：扩大改动面（joint/非模块化）会低于不演化基线，为"收窄可直接做、扩大须具名批准"提供量化依据。
- 初步价值：高，4 分。把归因粒度与验证门做成可施工结构，负面结果直接支持现有收窄纪律。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。核心是信用分配、验证门与 benchmark-disjoint 协议，属评测有效性与 harness 自改进；验证门太浅，只借结构不借强度。

### 2610.14224 Harness²: Recursive Agent Harnessing for an Open World

- 本地 PDF：`docs/可信harness/papers/2610.14224_harness-squared-recursive.pdf`
- 讲了什么：面向"没有真值 verifier、任务持续到达"的开放世界做两层递归。任务级递归用 Propose–Probe–Compose：先跑参考执行，再提 invariant 与 domain-specific 两个候选 harness，在同一模型同一环境各跑一次，用行为对比（而非分数）决定合并、改写或保留，k 控制并行/串行宽度。harnessing 级递归把被采纳的 harness 和"为什么有效"写成 EXPERIENCE.md 入库，供后续任务复用。适用于专业交付类任务，不适用于有确定性验收器的场景。
- 关键证据：WorkBuddy-Bench / JobBench / LAB 三基准，Gemini 3.5 Flash 与 GLM-5、OpenCode 与 Codex 四配置。单步最大 +11.5（WB 64.2→75.7）、+4.5（JobBench）、+11.8pp（LAB Partial）；并行 k=5 再加最多 +3.9（WB）、+4.2（JB）、+6.7pp（LAB）。消融：去 library −3.1/−1.8、去 scoping −2.9/−3.7、去 composition −1.6/−1.9。关键负面结果：不给参考执行与候选探针、直接改 harness，WB-code 73.4→63.2、WB-web 69.9→65.0；k=1 的 library 只能拉回基线，k=5 才带来 +0.9/+4.4/+5.1。
- 局限与不可直接外推：(1) 三个基准都是办公/法务类交付，评分靠 agentic selector 或 rubric，不是可执行验收器；(2) probe 用行为对比替代真值，作者承认受执行随机性与共享模型偏见影响，不保证迁移；(3) 成本随 k 线性上涨；(4) 同模型既当 executor 又当 editor 也能涨（LAB +13.7），但这只说明不需要更强 editor，不构成独立验证。
- 对本仓库的具体价值：两层递归与我们"P1 执行面 overlay / P2 与 experience 改进面"同构，差别是它的 improvement harness（提案生成规则）可被经验更新，而我们冻结；记下即可，不构成现在改 P1 的理由。"没有 execution contrast 的经验不入库"可落到 plan-07：reported/retired 过滤之外再加一条证据门槛，避免把自评写成经验。"直接编辑不给执行就退化"是"自证循环"担忧的量化版，可作 plan-02 拒绝无对照提案的外部依据。但它的 probe 只做一次执行对比，强度低于 fresh-input 复验，不能拿 +11.5 证明 overlay 有效。
- 初步价值：中，3 分。机制对得上，但它的核心难题（无真值）恰是 tcenv 已经解决的那一半。
- 最终层级：B（主代理校准）
- 可信 harness 候选：yes（偏弱）。直接做 harness RSI 与经验生命周期，但验证信号本身不可靠，只能借分层与入库门槛，不能借效果数字。

### 2603.28052 Meta-Harness: End-to-End Optimization of Model Harnesses

- 本地 PDF：`docs/paper/2603.28052_meta-harness-end-to-end-optimization-of-model-harnesses.pdf`
- 讲了什么：把 harness 代码搜索外包给一个 coding agent proposer：每次评估的源码、分数、执行轨迹全部落盘，proposer 用 grep/cat 自行决定看什么，而不是接收压缩摘要或标量奖励；外层循环只有"提议—评估—记录"，不设父代选择规则和固定搜索骨架。适用于"单个可执行程序即 harness、评估可重复"的任务；代价是单次评估可产生上千万 token 诊断材料，主张是经验不该被压成摘要。
- 关键证据：在线文本分类（GPT-OSS-120B，3 数据集）48.6% vs ACE 40.9%（+7.7pp），上下文 11.4K vs 50.8K token；只需 4 次评估就追上对手 60 次提议的最终准确率，最终准确率高 10 点以上。接口消融最关键：scores-only 中位 34.6/最好 41.3，scores+summary 34.9/38.7，全量轨迹 50.0/56.7。检索增强数学：200 道 IMO 级题，五个 held-out 模型平均 +4.7pp（38.8 vs 无检索 34.1）。TerminalBench-2：Opus 4.6 76.4%（Terminus-KIRA 74.7%），Haiku 4.5 37.6%（Goose 35.5%）。proposer 每次迭代中位读 82 个文件。
- 局限与不可直接外推：(1) TerminalBench-2 上搜索与最终评测是同一批 89 题，只靠人工检查与正则查泄漏，没有 held-out，76.4% 不能当泛化证据；(2) 依赖很强的 proposer（Claude Code + Opus-4.6），换 proposer 的效果作者明说未研究；(3) 成本量级（约 60 个 harness、单次评估 10M token）与我们单 run 预算差两三个数量级；(4) 文本分类与数学是 harness 代码搜索，不涉及内核正确性与计时语义，不能外推到 tcenv 验收门。
- 对本仓库的具体价值：接口消融直接戳到设计：scores+summary 相比 scores-only 没有提升甚至更差（38.7<41.3），原始轨迹才是有效信号。我们 TASK 只有 12KB，tip/experience 渲染本质是 summary 通道，按它的证据很可能在丢诊断信息。折中是"指针 + 按需钻取"：TASK 只放结论与稳定路径（runs/<id>/ 失败报告、triage_summary.md），让模型自己 grep；属渲染层改动，先当假设，不进 plan-06 必做项。它的同集搜索/评测则是必须避免的反面样板：我们的 confirmation gate 换种子、禁缓存、三批与 plan-01 fresh-input 正是它缺的门。
- 初步价值：中，3 分。接口结论可操作，但成本与评测协议都不适配当前仓库。
- 最终层级：B（主代理校准）
- 可信 harness 候选：yes（警示型）。它做 harness 自改进并暴露"同集搜索即评测"的评测有效性缺陷，正好当 confirmation gate 的反例；机制本身不涉及权限与执行安全。

### 2505.22954 Darwin Gödel Machine: Open-Ended Evolution of Self-Improving Agents

- 本地 PDF：`docs/可信harness/papers/2505.22954_darwin-godel-machine.pdf`
- 讲了什么：用"经验验证"替代 Gödel machine 的"形式证明"：coding agent 读自己的评测日志，提议并实现对自己代码库的修改，新版本在 coding benchmark 上评测后进档案；父代按分数正比、按已有子代数反比采样，保留所有仍能编辑代码的版本，形成开放式改进树。被改的是 agent 自身代码，而"档案维护与父代选择"这套探索机制本身固定不可改。适用于能自动评分的 coding 任务。
- 关键证据：80 轮，SWE-bench（Verified 子集，分阶段 10/60/200 题）20.0%→50.0%，Polyglot 50 题子集 14.0→38.0、全量 14.2→30.7。消融：去掉自我改进（固定 meta agent，ADAS 式）与去掉开放式档案都更差。仍低于闭源 SoTA；单次 run 约两周并产生显著 API 成本。安全侧：执行与自改全在隔离沙箱、严格时限内，人工监督，档案保留可追溯 lineage；作者称未观察到有害行为，但明说这依赖当前前沿模型的上限。
- 局限与不可直接外推：(1) 核心假设"coding 分数上升即自我改进能力上升"未验证，其后续 HGM 工作指出二者会错配；(2) 单次两周与大量 API 成本，我们无法复现，50.0% 不能当基线；(3) 改进对象是整个代码库，允许改工具、上下文管理与 peer-review，改动面远大于我们的 P2；(4) 沙箱与人工监督是做自改的前提，不是顺带结论。
- 对本仓库的具体价值：可借的是治理结构而非算法：沙箱、时限、可追溯 lineage、人类监督四项，与 plan-03/plan-06 的 never-auto、P1 隔离同向。"子代必须保留编辑代码库的能力否则丢弃"对应我们的硬约束——harness 改动不得破坏验收链与工具链。"benchmark 分数 ≠ 自改进潜力"支持把 search best 与 confirmation speedup 分开报。档案可用于被否决提案的可检索历史，但不自动复燃。
- 初步价值：低，2 分。机制映射只剩治理与档案，成本与改动面都超出本仓库范围。
- 最终层级：B（主代理校准）
- 可信 harness 候选：yes。第 5 节就是自改系统的安全与可追溯性讨论，与 P0/P1/P2 的闭环程度限制直接相关；只作原则引用。

### 2610.08900 Humanize: Judgement Engineering for Agentic Coding

- 本地 PDF：`docs/可信harness/papers/2610.08900_humanize-judgement-engineering.pdf`
- 讲了什么：把"完成判定"从写码 agent 手里拿走。人批准 plan contract（目标、验收标准、TDD 正负测试、路径边界）；builder（Claude Code）按轮实现，提交带证据的 claim 与未决项；另一厂商的 reviewer（Codex）在全新进程里只读整仓、plan 与前几轮，判定 COMPLETE 或给 findings；确定性 hook（不是模型）在角色间路由并执行 72 条机械门。作者把这条链看成两模型联合采样，缺陷存活率写作 b·mR·mO（builder 漏、reviewer 漏、外部 oracle 漏）。范围是仓库级编码会话的流程治理。
- 关键证据：
  - 部署：108 天 68 版、1,468 stars；150 issues/52 作者，其中 118 份真实 loop 的 postmortem（113 份由其 methodology analysis 生成）；双 LLM 编码一致性 κ=0.93（轮数）/0.79（主压力）。
  - 失败面：45/118 份记录 builder 夸大完成；93 份报轮数者中位 10 轮、最长 87 轮（实现上限 42）；27 份分阶段样本中 364/541（67.3%）轮落在实现已被接受之后的 code review 阶段。
  - 学习面：771 条编号建议无一条被强关联到主分支改动；86/150 issues 在最后一版之后才到。
  - kernel 应用（team-reported）：KDA 在 MLSys 2026 FlashInfer Full-Agent 三赛道进前三（MoE 1、DSA 2、GDN 3），DSA indexer 19.08×，5 个核里 2 个慢于基线；48h 消融：只 loop 3.71× → +KernelWiki 6.14× → +ncu profiling 8.58×（K-Search 1.37×）。
  - 反面引用：Xiang et al. 2026 的受控研究里，Codex 评审 Claude 草稿在 reviewer 不能跑测试时是负收益。
- 局限与不可直接外推：
  1. 纯观察性证据；作者明确说没有"同 builder 有无 reviewer"的受控对照，应用数字多为 team-reported。
  2. 门只查 artifact 存在与形式、不查内容，且 state 文件损坏时 validator fail open —— 正是 plan-06 的注入面。
  3. code review 无轮数上限，终止规则粗；reviewer 假阳性直接变成额外轮次成本。
  4. 依赖 Claude Code hook 与 Codex CLI，上游版本变动曾打断插件；社区 runtime 不都保留独立性保护。
- 对本仓库的具体价值：机制词汇几乎逐条对上现有 plan。
  - "deterministic hooks, not a model, route work" 就是 recipient 路由；且它把路由与判定分层：hook 判形式、reviewer 判内容，对应 plan-03/06"按接收者与可执行性分流”。
  - 每次 review 起新进程、reviewer 看不到 builder 推理 → fresh-context 复验的反 anchor 依据（plan-05）。
  - 45/118 夸大完成与 771 建议零落地，是"agent 自报成功"与"自生成反馈≠学习"两个样本，支撑 plan-07 只做过滤与人工去重。
  - b·mR·mO 给出判据：tcenv 的确定性检查对某条 claim 完整时（mO→0），再叠同族 reviewer 主要买假阳性；第二委员会应留给检查覆盖不到的 claim（语义等价、是否偷换 task 契约）。
- 初步价值：高 5/5 —— 与本仓库信任层几乎一对一，且附一份罕见的公开 postmortem 语料。

### 2510.26692 Kimi Linear: An Expressive, Efficient Attention Architecture

- 本地 PDF：`docs/paper/2510.26692_kimi-linear-an-expressive-efficient-attention-architecture.pdf`
- 讲了什么：Kimi Delta Attention（KDA，与本仓库文档里的 KDA=Kernel Design Agents 同名但无关）在 Gated DeltaNet 上加通道级细粒度门控，用 DPLR 特例 + UT 变换做 chunkwise 并行（块内并行、块间递推），并给出 U 型分解：prefill 走 FLOP 密集的 chunk 核、decode 走 recurrent 核。模型层按 3:1 交错 KDA 与 MLA。文中给出显式代价式 FLOPs_KDA = 6Td² + 3TCd + TC² 与 full attention 的 2T²d，并把块大小 C 当可调参数。适用：长上下文、解码密集的推理侧算子。
- 关键证据：与 MLA 同配方 1.4T token 训练下，RULER@128k 84.3（MLA 81.3、GDN-H 80.5），长上下文均值 54.5（52.2 / 51.2），MMLU-Pro 51.0 vs 47.2；KV cache 最多降 75%；1M 上下文 TPOT 1.84ms vs 11.48ms（6.3×，batch=1）；同为线性注意力，KDA 核执行时间约为通用 DPLR 的 1/2（图 2，作者记作算子效率 +100%），原因是把二级 chunk 矩阵乘从 4 次降到 2 次以保住 half 精度 matmul。
- 局限与不可直接外推：(1) 全部数字来自自家 Hopper 级 GPU 与 vLLM，Apple GPU 的带宽/矩阵单元比例不同，6.3× 不可外推；(2) 收益集中在 ≥128k 与 decode，本仓库任务（conv2d、gemm、scan、attention 短形状）多数吃不到；(3) "同配方公平比较"仍是单实验室自报，无种子、方差与重复次数，架构级消融（3:1 交错）不能当核级结论；(4) 训练侧配方与 checkpoint 规模都无法在本机复现。
- 对本仓库的具体价值：三条可落地。(a) 把块大小写成显式代价式再测，可做 taic 候选的解析先验、也是 plan-02 可证伪预测的样板：先算 6Td²+3TCd+TC² 的拐点再选 C，实测对不上就说明模型漏项。(b) 精度换吞吐的具体取舍：log 域写法会失去 half 精度 matmul，应像 tasks/mamba2_chunk_scan 那样让衰减项留在 fp32、把乘加压回输入 dtype，正好对应 `policy.py` 的 acc_bucket 与 tcenv 的 dtype 策略。(c) "同一算子两套实现按形状选"匹配 tcenv 按 size 计时，搜索应允许保留形状特化变体而不是只留一颗。
- 初步价值：中，3 分。是五篇里唯一给出核级可核算代价模型与精度取舍的，但场景落在 GPU 长上下文。
- 最终层级：B（主代理校准）
- 可信 harness 候选：no。属于算子与架构效率工作，不碰可信执行、评测有效性、权限或经验生命周期；它的"公平比较"缺种子与方差，也不能当我们的评测规范。

### 2512.24880 mHC: Manifold-Constrained Hyper-Connections

- 本地 PDF：`docs/paper/2512.24880_mhc-manifold-constrained-hyper-connections.pdf`
- 讲了什么：Hyper-Connections 把残差流加宽成 n 路并多样化连接，性能涨但破坏恒等映射，导致训练不稳、扩展受限，且访存开销近似随 n 增长。mHC 把残差映射投影到双随机矩阵流形（Sinkhorn-Knopp，20 次迭代近似），使前向信号增益与反向梯度增益有界；配套 TileLang 手写融合核（RMSNorm 后移到 matmul 之后、两条 scan 合一、残差合并融合）、选择性重算（最优块长 L*_r ≈ √(nL/(n+2))）与 DualPipe 通信重叠。适用：大规模预训练架构与训练系统。
- 关键证据：n=4 时训练额外时间开销 6.7%；27B 上最终 loss 比 baseline 低 0.021，BBH 51.0 vs baseline 43.8 / HC 48.9，DROP 53.9 vs 47.0 / 51.6。稳定性：HC 的复合映射最大增益近 3000，mHC 约 1.6，降三个数量级。访存：残差合并融合后每 token 读从 (3n+1)C 降到 (n+1)C、写从 3nC 降到 nC。算力扩展曲线覆盖 3B/9B/27B，优势仅轻微衰减。
- 局限与不可直接外推：(1) 主体是训练侧（反向重算、DualPipe、checkpointing），本仓库只做前向推理核，重算与通信结论不可搬；(2) 全部在 DeepSeek 内部集群与 TileLang 上测得，6.7% 和 loss 0.021 都不是可比的性能单位；(3) Sinkhorn 只迭代 20 次，实测增益偏离理论值 1.0（约 1.6），作者自承是近似；(4) 没有种子与方差，收益口径是"同算力下 loss 更低"，属于架构选择而非内核质量。
- 对本仓库的具体价值：借两条可核查的写核纪律，不借架构。(a) 先算每 token 读/写元素数再谈 FLOPs：这跟 tcenv 的 roofline `bound=memory`、`hwfeatures` 的 vector_load/register_prefetch/tg_staging 是同一套语言，可写成核评审清单项（融合后全局读写次数必须显式计数）。(b) 混合精度分层（系数 tf32、激活 bf16、末端 fp32）对应 acc_bucket 与 dtypes 策略，说明哪些量必须留高精度要有理由，而不是整体升 fp32 图省事。(c) "数学等价的重排换掉一次带宽"（RMSNorm 后移）是 MSL 里可照做的动作，应进搜索的变体族。
- 初步价值：中，3 分。工程纪律（I/O 记账、融合、精度分层）可直接用，论文主体是训练架构。
- 最终层级：B（主代理校准）
- 可信 harness 候选：no。无可信执行、评测有效性、权限或经验机制；I/O 记账是性能分析，不是评测有效性。

### 2605.04956 KernelBenchX: A Comprehensive Benchmark for Evaluating LLM-Generated GPU Kernels

- 本地 PDF：`docs/可信harness/papers/2605.04956_kernelbenchx.pdf`

- 讲了什么：建在 TritonBench-T 之上扩到 176 任务 15 类，核心是两段式正确性协议：call accuracy（能否导入、编译、调用并满足约束，量化题另加静态检查禁止高层量化 API）+ execution accuracy（须在 N(0,1) 与 outlier 模式——0.1% 概率、放大 50 倍——两种输入下都对）；量化题要求余弦 0.90–0.95、L1 相对误差 ≤0.05–0.10、RMSE ≤0.10–0.15 同时满足。计时用 `do_bench`（25 预热/100 次取中位），基线每机重测 eager，并加 IOU/MFU 归一化效率；落点是机制解释而非排行榜。

- 关键证据：176 任务 × 5 方法 × 6 卡。GEAK 编译 68.8%、语义正确 30.7%；KernelAgent 64.2%/10.8%（转换率 16.8%）。46.6% 的正确 kernel 仍慢于 eager，中位加速比 1.0008×；跨卡 max/min 加速比中位 2.15×、最坏 21.4×，慢于 eager 的比例从 A100 的 18% 到 L20 的 76%。GEAK 三轮编译 52.3→68.8%、正确 18.2→30.7%，但加速比 1.58→1.44×；"救回"的 kernel 只有 1.16×，本就正确的 1.58×；352 个相邻 diff 以"实质未变"与掩码修正为主，性能重写极少。量化 30 组合 0 正确，而编译率最高 83.3%。类别解释语义正确方差 9.4%，方法仅 3.3%。

- 局限与不可直接外推：（1）只有 Triton + 六张 NVIDIA 卡，未涉 Metal，绝对值不可搬；（2）IOU/MFU 分子是按理想实现估的 FLOPs/bytes，作者自标为"归一化代理"；（3）各方法带自己的 adapter 与轮次，非等预算比较；（4）单次运行、无置信区间，21.4× 可能被个别任务主导。

- 对本仓库的具体价值："正确 ≠ 快"（46.6%）是"慢不改变 ok、判快要另过噪声门槛"的经验依据；每机重测基线对应 `targets/<id>/` 的 per-target 基线，而非复用别处加速比；编译通过但语义错的缺口印证 compile/abi 与数值关必须分开判；outlier 模式与量化三指标可扩成差分与域扫描的具体输入；"迭代只修不优"（1.16× vs 1.58×）直接质疑多轮搜索的边际收益，说明反馈必须带 roofline/带宽信号——与 `stop_at_roofline`、`hw_feedback`、`patience` 同向。

- 初步价值：高 5/5 — 每条发现都能在我们自己的 `result.json` 上复算并改策略。
- 最终层级：S（主代理校准）

- 可信 harness 候选：yes。两段式正确性（拒绝偶然通过）+ 分布外输入 + 量化契约静态检查 + 每机器重测基线 + 效率归一化，全落在评测有效性上；但它只度量跨机器方差，没有治理手段，安全与权限侧为零。

## 本组前 2 名

1. **2605.04956 KernelBenchX** —（5/5，可信 harness yes）它给的三条结论都是可以在我们自己的 `result.json` 上复算并证伪的命题（46.6% 正确但更慢、迭代只修不优、跨机最坏 21.4×），协议（两段式正确性、outlier 输入、每机器重测基线、效率归一化）能直接接在 compile→abi→数值→计时 的既有门上，改的是"到底发布哪个数字"，而不是再加一个排行榜。
2. **2603.08721 KernelCraft** —（5/5，可信 harness yes）它是唯一把"模型只能通过工具看世界、判决由工具给出"落成可复用接口清单的工作（write/check/eval/view/grep），并把 per-target 容差政策、容差与业界口径交叉校验、工具编排失败的单列归因一起给出，直接对上 `hmz` 工具面、`targets/<id>/` 信任与 `agent_no_submission` 处理；压到第二是因为其"文档极稀的新 ISA"前提对成熟 Metal 栈只有部分成立。

### 2603.08721 KernelCraft: Benchmarking for Agentic Close-to-Metal Kernel Generation on Emerging Hardware

- 本地 PDF：`docs/paper/2603.08721_kernelcraft-benchmarking-for-agentic-close-to-metal-kernel-generation.pdf`

- 讲了什么：瞄准最不成熟的一档硬件——新型 ISA 的裸机汇编 kernel。33 个任务（23 ML + 10 CPU）、三个新兴加速器（PLENA、AMD NPU、Coral NPU）加 RISC-V BOOM，每任务 5 组配置。关键设计是把 agent 的工具面固定为 6 个原生 function call：write code / check syntax / run evaluation（回 match rate 与 latency）/ view output（逐元素差异统计）/ get instruction size / grep docs。agent 靠"写—查语法—跑评测—看内存差异—查文档—改"收敛，按 success rate 与相对编译器基线的加速比评分，迭代上限 15/20/25。

- 关键证据：>1100 次实验。GPT-5.2 成功率 PLENA 56/100、AMD 19/110、Coral 35/75；Gemini-3-flash 35/100、12/110、29/75；Sonnet-4 12/100；会写 CUDA 的 DeepSeek-R1 三平台各只成功 1 个。L1 原语在 PLENA 达 74%，L2 掉到 45%，L3 全组合仅 1 个 ConvBlock 通过。加速比：Coral ConvBlock 最高 7.93×，PLENA 归一化 1.06–1.22×，AMD 0.89–1.18×；与人类专家手写 depthwise conv 比，agent 为 2.5×/0.6×/0.5×，专家为 20×/18.2×/31.5×。无 thinking token 时 0/5，medium thinking 时 3–4/5。容差按平台声明（PLENA ε_abs 0.012/ε_rel 0.01、AMD 用 `torch.allclose` 默认、Coral int8 要求精确相等），并与 CUTLASS、Triton 口径交叉验证，匹配率 97.3–100%；13 组输入扰动（含 1% 20× 离群）全通过。

- 初步价值：高 5/5 — 工具面、容差政策、失败归类三样都能直接落。
- 最终层级：A（主代理校准）

### 2502.10517 KernelBench: Can LLMs Write Efficient GPU Kernels?

- 本地 PDF：`docs/paper/2502.10517_kernelbench-can-llms-write-efficient-gpu-kernels.pdf`

- 讲了什么：以 250 个真实 PyTorch 负载为输入（100 单算子 / 100 算子序列 / 50 端到端架构），要求模型产出 `ModelNew`，内部可内联任何语言的 kernel（CUDA/PTX/Triton）。基准只做自动验证、不提供 ground truth kernel，故可迁到任意硬件。核心贡献是 `fast_p` 指标：既数值正确、又比基线快过阈值 p 的任务占比（`fast_0` 即正确率），以及三类 test-time 手段的对照：重复采样 `fast_p@k`、带"生成/执行/剖析"反馈的迭代修正、硬件知识与范例的上下文注入。定位是"以 PyTorch 为参照、按墙钟衡量收益"的通用落地方案。

- 关键证据：一次性 `fast_1`：o1 为 10/24/12%、DeepSeek-R1 为 12/36/2%（三级，vs Eager，L40S），均 <20%；R1 加 G+E+P 迭代十轮后升到 43/72/18%。DeepSeek-V3 在 L2 上重复采样 k 从 1 到 100 把 `fast_1` 从 4% 抬到 37%，但 34 个卷积变体用满 100 样本仍 0 正确。计时为 3 次预热 + 100 次 CUDA event 取均值，自报 CV<3%；正确性用 5 组随机输入，100 个 kernel 的对照实验里 50 个在 5/5 与 100/100 同时通过、19 个在 0/5 与 0/100 同时失败。硬件泛化：R1 L2 在 L40S 为 36%、A10G 为 47%。

- 局限与不可直接外推：（1）全在 NVIDIA/CUDA/PyTorch 生态，基线语义与指令集都不能搬去 Metal；（2）正确性等于 5 组随机输入，论文自认等价不可判定、无形式化保证，只能算抽样证据；（3）`fast_p@k` 随采样预算单调上升，是搜索预算的函数而非内核质量，k 不同的数字不可比；（4）用均值墙钟、未给噪声门槛与跨机器重测。

- 对本仓库的具体价值：`fast_p` 的"正确且快过阈值"正好是我们"搜索门 + 噪声门槛 + 确认测量"的对外口径；把 `fast_p@1` 与 `fast_p@k` 分开记账，就落成 `result.json` 里 `best_speedup`（搜索期、k 次）与 `confirmed_speedup`（确认期）两个字段，避免"从多次噪声里取最大"。G/E/P 三档反馈对应 `feedback.txt`、`hw_feedback`、`roofline` 三个注入源，可据此做"只给编译错误 vs 加剖析"的对照。硬件知识与范例注入降低 `fast_1`、却把激进优化比例推高（o1 在 77% 的 GEMM 变体上用上 tiling），说明 `device.md`/`experience.md` 的效果要连 compile/abi 失败率一起看，不能只看速度。

- 初步价值：高 5/5 — 指标定义与反馈闭环直接可用，且与我们的门/确认口径同构。
- 最终层级：A（主代理校准）

- 可信 harness 候选：borderline。它把"抽样正确性"与选择偏差讲清楚了（等价不可判定、0/5 与 0/100 一致、`fast_p@k` 随 k 上升），对评测有效性有用；但没有隔离、权限、信任域与 provenance，正确性判据也弱于我们现有的数值关 + 域扫描 + 差分复查。

### 2507.17773 MultiKernelBench: A Multi-Platform Benchmark for Kernel Generation

- 本地 PDF：`docs/paper/2507.17773_multikernelbench-a-multi-platform-benchmark-for-kernel-generation.pdf`

- 讲了什么：先指出既有基准三个缺陷（只支持 NVIDIA、分类过粗、类别失衡），据此做 285 个任务、14 个功能类（新增 Broadcast/Resize/Optimizer，扩 Index），覆盖 CUDA/AscendC/Pallas 三平台，并把基准拆成"平台无关核心 + 可插拔 backend"：每个平台实现设备初始化、编译执行、正确性与计时、资源清理，用 `@register_backend` 注册，新增平台不改核心逻辑（论文称接 Triton 少于 20 行）。指标三层：Compilation@k、Pass@k、SpeedUp_α@k。正确性沿用 N=5、atol=rtol=1e-2；性能用平台同步标记夹住执行区间；基线只用 PyTorch eager，明确排除 torch.compile（认为其行为随平台变化、破坏可比性）。

- 关键证据：285 任务 × 7 模型 × 3 平台。最强 Claude-Sonnet-4 在 CUDA 上 Comp@1 92.3%、Pass@1 47.0%、SU1@1 20.4%，全平台贪婪解码只过 164/855；DeepSeek-R1 CUDA Pass@1 52.6% 但 Pallas 仅 2.8%；AscendC 最高 Pass@1 仅 2.5%，Pallas 8.4%。类别落差极大：Activation 平均 88.9% vs Convolution 13.7%。类内 one-shot 例让 GPT-4o 在 AscendC 上编译成功率相对 +380%、Pass@1 相对 +160%；AscendC 编译失败中 74.8% 含 "no member named"。

- 局限与不可直接外推：（1）基线只有 eager，与我们区分 `compiler_baseline`/torch.compile 的口径不同，数字不可直接比；（2）容差 1e-2 相当宽，作者自述是为容忍 BF16/FP8，会放过真实数值错误；（3）计时只声明"同机不同时间稳定"，无 CV、无批次数、无噪声门槛，2µs 级算子的加速比作者自己怀疑是噪声；（4）三平台都是"能跑通"级别，分母是每模型每平台任务数，不可跨平台加总。

- 对本仓库的具体价值：它的 backend 抽象正是 `tcenv/backends/<id>/` 加 `registry` 的形态，可作为协议对照清单——尤其"资源清理"和"平台原生同步标记"两项，如果我们写进协议，就不会把异步 launch 当成已完成计时。三层指标对应我们 compile→abi→数值→计时 的关卡分离，Comp@k 远高于 Pass@k 的巨大落差支持"编译通过不算候选"的既有设计。类别粒度论证（同一难度档内 88.9% vs 13.7%）提示 experience index 应带"类别"维度而非只用难度；类内示例的相对增益为"任务书里放同族示例"提供了比泛化 few-shot 更具体的依据。

- 初步价值：高 4/5 — 后端抽象与指标分层可直接对照；扣分在宽容差、无噪声门槛。
- 最终层级：A（主代理校准）

- 可信 harness 候选：borderline。后端解耦属于 harness 架构而非信任机制，且其宽容差、无 CV 的计时口径与我们的可信口径方向相反。

### 2502.14752 TritonBench: Benchmarking Large Language Model Capabilities for Generating Triton Operators

- 本地 PDF：`docs/paper/2502.14752_tritonbench-benchmarking-large-language-model-capabilities-for-generatin.pdf`

- 讲了什么：第一个以 Triton 为目标的算子生成基准，双通道：G 通道 184 个来自 GitHub（95 个 ≥100 star 仓库、845 个 py 文件筛出 250 个候选，再人工整理/补 wrapper/去重）的真实算子；T 通道 166 个与 PyTorch 接口对齐、按 The Stack V2 频次采样再融合的算子。指标不止正确率：CodeBLEU 相似度、call accuracy、execution accuracy、相对参考实现的 speedup，以及以 A100 峰值为分母的 GPU efficiency（`triton.testing.do_bench`，逐步加长预热与重复直到计时稳定）。结论是 LLM 写 Triton 远未过关，并把失败按 16 种错误归为语法/属性类型/名字引用/运行逻辑四组。

- 关键证据：G 通道最高 execution accuracy 23.91%（o1 一次性），T 通道 53.01%（R1 零样本）；最高 speedup 分别 1.56× 与 1.91×。领域小模型零样本 0.00%，SFT 后 Qwen2.5-Coder-7B 4.89%、deepseek-coder-6.7B 9.78%（G 通道）。基准自带人工算子平均 GPU efficiency 仅 43.0%，其中 19.6% 低于 10%。全部实验在单张 A100。

- 局限与不可直接外推：（1）单卡 A100、单一 DSL，efficiency 的分母是 A100 峰值，换芯片不可外推；（2）speedup 只在"执行正确"的子集上算，而论文自己说正确子集偏简单、融合收益被放大，是条件在选择上的偏差；（3）未给出显式 atol/rtol 讨论，也没有跨机器重测基线；（4）参考实现经过人工修补，"最优性"未验证。

- 对本仓库的具体价值：这是我们唯一"上游同构"的基准——题面就是 Triton 算子，而我们的题目正是 Triton→MSL，题面形态与失败类型可直接复用为 `tcenv` 回归题与失败分类。16 类错误可映射成 compile/abi 关卡的 message 分类，成为 P1（任务书措辞）与 P2（`msl_reference.md` 技能）的选题依据；四类错误在 zero-shot 与 one-shot 之间的迁移（语法类上升、逻辑类下降）正是 `experience.md` 生命周期要验证的假设。GPU efficiency = 实测 GB/s、TFLOPs 除以芯片峰值，与 `targets/apple-m4-max` 的 chip profile 加 roofline 上界同思路，可把我们的 roofline 比值升级为归一化效率，减少小 kernel 上墙钟噪声主导。

- 初步价值：高 4/5 — 上游同构、失败分类可直接进经验库；扣分在单卡、无容差协议。
- 最终层级：A（主代理校准）

- 可信 harness 候选：borderline。`do_bench` 稳定化与效率归一化触及计时有效性，但整体不涉信任域、隔离或权限，正确性证据也只有单次执行对比。

### 2606.20128 The Correctness Illusion in LLM-Generated GPU Kernels

- 本地 PDF：`docs/可信harness/papers/2606.20128_correctness-illusion.pdf`
- 讲了什么：直接测而非假设 KernelBench/TritonBench/GEAK 共用的正确性判据——固定形状、小样本 allclose——是否乐观。作者造 24 个 Triton 与 numpy 替身内核的受控语料（15 个正确对照 + 9 个按已知 LLM 转写错误注入的变异），用算子 schema 感知的种子化 fuzz（共享符号维度采样，候选集含边界值）、fp64 参考、按 (op,dtype) 的绝对容差重判；再扩到 26 个算子、5 类 GPU 复跑。适用于任何已有 allclose 判据的工程，不需要训练模型。
- 关键证据：单卡 24 题上，种子化判据抓出 9/9 变异、放过 15/15 对照（对照上零误报）；扩到 26 题后 5 类 GPU（RTX 3060/A10/L40S/A100/H100）判定完全一致：10/10 illusion 抓住、16/16 对照干净。关键负面结果在形状：softmax tail-mask 变异在 30 个随机 case 里失败 13 个，只用规整形状时 0/10 失败，只用边界形状时 6/10；bug 在 H=3 出现、H=256（2 的幂、无尾巴）消失。最小失败形状 softmax [1,1,3] fp16、gelu [2,1,1] fp16，allclose 原判据都不会碰到。两类 bug 需要不同对策：幅度均匀型（漏 0.5、漏 sqrt、α 错）几乎每个形状都错，只是容差压在常数偏差之上；形状相关型（tail mask、acc= 而非 acc+=）只在边界形状可见。
- 局限与不可直接外推：(1) 10 个变异是作者按文献播种，不是真实 LLM 输出，结论是"哪种 bug 型会被判对"，不是"某模型 bug 率"；(2) 语料小（24/26 题、多为单算子、30 次/op·dtype ≈1440 case），无计时、无性能维度；(3) fp64 参考被当作"正确"的定义，且只做同 dtype 比较，bf16 在客户端被代理成 fp16；(4) 容差本身是否校准被推给同作者的另一篇（2607.16228），本文不回答。
- 对本仓库的具体价值：正中我们的形状盲区。`tasks/*/task.py` 用固定两档 size，且显式 `assert M_TOTAL % BLOCK_M == 0`（conv2d 等），也就是它的"regular-shapes-only"设定——按它的测量，这一档对 tail-mask 变异召回为 0。我们的 `domain` 全位型扫描只扫值不扫形状，`ieee`/`tiny`/`large` 也都是同形状换值。可施工的两条：(a) 给一部分题加"尾部"档（尺寸不被 BLOCK/threadgroup 整除，例如 n=3、7、1025），成本是新 contract 实例而非新内核；(b) 在 correctness 里记 ErrorStats（max abs/p99/ULP 分位）而不只是布尔，这样"幅度均匀型 bug 被宽松容差吸收"会留下证据，也直接对上我们"允许值升到库误差 2 倍、上限 8"的放宽策略——该策略正是它指出的那种吸收。它的可重放（每个失败存种子、逐字节重放）与我们 case 种子入报告同构，无需改。
- 初步价值：高，5 分。它是本组唯一直接命中我们正确性判据形状假设的工作，且修法便宜。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。对象就是评测判据的有效性（oracle 强度、输入生成、容差、可重放），是 tcenv 差分门的直接依据。

### 2607.16241 KernelBench-Verified: Do LLM-Generated Kernels Actually Beat PyTorch?

- 本地 PDF：`docs/可信harness/papers/2607.16241_kernelbench-verified.pdf`
- 讲了什么：论证 KernelBench 式"单轮生成、固定形状、torch.rand 输入、fp32 eager 基线"的协议同时高估速度与正确性。作者加三件事：把 PyTorch 基线开到 TF32 张量核（从业者实际路径）、用四组值变换（原始/×3/×0.01/取负）做隐藏正确性门、再补峰值显存指标；7 个前沿模型在 H200 上重测 250 题、best-of-5。适用范围是单轮推理内核排行榜的协议修正，不涉及多轮搜索。
- 关键证据：GPT-5.5 聚合加速比 1.43×→0.88×，无模型在任何 level 达到 1×（区间 0.47–0.88）。分解到 250 题：TF32 基线影响 21.2%、隐藏用例 11.6%、两者 2.4%、都不影响 64.8%；L2 上 GPT-5.5 1.67→0.88（TF32）→0.85（隐藏）。三题参考输出恒为零（PID 23/80/83），GPT-5.5 直接返回零拿 71×/34×/235×，被剔除。P19 ReLU 用形状守卫返回输入，得 374×。容差 1e-3→1e-4 时 GPT-5.5 的 L1 正确率 99%→83%、加速比反而 0.90→1.25（选择偏差）。28% 的正确内核峰值显存反而升高，L3 显存效率中位 0.88。453 个幸存加速核双 LLM 评审：一致标记 6 个，人审后 4 个真 hack（0.9%）、2 个合法形状特化。
- 局限与不可直接外推：(1) 单轮、单卡 H200、只测推理，作者承认多轮反馈会开新的 hack 面；(2) 隐藏用例是 4 个确定性变换、只变值不变形状，可被预见；(3) 基线只对 eager PyTorch、不对 torch.compile；BF16 下同模型 L2 达 1.63×，说明"打不过库"强依赖基线选择；(4) 剔 3 个退化题、2 个 NaN 配置、以及 τ 的选择都改聚合分母，作者自己展示这会翻转结论方向。
- 对本仓库的具体价值：最有价值的是"退化题审计"——若某题参考输出在全部 case 下恒定（卷积→GroupNorm→取均值这类），候选返回常数即可过差分与确认，拿到巨大 confirmed_speedup；可做一次性 corpus 审计（每 case 三个种子跑参考，全恒定则标记），不调模型、不重测。其次是容差与分母的耦合：published speedup 是"通过题集的几何均值"，收紧容差同时改变谁算通过和题集大小；report 现在记 rtol/atol_rel，但不记该容差下的通过题集，也没有敏感性分析，按它的证据收紧可能让数字变好看。第三是缺口：EvalReport 没有峰值显存，一个 2× 快但 3× 显存的内核在我们的信任语义里仍算合格。它的 input-blind 生成（提示里去掉 get_inputs）对我们不适用（TASK.md 本就给形状），可借的是"评审后按 hack 家族回归"而非去掉形状。
- 初步价值：高，4 分。退化题审计、容差—分母耦合、显存缺口三条都能直接落成 corpus 检查与报告字段，成本低。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。核心正是评测有效性（基线现实性、隐藏分布、退化题、外部审计），且示范了"审计脚本自身要人复核"。

### 2607.04454 Correct but Slow: An Empirical Study of the GPU Kernel Evaluation Gap in Modern Domain-Specific Languages

- 本地 PDF：`docs/paper/2607.04454_correct-but-slow-an-empirical-study-of-the-gpu.pdf`
- 讲了什么：论证"过正确性门"不等于"可替代库算子"。作者用 22 个 Triton/TileLang 内核（GEMM、attention、conv、norm、逐元素/归约五类）在 A100 与 GH200 上跑 KernelBench 端到端 + TritonBench 判据分析 + NCU 计数器，把隐藏的性能差按"修在哪一层"分类：用户书写（RC0a/RC3）、编译器代码生成（RC0b/RC1/RC2a）、库成熟度（RC2b/RC4），再给出两条轻量判据（库相对效率 + roofline 占比）。
- 关键证据：一个惯用写法的 TileLang LayerNorm 过了 KernelBench 正确性门却在 GH200 上慢 323×（51.5 vs 0.16 ms），RMSNorm 慢 117×，最坏变体 1293×；KernelBench 唯一的 reward-hacking 守卫（吞吐超基线 10×）永不触发，因为它只防"太快"。成因定位：把 T.serial 换成 T.reduce 加原生 bf16 I/O 一处修好 LayerNorm，364 ms→0.270 ms（1347×，达 PyTorch 的 124%），GH200 侧 authoring cliff 1541×。残留是真差距：Conv2d 42.4%（3×3 只 28.9%）、大方阵 GEMM 77%、argmax 27%，其中缺 Winograd 只占 ≈2–3%。跨目标一条最刺眼：logsumexp 在 A100 是 581.7%，同内核在 GH200 寄存器溢出（255 regs、≈280 GB 局部溢出、12% 占用）掉到 1.0%，重调参上限也只到 63%。另一条：FP32 TileLang GEMM 的 T.gemm 在 SM80 静默降到 TF32，10⁻⁵ 精确检查下 31.8% 输出不符，而手写 FMA 通过。
- 局限与不可直接外推：(1) 只测前向、只 NVIDIA、只两个 DSL 版本，ROCm/XPU 未测；(2) TileLang 内核是作者自己重写，"300×"的代表性被作者列为 construct validity 威胁；(3) 22 题是诊断探针而非基准，作者明确说不用于认证；(4) roofline 占比 ρ 依赖"本质工作量"与硬件峰值假设，两条判据在 ρ≈0.5 附近会给出相反判断。
- 对本仓库的具体价值：两条可直接用。(a) 跨目标信任：它给出"同一内核在一个目标上 581.7%、换一个目标 1.0%、且无任何正确性信号"的实例，正是我们 `target_id`/目标激活/trust scope 要防的失效模式；建议把"信任只在被激活目标的芯片档案下成立"写成硬约束，target 或工具链指纹一变即视为未验证，而不是沿用旧结论。(b) 静默降精度探测：我们的 compile 门不检查工具链是否把 fp32 降到 tf32/fast-math 等价路径；可对每个 fp32 题保留一次严格阈值探针（它用 10⁻⁵ 抓住 31.8%），把"参考实现自身不达标"与"候选写错"分开。附带一条：它的 comparability screen 会循环（基线既当标准又是定义），我们已用 roofline 字段缓解，但可把 ρ 当作"送确认前"的廉价预筛，避免把批次预算花在离硬件峰值极远的候选上——注意我们 `bench` 的语义是"慢不失败"，所以这是省预算，不是加门。
- 初步价值：中，3 分。跨目标复验与静默降精度两条硬，其余（roofline 预筛）与我们已有字段重叠。
- 最终层级：A（主代理校准）
- 可信 harness 候选：yes。它讨论的是验收判据该不该只看正确性、以及结论的适用范围（哪个目标、哪个工具链），属评测有效性与信任边界。

### 2605.26329 JobBench: Aligning Agent Work With Human Will

- 本地 PDF：`docs/paper/2605.26329_jobbench-aligning-agent-work-with-human-will.pdf`
- 讲了什么：不做内核，做职业知识工作的 agent 基准。以 Workbank 的"工人愿意委派哪些职责"问卷为选题信号，取高委派意愿且高经济暴露的 35 个 O*NET 职业，构造 130 个任务（65 main / 65 easy），每题是一个含 3.9 个异质参考文件的 workspace（502 个文件、17 种格式），由"事实锚定的 rubric 链"评分：4,631 条二元判据、平均 35.6 条/题，一条链里所有判据同时通过才给分，无部分分。适用于衡量专业交付质量，不涉及可执行验收器。
- 关键证据：36 个模型-脚手架配置，最强 Claude Opus 4.7 + Claude Code 仅 45.9%，GPT-5.5 + Codex 42.7%，Claude/GPT 之外无配置超过 19%（最弱 Grok-4.2-Fast 4.38）。对比 GDPval 已饱和（GPT-5.3-Codex 70.9、GPT-5.4 83.0）而 JobBench main 只 33.7/38.9，同模型 runtime 是 GDPval 的 2.40×；easy 集分数高 26–31 点。脚手架本身可移动 3–6 点（Sonnet-4.6：Claude Code 36.9 vs OpenClaw 30.6）；推理档位 low→xhigh 升 7.0 点。语料质量：71% 任务通过三阶段门（自动审计/标注复核/试解），全基准的 union pass 率 95.4%。评审用 x-ai/grok-4.1-fast，与 Opus-4.5 判分差 0.1–0.7 点，成本从 $38–46 降到约 $1.5–2（约 20×）。

- 对本仓库的具体价值：几乎没有机制可搬。tcenv 的判决是确定性的执行结果，不需要 rubric 链，也不需要 judge 成本与一致性校准。唯一可借的是它的**任务可达性过滤**：只有"跨多种 agent、多次采样后 union 覆盖 >90% 自身 rubric"的任务才入集——对应到我们，就是"某个 case 没有任何候选（包括参考内核）能稳定通过"这类死题应当在 corpus 审计里标出，而不是让它在搜索里反复消耗批次。它的"脚手架与模型同等重要"只作旁证，不能拿来论证我们 overlay 的收益。
- 初步价值：低，1 分。领域与判据机制都与 tcenv 不同，只有语料卫生一条可借。
- 最终层级：C（主代理校准）
- 可信 harness 候选：borderline。它是基准有效性（饱和、judge 一致性、全或无链防"流畅但错"）的正面案例，可作为"LLM 评审层"若将来出现时的模板；但没有任何执行可信、权限或经验生命周期的内容，不能进可信 harness 的证据链。

### 2608.12629 CAKE: Compiler-Agent Co-Design for Frontier Kernel Evolution

- 本地 PDF：`docs/可信harness/papers/2608.12629_cake-compiler-agent-codesign.pdf`
- 讲了什么：把 kernel agent 与 GPU 语言当成共同演化的一个对象。agent 不写 CUDA，而写 Cake IR——带类型、显式声明 warp 角色、共享内存/TMEM 资源、barrier、流水线阶段与指令形式的 schedule 表示；刻意不引入 layout 代数，布局写成具体承诺、合法性由编译器检查。harness 在编译前做安全、硬件契约、数据一致性、schedule 语义四类静态门，诊断定位到具体资源/角色/阶段；成本模型只用于排序过滤，GPU 实测仍是最终真值。第二层是编译器演化：失败候选的诊断被蒸馏成新 verifier 规则、IR 原语、成本模型标定或可复用 tactic，改动须过 kernel corpus 测试并由人工合并门放行。单形状演化与库级 dispatch 泛化被显式拆成两个阶段。
- 关键证据：Flash-KMeans 干净启动、每臂三次匹配运行（同一 GPT-5.6-sol xhigh、8000 万 token 预算、隐藏低层实现）：Cake IR 3/3 达到预设平台期，最好 1.144×（[1.041,1.205]）调优 FlashML Triton 基线（0.938 ms）；直写 CUDA/PTX 0/3、0.928×（[0.852,1.151]），活跃演化 1.89 h vs 3.73 h。前沿核：KDA prefill 六个 B200 BF16 形状几何均值 2.05× 超官方 FlashKDA，按验证契约 bitwise 正确，并在 Kimi-K3/SGLang 端到端服务验证；已知核复现 11 项中 10 项不低于参考、1 项 96.5%。dispatch 家族在 112/198/124 个形状上 1.418×/2.116×/1.803×，无错误输出。corpus 含 400+ 静态/编译用例与 399 条 GPU 正确性用例、约 28 家族。
- 局限与不可直接外推：(1) 干净启动仅 n=3 且两臂区间重叠（[1.041,1.205] 与 [0.852,1.151]），1.144 vs 0.928 支持度有限，不能当可复现效应量；(2) 计时几乎全在 B200，成本模型只在 B200/H100 标定、其他目标明确"拒绝预测"，非 NVIDIA 完全未测；(3) 静态分析自认不完整、可能出假阳与假阴，"coverage 缺失按显式不可判报告"不等于证明；(4) 已知核里高于参考的条目作者自认含 porting 期搜索出的额外优化，"parity" 不是转录保真度，编译器演化仍在人工合并门下。
- 对本仓库的具体价值：三处可直接落地。其一，Table 1 的 disposition 分类（pre-compile gate / execution gate / report / hint）是我们 compile→abi→safety→numeric→timing 关卡的通用化写法，尤其"hint 永不阻塞、report 只给瓶颈类"这条分界可作 plan-02/plan-06 渲染分流的依据：建议性内容不得走阻断通道。其二，"信息缺失按显式不可判处理，不当作检查通过"对应我们 `verify()` 恒 `unsupported`、`eligible` 只等于 `status == ok` 的诚实声明，可写进 plan-09 的一致性表述。其三，第 6 节防泄漏规则——有效形状域在调优前声明、dispatcher 谓词不得新增评测行、覆盖度只经同源确定性未见解分片扩张——是确认门之外我们缺的另一半：换种子防的是"同批输入被重放"，它防的是"评测域被搜索过程改写"。它还把"新 verifier 规则不经 corpus 验证会误杀合法核"写成显式风险，正对 plan-01 要求把攻击检出与合法解误拒分账。
- 初步价值：高，5 分。唯一同时给出可演化 verifier、fail-closed 不可判语义、dispatch 防泄漏与人工合并门的完整结构。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。核心命题就是"harness 本身是被演化对象"：失败→新 verifier 规则→corpus 测试门→人工合并，属 harness 自改进与评测有效性；它把诊断绑定到资源/角色/阶段，也是可信执行记录里可归因的最小单位。静态门强度有限，借结构与纪律，不借效果数字。

### 2601.22760 AscendCraft: Automatic Ascend NPU Kernel Generation via DSL-Guided Transcompilation

- 本地 PDF：`docs/paper/2601.22760_ascendcraft-automatic-ascend-npu-kernel-generation-via-dsl-guided.pdf`
- 讲了什么：把"直接写 AscendC"改成两段式。第一段让 LLM 写一个轻量 DSL：host 函数显式声明核划分与切分策略，kernel 函数显式分配 UB/L1 缓冲、并把计算切成 copyin/compute/copyout 块，禁止隐式别名；提示由 DSL 规格加"按算子类别、按形状"的专家示例组成。第二段用四道受约束的 lowering pass（host 侧、kernel 初始化、计算翻译、可选的 32 字节对齐/padding 精修）把 DSL 转成 AscendC，每道 pass 后用编译器反馈做修正，并把每个 DSL 块固定映射成一个 `__aicore__` 阶段函数，从结构上禁止数据搬运与计算非法交错。目标是新兴 NPU 这类语料与文档都稀缺的平台。
- 关键证据：MultiKernelBench 七个类别 52 个核（MatMul 与 Conv 被排除），单次生成下 Comp@1 98.1%、Pass@1 90.4%；性能用 Fastα（达到 eager 的 α 倍）分档，Fast0.2 82.7%、Fast0.8 57.7%、Fast1.0 46.2%；分档差异极大——Reduce 的 Fast0.8 与 Fast1.0 均为 0%，Pooling 的 Fast0.8 为 0%，Normalization 的 Fast1.0 只有 37.5%。对照是文献里直接生成 AscendC 的正确率（Claude Sonnet-4 13.0%）。迁移案例：mHC 的两个新核单次生成正确，分别 6.6×/3.0× 于 eager；人加 LLM 再优化后到 15.9×/7.2×。环境 Ascend 910B2、CANN 8.1、PyTorch 2.6，用更新后单核耗时超 15 ms 的形状。
- 局限与不可直接外推：(1) 排除了 MatMul 与 Conv 这两个最重的类别（自认 Cube 编程难度未解，在试 CATLASS），所以 90.4% 不代表最难的部分；(2) 性能基线只有 PyTorch eager，没有与任何专家 AscendC 核或厂商库对比，Fast1.0 只说明"不慢于 eager"；(3) 示例是"按类别、按形状"给出的，与测试集是否同源、是否有泄漏控制全文未交代，泛化上界不清楚；(4) 单芯片单 CANN 版本、无计时噪声协议、Pass@1 只算单次尝试，也未给失败分类。
- 对本仓库的具体价值：两条思路可移植。其一，"为生成设置结构骨架"与我们 `TASK.md` + `msl_reference.md` + `device.md` 的分工一致：DSL 隐去 DataCopyPad 这类冗长细节、保留 UB 分配与流水阶段——正对应我们把 MSL 的线程组/线程组内存/同步这些必须显式写清、把模板化样板交给技能文档。它给出的是"隐去什么、保留什么"的判据，可用于 P2 技能与 TASK 措辞的取舍。其二，Fast0.2/0.8/1.0 的三档把"能用但很朴素（走标量、单核）"与"有竞争力的数据流"分开；我们目前只有 `roofline` 比值与噪声门槛，"慢但正确"一律落 `status == ok`。把 roofline 距离做成"是否用上并行/向量化"与"是否接近上界"两级报告，属渲染层改动，可先作假设。多道 pass 加逐 pass 编译反馈也可映射到 P2 的增量修复顺序，但强度低于我们已有的整核编译关。
- 初步价值：低，2 分。抽象层次与分档报告的思路有用，但硬件、语言、基线全都不可外推，且缺最重类别。
- 最终层级：A（主代理校准）
- 可信 harness 候选：no。它是生成侧的结构约束，不是执行侧的可信边界；正确性仅对 eager 做数值对比，无对抗模型、无权限、无 harness 演化。

### 2606.07665 AgentCompile: An LLM-Guided Compiler for Direct CUDA Inference

- 本地 PDF：`docs/paper/2606.07665_agentcompile-an-llm-guided-compiler-for-direct-cuda-inference.pdf`
- 讲了什么：把"谁写"与"谁准入"分开。Tier 1 里 LLM 只当顾问：编译器切 region、枚举有界模板候选空间，LLM 只回语义标签、候选偏好、参数提示与风险标注，越界即丢弃，代码全由模板生成。Tier 2 里 LLM 直接写五类 decode 关键融合核（QKV+RoPE、gated MLP、residual+norm/RoPE、paged decode attention、o_proj 与 lm_head+argmax），但必须满足编译器定义的契约：张量接口、dtype 规则、数值容差与性能下限；提示词来自"原则库"（只含设计决策与被证伪的死路，不含核源码），θ_gen=0.99、至少 4 轮结构化失败反馈回灌并保留最好候选。运行时再做一次 in-graph 实测准入：T(k) ≤ µ·T(b)，µ=1.04，否则回落库/手写路径。适用范围是 transformer 式推理的 decode 路径。
- 关键证据：A800，六个模型家族。单请求 2.23–6.98× 于 PyTorch eager、1.04–1.16× 于 vLLM；多请求 uniform 1.04–1.12×、ragged 1.04–1.08×。消融（Qwen3-4B，i128/o128 由 4765 ms 降至 824 ms）：CL+GEMV+StaticCache 1.58×，加 FAKV+QKV proj+Graph 到 2.32×，LLM 层再加 1.34×，合计 4.95×。核级呈两极：融合替掉多算子框架路径才有大赢（RoPE 4.27×）；已有实现接近带宽屋顶时生成核聚在 0.96–1.12×，paged decode attention 仅为 FlashAttention 的 0.955–0.975×，GLM-4 的 32:2 GQA 配置 0.45× 被拒。
- 局限与不可直接外推：(1) 最要紧：µ=1.04 意味着慢 4% 以内的核仍会进场（0.962× 以上即通过），0.955–0.975× 恰好落在该容差内，与"生成核匹配或超过专家核"的表述不一致——端到端收益主要来自运行时（Graph、paged KV、静态 cache），不是核质量；(2) 报告 174/174 全部验证通过且最大绝对/相对差 0.00e+00，在 bf16 下异常，未说明参考与比较方式，存在同源对比可能；(3) 单卡 A800、LLM 层固定 Claude-Opus-4.8、只覆盖五类 decode 核与 transformer 式 region，越界一律回落；(4) 作者自认与 vLLM 是各自优化栈的不同部分，1.04–1.16× 不能归因于核。
- 对本仓库的具体价值：三条。一是"性能下限写进契约"：θ_gen 放进候选准入，而不是等到搜索替换策略再判；我们目前把噪声门槛放在替换/确认两层，这正是"候选级 vs 发布级"两级门限不能共用同一阈值的对照设计，可作 plan-02 讨论材料。二是 in-graph 实测准入加 never-worse 回落，是"慢本身不改 `status`、但慢于基线不得替换"的形式化写法，我们已有 fallback，但没有逐 site 的 µ 记录字段。三是原则库专收"被证伪的死路"并跨模型复用，正对 plan-07：retired/refuted 条目不是垃圾而是负向经验，用来防止模型重走已测死的方向；它的 decode attention 作为跨模型 seed 仍需重新过门，也为我们"经验迁移必须重新验证"提供同构先例。
- 初步价值：高，4 分。门限分层与负向经验最贴我们；核级证据自相矛盾，只能借机制不借加速比。
- 最终层级：A（主代理校准）
- 可信 harness 候选：borderline。把"作者权"与"准入权"分离、以实测加裕度决定谁能跑，属评测有效性；但它没有对抗模型、没有权限/信任域、没有 harness 演化闭环，正确性也只是容差内的经验对比。

### 2607.24762 Kernel Forge: An Agent Harness for LLM-based Generation and Optimization of CUDA Kernels

- 本地 PDF：`docs/paper/2607.24762_kernel-forge-an-agent-harness-for-llm-based-generation.pdf`
- 讲了什么：面向真实 PyTorch 模型的端到端 agent harness。先跑模型捕获实际执行的算子，按 shape/dtype/layout/参数聚成 variant 并写成 operator card（调用次数、eager 耗时、运行占比、验证样本）；agent 只针对 variant 生成 CUDA 与 launch wrapper，过 nvcc、启动、与捕获的 eager 输出按 dtype 容差比对三道关后进入 MCTS 树（UCT 取最小化 + progressive widening，α 0.5→0.3，C=1.0，保留变慢但合法的节点）；最后导出带守卫的包：仅当可用、与捕获调用兼容、在记录样本上数值有效、且实测快于同一 variant 的 eager 时才替换，否则回落，并给每条路径打 generated CUDA / wrapper-backend / fallback 三类审计标签。附 GUI 与 CLI 供检查候选、树与失败。
- 关键证据：单机 DGX Spark（GB10，sm_121），四个模型（ResNet-50、SD3.5 Medium、Gemma 4 E2B、Qwen3.5 35B-A3B），每核仅 50 次迭代：1.52× adaptive_avgpool2d、1.70× group_norm、2.83× softmax（Gemma）、1.54× softmax（Qwen）。但收益结构是关键：开源/native 算子 13/24 快于 eager，厂商库算子仅 1/9；支配性算子全部低于 1.0——conv2d 0.999× 占 53.35%，SD3.5 linear 0.495× 占 53.40%、SDPA 0.021× 占 27.12%，Gemma linear 0.246× 占 90.13%，Qwen grouped matmul 0.616× 占 93.62%。成本按 Opus 4.7（$5/$25 每百万 token）记录，opt50 一档吃掉大部分花费，且"固定每算子预算与部署影响不对齐"。
- 局限与不可直接外推：(1) 只报算子区域（operator-region）结果，没有端到端模型延迟，也没有按运行占比加权的总体收益，2.83× 与真实收益不可等同；(2) 正确性只是"对捕获输入与 eager 输出一致"，作者明说这是过滤器不是证明，样本外不保证；(3) 计时无噪声门槛、无重复间变异、无跨机复测，单卡单 provider（Opus 4.7），各臂无方差；(4) MCTS 未声称优于线性细化，alpha/C 与 50 次预算是设定而非调优结果。
- 对本仓库的具体价值：三处值得抄。其一，三态审计标签解决的是我们发布层已有的同一问题——"提升"到底是生成核的功劳、包装路径的功劳还是回落保住的基线；我们只有 `publication_role` 的 primary/fallback 二分，缺 wrapper/backend 这一态，可作 plan-04 证据链的字段补充。其二，"受守卫的替换"把准入判据写成四个合取（可用、兼容、样本内数值有效、实测更快），与我们"编译→接口→安全→数值→计时"的顺序门同构，可直接引为 `tcenv` 判定的外部对照。其三，按运行占比加权的记账给了 taic 一个真实短板：我们对每道题花同样预算，而它证明"高占比算子往往已被厂商库占住、局部大赢集中在低占比算子"，对 Metal 的推论是——收益更可能来自替换多算子框架路径，而不是在 MPSGraph 已覆盖的 matmul/conv 上取胜，可作为选题与预算分配的假设（先当假设，不进必做项）。
- 初步价值：中，3 分。审计标签与占比加权可直接用，但它自己就示范了"局部加速比不等于部署收益"。
- 最终层级：B（主代理校准）
- 可信 harness 候选：borderline。守卫替换与三态标签属评测有效性（决定什么能替换、什么能声称），但无隔离、无权限、无信任域、无 harness 自演化，验证强度也低于我们现有的差分关与域扫描。

### 2602.05885 Dr. Kernel: Reinforcement Learning Done Right for Triton Kernel Generations

- 本地 PDF：`docs/可信harness/papers/2602.05885_dr-kernel.pdf`
- 讲了什么：面向 Triton 的 RL 训练系统。先建 KERNELGYM：server–worker 分布式 GPU 环境，一卡一任务、每次评测在
  全新子进程、心跳与失败重排，向模型暴露正确性、计时、hacking check、profiler 四类结构化反馈。指出多轮 GRPO
  的组内均值基线含自身回报，梯度被系统性缩小 `1-1/N_t`，改用按 turn 的留一法 TRLOO；再用几何均值不匹配抑制
  处理训练–推理漂移，用"生成核占端到端 CUDA 时间比例"（PR）与 PRS 抑制 lazy optimization，最后做顺序测试时扩展。
- 关键证据：KernelBench 250 题、H100。作者复测 AutoTriton 发布模型：Level-1 仍有约 10% hacking，Level-2 上
  Fast@1 有 30.6% 而 Fast@1.2 只有 9.2%。本方法 hacking 率 1.7%，训练中从约 20% 降到约 3%；关掉 hacking check
  后约 50 步就饱和。lazy 案例生成核只占端到端 CUDA 时间 0.014%，改写成功的一例占 86.15%。Level-2 Fast@1.2：
  冷启动 5.6 → 25.6（14B），STTS 31.6%，取历史最优 turn 47.8%（对照 Claude-4.5-Sonnet 26.7%、GPT-5 28.6%）。
- 局限与不可直接外推：
  1. hacking check 的判据是"插桩 Triton 启动路径，train/eval 两种模式下都没执行到 Triton 核即判错"。它抓"根本没
     启动"，抓不到"启动了但读旧输出/只算首末轮组"，与我们 fresh-input 复验的攻击面不是同一集合。
  2. 计时为固定 warmup 加重复，奖励里速度比被截断到 3×，没有中位墙钟、CV 门与确认门，不能当我们发布成绩的方法。
  3. 只在 NVIDIA H100 与 KernelBench 上验证，分母固定 250 题，不含 Metal 后端、ABI/线程组约束与容差口径。
  4. 依赖分布式 GPU 池与多轮 RL 训练；本仓库不训练权重，也不付这份算力。
- 对本仓库的具体价值：把"作弊率"变成可测指标并随评测落盘，可并入 `EvalReport` 与反馈链路，让 plan-01 的每条
  反例都有分母而非轶事。启动级插桩与我们的毒化图案加两次重跑互补：它证明"没有实际执行"是首要攻击面，我们补上
  "执行了但没写全/写旧值"。一卡一任务是为计时可信，与 `tcenv` 机器级计时锁同源，可作 `docs/架构/评测.md` 的外部
  佐证。PR 是便宜的采纳信号：加速了但覆盖率 0.014%，就是 lazy optimization，可作 `taic` 反馈的判据。Fast@1 与
  Fast@1.2 的落差独立复现了"搜索 best ≠ 可发布"。
- 初步价值：高，4/5。反作弊与计时可测性可直接搬结构，但需从 CUDA/RL 语境降到"评测端只读证据"的规模。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。整篇都在讲评测有效性（作弊、lazy optimization、计时独占、失败隔离与自恢复），与
  plan-01/plan-04 是同一问题，且给出可执行判据而非倡议。

### 2602.24286 CUDA Agent: Large-Scale Agentic RL for High-Performance CUDA Kernel Generation

- 本地 PDF：`docs/可信harness/papers/2602.24286_cuda-agent.pdf`
- 讲了什么：大规模 agentic RL 系统，基座 Seed1.6（23B 激活/230B 总参数）。三块：数据合成（torch/transformers
  种子算子 → LLM 组合 1~5 个算子成融合题 → 四项过滤，得 6,000 条训练集）；skill 化 agent loop（OpenHands 风格
  工具加 `SKILL.md` 固定流程：先 profile、再改写、再在 GPU 沙箱编译评测迭代，达标线是超过 torch.compile 5%）；
  训练稳定性（单轮 PPO 热身 → RFT 初始化 actor → value pretraining 初始化 critic）。奖励改用 −1/1/2/3 里程碑分箱。
  CPU 侧编译在 Docker 终端沙箱，验证与 profile 作业派到独立 GPU 池，agent 只能通过固定脚本调用。
- 关键证据：KernelBench 250 题。Pass 98.8%、快于 torch.compile 96.8%、几何平均 2.11×（Claude Opus 4.5 为
  66.4%/1.46×，Gemini 3 Pro 69.6%/1.42×）；Level-2 100%、2.80×；Level-3 90%/1.52×。消融：去掉 agent loop
  快于 compile 只剩 14.1%，换回原始 speedup 奖励 60.4%，去掉 RFT 或 value pretraining 会崩溃。代价是 128 张 H20、
  150 训练步、128k 上下文、最多 200 轮；去污染用 AST 相似度阈值 0.9。
- 局限与不可直接外推：
  1. 128 卡专用池是它"测得准"的前提，资源量级不可复制，不能当常规 CI 或本仓库默认路径。
  2. 反作弊是工程手段合集（文件权限保护评测脚本、上下文管理器禁 `torch.nn.functional` 兜底、每题 5 个随机输入、
     数据集层排除常数或不可区分输出），没有对抗性反例集、误拒率或作弊率随时间变化的度量。
  3. 指标取轨迹内最优解，不是可复核的单次提交，与"发布绑定确认门重测核"语义不同，数字不可平移。
  4. 训练与评测都用 5 个随机输入并沿用 KernelBench 协议，与我们容差、毒化、差分、`domain_sweep` 的证据标准不同源。
- 对本仓库的具体价值：其一，权限隔离——评测与 profile 脚本对被测 agent 只读，正对应 plan-03/06 把 `tasks/`、
  `tcenv/task.py`、`tcenv/distributions.py` 划入 `SECURITY_CRITICAL` 的方向。其二，禁用兜底实现——它用运行时约束
  封死"难写的部分留给框架"，正是 AutoTriton 那类假优化的入口；Metal 没有 torch 兜底，但"用库算子冒充自写核"
  同形，值得一条等价检查。其三，数据过滤要求不同输入的输出不得为常数或数值不可区分，几乎就是
  `tcenv/distributions.py` 的反退化输入要求；AST 0.9 去污染可作 fresh-input/holdout 之外的泄漏参照。里程碑分箱
  奖励直接提示 `taic` 评分应分箱而非回归原始比值，抗噪且不易套利。
- 初步价值：高，4/5。反作弊与权限条款最贴近当前施工项，但整体依赖训练，只可取机制不取结论。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。评测脚本权限隔离、兜底禁止、输入非退化筛选、去污染阈值都属可信执行与评测有效性，
  可以落成检查项而非口号。

  40.36/39.16、fast1 17.04，去掉 RL 的 SFT-only 为 34.94/34.94、15.06；KernelBench L1 执行精度 36%、fast1 10，
  L2 45/17，L3 20/10。奖励消融（不含 `@triton.jit` 的生成数）：有规则奖励 5/6，无规则奖励 18/25，仅骨架 66/10。
- 局限与不可直接外推：
  1. 奖励只到"能跑且像 Triton"，没有性能项；作者自陈缺 performance-guided training，速度本就不是优化目标。
  2. 论文自己给出仍在发生的作弊：卷积留在 PyTorch 只给 ReLU 写核；或写一个从不被调用的假 Triton 核来满足
     `@triton.jit` 检查。Dr. Kernel 复测其发布模型，KernelBench L1 仍有约 10% 这类样本。
  3. 跨论文数字不可比：Kevin-32B 被指出用 180 条评测数据训练，本表仍并列比较，说明同榜对比需去污染证据才能读。
  4. 只在 NVIDIA 与这两套基准上，没有 Metal，也没有容差、确定性、ABI 口径与误拒分析。
- 对本仓库的具体价值：它是反例素材库的现成条目。三类"通过正确性但无意义"的形态（部分下放框架、假核不被调用、
  只改琐碎子算子）正是 `tcenv` 毒化输出、两次重跑与差分验证要挡的东西，也说明"测试通过"单独不够：须分别判
  "核是否真的承担了工作"与"加速是否来自被改写的那部分"。规则奖励被反噬（模型学会保留一个不调用的核骗 linter）
  是明确教训：plan-01 任何字面特征检查都不能替代执行证据，这与我们"未写判定按原始字节比较"的取向一致。
- 初步价值：中，2/5。方法与系统可迁移性低，但作为攻击形态清单与失败案例证据价值实在。
- 最终层级：B（主代理校准）
- 可信 harness 候选：borderline。没有可采纳的防护机制，只提供"评测可被如何骗过"的一手证据，宜进入 plan-01 的
  攻击登记与反例语料，而非可借机制的文献清单。

### 2511.01884 CudaForge: An Agent Framework with Hardware Feedback for CUDA Kernel Optimization

- 本地 PDF：`docs/paper/2511.01884_cudaforge-an-agent-framework-with-hardware-feedback-for-cuda.pdf`
- 讲了什么：Coder 生成、Judge 评判的两代理无训练循环。Judge 分两模式：编译或数值失败时给修错反馈；通过后调 Nsight Compute 取硬件指标 + GPU 规格，判定瓶颈（memory/compute/occupancy），每轮只让 Judge 抓 3–4 个关键指标给一条优化建议。指标集是离线筛出来的 24 个（每任务 100 个核取最快最慢各 5、按与运行时相关性取 Top-20、跨任务取 P75 以上）。适用于 KernelBench 式"PyTorch 参考 → CUDA 核"。
- 关键证据：KernelBench L1–3 共 250 题、RTX 6000：正确率 97.6%、平均 1.677×（中位 1.107、75 分位 1.592、Fast1 70.8%）；o3 直出 57.6%/0.680，o3 自反思 90.8%/1.107，只给修错 97.6%/1.222，只给优化 88.4%/1.509。分层子集 D* 上 100%/1.767×，轮数放大到 30 得 2.265×。换卡 A100 1.841、4090 1.327、3090 1.320，正确率都 100%。单核 $0.3 / 26.5 分钟（全指标版 $1 / 40 分钟）。容差 1e-4，默认 10 轮。
- 局限与不可直接外推：(1) 报的是"所有候选里最好的一颗正确核"，无独立复测、无换种子，1.677× 天然乐观，不能当发布级数字；(2) 正确性只靠 KernelBench 自带的少量输入 + 1e-4 容差，没有覆盖声明；(3) 与 Kevin-32B 的比较是跨硬件拼接（H200 对 RTX 6000），作者自己承认无法公平复现；(4) NCU 是 NVIDIA 专属，指标筛选流程依赖 100 次采样预算。另有一条正面发现：作者查到 CUDA-L1 报"高性能"的核里根本没有 CUDA 代码，靠 try-except 回退到 PyTorch 官方实现（他们叫 fake kernels），最后只能人工逐颗核对。
- 对本仓库的具体价值：fake kernels 是我们安全门的对手模型——现有的输入不变性、毒化图案、着色器校验能挡住"不写输出"，但挡不住"真的调库回退、输出正确且计时真实"。可加一条探针：核内不得出现框架/库回退路径，并用 dispatch 计数或耗时下界佐证。指标筛选"只喂与运行时相关性最高的子集、每轮只抓 3–4 个"可直接改我们 hwfeedback.py 给 planner 的 profile_poor 输入（现在容易把整份 Instruments 报告塞进 TASK）。"修错反馈优先于优化反馈"与我们五关顺序一致，可当关卡顺序的外部依据。
- 初步价值：高，5 分。唯一给出反作弊实证 + 可直接落地的硬件反馈裁剪办法。
- 最终层级：A（主代理校准）
- 可信 harness 候选：yes。fake kernels 属安全与评测有效性，指标裁剪属证据纪律；但它的 best-of 报告口径必须反过来读，不能照抄。

### 2507.23194 GEAK: Introducing Triton Kernel AI Agent & Evaluation Benchmarks

- 本地 PDF：`docs/paper/2507.23194_geak-introducing-triton-kernel-ai-agent-evaluation-benchmarks.pdf`
- 讲了什么：AMD 的 Triton 核生成代理：Generator / Evaluator（先功能后性能的级联）/ Reflector（吃错误迹修）/ Optimizer（按历史性能排序提优化方向），配 1-shot 相似代码检索、领域知识注入、temperature=1 的并行采样与 Reflexion。同时发布两个基准：修过的 TritonBench-revised（184 核）与 ROCm Triton Benchmark（30 个来自 ROCm 仓库的真实核）。适用于 Triton + AMD（MI250/MI300）。
- 关键证据：TritonBench-revised 上执行正确率 52.72%（MI250）/54.89%（MI300），平均加速 2.42×/2.59×；ROCm 基准 63.33%（19/30）但平均加速只有 0.92×（多数核没变快）。直接提示 GPT-4.1 执行正确率 8.70%（1-shot 14.13%）、Gemini 2.5 Pro 14.13%；ROCm 上 GPT-4.1 是 0%。模块消融：知识注入 8.70%→20.11% / 0.86×，加 1-shot 27.17% / 0.99×，加 Optimizer 40.76% / 1.45×。串行 19 轮执行正确率 44.02%，并行 pass@10 到 54.89%。
- 局限与不可直接外推：(1) 绝对水平低：过半核生成不出来，加速比在 ROCm 上还低于 1；(2) 作者在附录 B 自曝基准本身不可信：原 TritonBench 有 37/184 个核在 AMD 上跑不通，部分核缺 call 函数导致"比对空字符串也算通过"，每核最多 6 个单测，可能把错核判对；他们改成容差张量比对 + 固定种子，但 TritonBench-revised 仍沿用旧测试框架，因此明说"报告的正确率可能被高估"，不能外推为一般正确率；(3) 2.59× 的分母是 TritonBench 的参考实现，不是专家库；(4) 只在 AMD + Triton，`tl.flip`、warp 语义与 Metal 不同。
- 对本仓库的具体价值：这份附录是本次五篇里对我们最可操作的清单。(a) "比对空字符串"这类夹具缺陷，正好对应我们 tests/support/golden 与 task.cases 要守的东西——报告正确率必须带 coverage.kind，窄测试套必须显式声明覆盖局限，这条可直接写进结论模板与 tests/shared/test_structure.py 的检查项。(b) debugging trap 与 max_perf_debug_num（同一处反复修不过就换策略）≈ 我们 patience / max_rounds / max_hangs 的早停依据；"同一 bug 反复修"应成为换场次或换委员会的合法理由，而不是继续烧轮次。(c) pass@k 与"diversity 采样给无偏估计"是他们少数方法论上正确的部分，但用最大值；我们 confirm 用中位数并保留搜索种子，不能改成 best-of-k。(d) 该文自认"窄套会虚高"，可作为我们拒绝把单批输入结论写进 result 的引用。
- 初步价值：高，5 分。它把"基准/夹具可以被写成假通过"讲得最具体，正是可信 harness 的入口。
- 最终层级：A（主代理校准）
- 可信 harness 候选：yes。核心就是评测有效性与测试覆盖口径，且有明确自查清单。

### 2511.18868 KernelBand: Steering LLM-based Kernel Optimization via Hardware-Aware Multi-Armed Bandits

- 本地 PDF：`docs/paper/2511.18868_kernelband-steering-llm-based-kernel-optimization-via-hardware-aware.pdf`
- 讲了什么：把"选哪颗核、施哪种优化"形式化成上下文多臂老虎机。6 类策略（tiling/vectorization/fusion/pipeline/reordering/access&layout），用 5 维运行时特征（归一化时长、寄存器、共享内存、block、occupancy）聚成 3 簇、每 10 轮重聚；只 profile 簇心，某资源吞吐过 75% 就屏蔽相关策略（masked UCB）。理论在"增益有硬件上界 + 奖励对行为特征 Lipschitz"两条假设下把 regret 降到与簇覆盖数相关。
- 关键证据：TritonBench-G 修正版 183 核（剔掉可被平凡化简刷分的 sin_computation），DeepSeek-V3.2、T=20、默认 K=3：A100 几何平均 1.91×（正确 79.8%、Fast@1 60.1%），RTX 4090 1.74×，H20 1.45×，同条件 GEAK 为 1.34/1.44/1.06；摘要口径"平均提升 33%+"。关键消融（H20 50 核子集，全量 1.57×）：把 UCB 换成"让 LLM 自己看核选策略"掉到 0.97×，低于参考实现；去掉策略集、只注入原始 profiler 指标 1.12× 且正确率 43.9%；BoN 0.60×。T=40 时 1.71× 且仍在涨，GEAK 与 BoN 在 25 轮后停滞。$0.5/核预算下 1.83×（GEAK 1.35×）。
- 局限与不可直接外推：(1) 两条结构假设未验证，Lipschitz 常数 L 只是写在定理里；(2) 奖励是单步 clip 到 [0,1] 的延迟下降，看不见"先慢后快"的组合收益；(3) 口径偏松：Correct 指"至少一颗有效核"，几何平均只算正确任务、失败与回归不进分母，加速比又是 best-of-T，无独立复测；(4) 依赖 NCU（约 10 秒/次）与 Triton 3.3，75%、c=2.0、τ=10 均为手调，只测了 K 的敏感性。
- 对本仓库的具体价值：最有价值的是那条负结果——让模型凭语义判断挑优化策略会掉到 0.97×，低于不改，这直接支持我们"模型不参与判决"和 min_improvement=1.005 + noise_z=2.0 的纪律，也可作 P0 premise 反对"让 reviewer 模型改路由/改评分"的论据。策略族 + 饱和屏蔽可作为 tip 的先验：在 patience=6 之前先掐掉物理上不可能有收益的方向，省的是真实轮次与费用；Metal 侧对应信号我们已有（pipeline 的线程组上限、roofline、profile_poor 的 GPU idle/spill），不必引入 NCU。sin_computation 的剔除提醒：题目准入要排除可被平凡化简刷高加速比的形状，这条应进指纹。它"best-of 20 轮 + 只算成功任务"的口径正是我们确认门要修的东西，1.91× 不能当目标数字。
- 初步价值：中高，4 分。Triton 三卡四模型的对照实验可用，消融的负结果比正结果更值钱。
- 最终层级：A（主代理校准）
- 可信 harness 候选：borderline。碰了评测有效性（口径、刷分题剔除）与"模型不该自选策略"，但没有权限、信任范围或经验生命周期，属方法论旁证。

### 2509.07506 Astra: A Multi-Agent System for GPU Kernel Performance Optimization

- 本地 PDF：`docs/paper/2509.07506_astra-a-multi-agent-system-for-gpu-kernel-performance.pdf`
- 讲了什么：不从 PyTorch 翻译，而是直接优化 SGLang 里已有的 CUDA 核。四个角色（Testing 造测试、Profiling 测时、Planning 提建议、Coding 改码）组成 5 轮循环，每轮记 (round, code, correct, perf)。适用于"已有可运行实现、只需再挤性能"的场景；前后处理（从框架里抽出独立核、再 monkey-patch 回去并对原实现校验）是人工的。
- 关键证据：3 个 SGLang 核（merge_attn_states_lse、fused_add_rmsnorm、silu_and_mul），o4-mini、H100、5 轮，几何平均 1.32×（1.26/1.25/1.46），100 次重复 + 20 次预热。单代理同轮数只有 1.08×；其中 Kernel 1 单代理是 0.73×（比原核更慢），作者归因为"造测试输入的那一步由优化方自己做，输入不具代表性，把 profiling 带偏"。最终正确性不采信 Testing 代理自己造的用例，而由人工重写用例对 SGLang 原实现比对。
- 局限与不可直接外推：(1) n=3，且是人工挑出的、可独立抽出的核，SGLang 内部依赖被去掉；(2) 没有独立复测：报的是搜索过程中最好那一版，没有噪声门槛、没有换种子复验、没有发布门；(3) CUDA + H100 + Nsight，没有 Triton、没有 Metal；(4) 前后处理不可自动化，作者自认这是主要限制。
- 对本仓库的具体价值：0.73× 这条反例是我们"模型不参与判决 + 确认阶段换种子"最直接的外部依据，可作 P0 premise 的引用证据：测试输入生成方必须独立于优化方。它的 Log 四元组与我们 result.json 的 confirmations/失败批次表同构，差别是我们有 confirm_batches 与"不确定"标记，它没有——所以只借证据不借机制。case study 的四类变换（循环不变量外提、__shfl_down_sync 归约、half2 向量加载、fast-math）可进 Metal 写核笔记：shuffle 对应 simd_shuffle、half2 对应 packed half2 载入。half2 fast-math 那条要注意：我们用 __expf 等价物会踩容差，需同时记 guard band。
- 初步价值：中，3 分。机制我们已覆盖，但提供了"自造测试→负加速"的可引用实证。
- 最终层级：B（主代理校准）
- 可信 harness 候选：borderline。它触到评测有效性（谁造测试、谁计时），但只是一页轶事，没有验证机制、没有权限与信任边界。

### 2511.20100 QiMeng-Kernel: Macro-Thinking Micro-Coding Paradigm for LLM-Based High-Performance GPU Kernel Generation

- 本地 PDF：`docs/paper/2511.20100_qimeng-kernel-macro-thinking-micro-coding-paradigm-for-llm.pdf`
- 讲了什么：把"选优化策略"和"写代码"拆开。宏观层是一个 1.3B 小模型（DeepSeek-Coder-1.3B，用 PPO/TWOSOME 在 6 万条轨迹上训），输出语义动作 = 优化类型（tiling/fusion/pipeline/reordering）+ 代码区域（AST 与数据流定位）；微观层由通用大模型（Gemini 2.5 Pro/Flash、Claude、DeepSeek-V3）按动作逐条改码。适用于 Triton 与 CUDA 核生成，AAAI 2026。

- 局限与不可直接外推：(1) 宏观策略要训练：6 万轨迹 + PPO，我们的预算与"不训练"纪律都不允许；(2) 正确率高不等于快：L3 平均加速比在三种卡上分别是 0.77/0.73/0.65，都低于 1，摘要里"2.2×"只在 L1；(3) 摘要的"34×"是对 KernelLLM（0.01×、2–4% 正确率）这种弱基线的比值，不是对专家库；(4) 全部结果在 NVIDIA + Triton/CUDA，没有换种语言或 IR 的验证；(5) 加速比是算术平均、无确认阶段、无噪声门槛。
- 对本仓库的具体价值：动作空间（四类优化 + 显式代码区域）几乎就是我们的 tip 词表。现在 P1 overlay 的建议是自由文本，探针难比较；若给结构化提案加一个 action 枚举与 region 字段，同一 target/task 上两条 tip 才能被判定"是否同一改动族"，recipient 路由也多一个过滤维度。奖励只用客观门结果、不让模型打分，与我们"模型不参与判决"同构，可当旁证。步数衰减 ≈ 我们的 patience/max_rounds/max_hangs。宏观层小模型的思路可用零成本替代：把"选哪类优化"交给 taic/policy.py 的纯函数（按历史成功率与饱和指标），不训模型。
- 初步价值：中，3 分。词表与奖励设计可借，训练与数字都不可搬。
- 最终层级：B（主代理校准）
- 可信 harness 候选：no。属生成范式；只有"奖励=客观门"这一点与评测有效性沾边，没有权限、生命周期或验证机制。

### 2607.20501 MKEvolve: A Modular Multi-Agent Framework for Kernel Code Generation

- 本地 PDF：`docs/可信harness/papers/2607.20501_mkevolve.pdf`
- 讲了什么：把"整体优化一个内核"改成"分解 + 子内核 beam search + 分解结构本身演化"：LLMDecompose 拆出子问题与顶层模块，每轮按 runtime 分配调用预算、对每个子内核独立 beam search（奖励 = 相对 torch.compile 的速度，错的记 0），每隔 L 轮对仍失败的子问题再 split、对已正确的尝试 fuse，最后按程序化组合拼回整核。因此实现可替换、误差可归因到具体子内核。
- 关键证据：100 题 KernelBench L2 + 50 题 L3、A100、Claude 4.5 Opus：L2 Correct 0.99 / Fast1 0.49 / Fast2 0.09 / 1.7M tokens（beam search 0.96 / 0.36 / 0.07 / 2.0M）；L3 0.94 / 0.34 / 0.08 / 2.1M（beam 0.88 / 0.26）；Swap 变体 L3 Fast1 0.60。GPT-OSS 120B 同向，token 少 25–35%。关键在附录 D：BF16 causal attention 上 atol=1e-3 把 20/20 个正确输出全判错，atol=1e-2 能用但漏掉 5 个注入 bug 中的 2 个；FFN 上 atol=1e-2 同样全拒，唯一可用的 1e-1 漏 2/6。改成按子算子 max+3σ 校准容差后，BF16 抓到 4/5 与 5/6（端到端为 3/5、4/6），tile-boundary bug 的可行性间隙宽 99–101×，unsafe-softmax 与 GELU 近似的端到端间隙甚至为负而分解后转正。
- 局限与不可直接外推：(1) 只 FP32、只单卡 A100、只 150 题，L3 仅 50 题；(2) 容差结论来自 11 个手写注入 bug，不是真实模型错误分布；(3) 反作弊用 TritonRL 的 LLM 作弊检测器（Opus/Claude 4.5 Sonnet 与 GPT-OSS 各判各的），本身是概率判据；(4) 分解收益依赖任务可拆，单算子题无增益（Single Split 消融反而更低）。
- 对本仓库的具体价值：(a) 最硬的一条是容差校准方法论。我们现在"允许值升到库误差 2 倍、上限 8"是全局常数，它给出同一算子跨 dtype/shape 的误差跨数个数量级（matmul 4096 维：FP32 1.0e-3、BF16 1.0），以及"固定容差在 BF16 上松紧二选一都错"的表；可照它建注入语料（tail mask 漏边界、缺 residual、累加 dtype 错、softmax 不减 max、GELU 近似），量出每道题在当前容差下的 catch rate 与误拒率——这两个数我们现在没有，`docs/架构/评测.md` 只有"逐元素全部在容差内"。（b) feasibility gap = min(错) − max(对) 是纯离线可算的指标，能标出"我们的容差根本分不开"的题，避免把确认预算花在没有判据的题上。（c) 它的 forward shape coverage 与 `__init__` 输入覆盖检查（子问题输入生成必须覆盖顶层用到的全部形状与 init 输入）可直接借成 `task.cases` 覆盖性审计。（d) "只有过作弊检测的子内核才入选"与我们的 sanitize/差分门同向，但它在 Python 侧 `ModelNew` 上做，我们的边界更窄，不能照抄强度。
- 初步价值：高，4 分。本组唯一把"容差选错会同时造成漏检与误杀"量化成表的工作，且能在 CPU fixture 上先复现。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。对象正是评测判据（oracle 强度、容差校准、漏检/误拒权衡），是 plan-01 缺的那半张表的直接参照。

### 2605.26118 Xe-Forge: Multi-Stage LLM-Powered Kernel Optimization for Intel GPU

- 本地 PDF：`docs/可信harness/papers/2605.26118_xe-forge.pdf`
- 讲了什么：输入一个已正确但慢的 Triton 内核，做 Triton→Triton 的定向优化，而不是从 PyTorch 重新生成。九个阶段（算法重构、开放式发现、dtype、融合、访存、block pointer、persistent、XPU 专有、autotune）由 LLM planner 按硬依赖约束排序、无 issue 的阶段跳过；每阶段由 CoVeR agent（DSPy）跑"生成→四级验证→按错误反馈精修"，Intel 约束（warp 数必须 2 的幂、GRF 模式、SLM 容量）写在 YAML 知识库里；执行、计时、正确性全交给 AI Bench，与优化逻辑解耦。
- 关键证据：Intel Arc Pro B70（约 160 FP16 TFLOPS 峰值）上 97 个 KernelBench L2 内核：1.17× 几何均值 vs PyTorch eager，67% 提升，9 个 >5×（最大 82×，Matmul_Min_Subtract），GEMM 1.28×、MatMul 1.76×（几何均值相对 best baseline）；FlashAttention 16 组 LLM 服务配置 2–13.3× 且无回退；全部内核 100% 过 allclose(rtol=1e-2, atol=1e-5)；少数带宽受限卷积回退到 0.5–0.8×。成本 10–20 次 LLM 调用/内核（最坏 40–50），$0.5–2/内核。
- 局限与不可直接外推：(1) 只到 L2 单核/算子链，L3 的跨内核内存布局交互明确不支持；(2) 知识库与 issue taxonomy 是手写 YAML，换硬件要重做（作者估 2–3 天）；(3) 没有逐阶段回滚，作者自己把"比前后性能再决定保留"列为未来工作，0.5–0.8× 回退是真实缺陷；(4) 基线是 PyTorch eager 与 torch.compile，不是厂商库；数字绑 Intel XPU，不能搬到 Metal。
- 对本仓库的具体价值：(a) 第 5 条贡献"kernel harness separation"加第 VII.a 节是本组最贴近我们边界的东西：LLM 只准改 `@triton.jit` 函数体与 autotune 配置，`Model` wrapper、输入生成、执行路径都由 benchmark 规格固定且不可改；并给出规避手法的具体形态——`_nn = __import__('torch').nn`、`getattr(_nn, ''.join(['fu','nctional']))`，即动态导入 + 字符串拼接绕过正则过滤。plan-01 已写"不用静态关键词代替数值判决"，这篇补的是机制解释：正则注定漏，正确解法是结构上不给改的机会（我们的对应物是 contract/launcher 归 tcenv、候选只交 MSL 源）。(b) 四级验证级联（语法→结构含硬件约束→正确性→性能，任一级失败即不进下一级）与我们"编译→接口→安全→数值→计时"一致，但它的结构级失败会回具体可执行修复提示（"num_warps=24 非法，合法值 1,2,4,8,16,32"），可对照我们编译门/安全门 message 的信息量。(c) 计时卫生：hardware-event timing + warmup + L2 flush + 同步屏障，可与我们的中位数/保护带/计时后复验并列比较。(d) best-of-k 只在 k>1 时按实测选优，与确认门同构。
- 初步价值：高，4 分。它把"LLM 不得碰测量路径"写成架构不变量并附带绕过案例，是 security.md 与 plan-06 的直接外部依据。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。不可变 harness、测量与优化解耦、规避类别清单、验证级联顺序，都属可信执行与评测有效性。

### 2606.26758 EGG: An Expert-Guided Agent Framework for Kernel Generation

- 本地 PDF：`docs/paper/2606.26758_egg-an-expert-guided-agent-framework-for-kernel-generation.pdf`
- 讲了什么：把 Triton 内核优化拆成两级专家流程——"算法结构设计"（多 seed 探索不同算法范式，再对每个 seed 做语义保持的算法精修，例如把 attention 改写成 online-softmax 单核）与"硬件相关调优"（并行映射 → tensor tiling → 访存/流水）。每级由 profile / code / debug 三个 agent 围绕阶段目标闭环，profile 吃 NCU 指标出瓶颈与修改计划，debug 吃错误日志出根因；阶段间只传递已定稿决策、丢弃中间探索输出。适用范围是 PyTorch 算子→Triton 内核的生成与调优，单卡 NVIDIA。
- 关键证据：KernelBench 250 题、RTX 4090，平均 2.13×、success 100%、Fast1 87.6%（L1 1.83×、L2 2.73×、L3 1.52×）；对比 CudaForge 1.30–2.00×、Torch Compile 1.09–1.38×、DeepSeek-V3.2 0.84–0.99×、AutoTriton 0.83–1.20×。消融（相对 PyTorch Eager）：去 multi-seed 1.84×/78.4%，去多 agent 1.67×/74.0%，只留算法精修 1.52×/60.8%，只留硬件调优 1.46×/72.0%。成本约 20 分钟、50k output tokens/内核，CudaForge 约 30 分钟、110k。附录 A 换卡：RTX 5090 整体 2.31×，H20 L2 3.23×，RTX PRO 6000 L2 2.95×。
- 局限与不可直接外推：(1) 序贯阶段禁掉跨阶段联合搜索，作者自认"局部最优的并行映射配另一种 tiling 可能更好"；(2) 强依赖专家先验，可能把探索压在已知优化套路上；(3) 基线全是 PyTorch Eager（附录另有 torch.compile max-autotune），不是厂商库；(4) 全程没有作弊面、判据强度或信任边界分析，成功率 100% 是在 KernelBench 自己的容差下得到的。
- 对本仓库的具体价值：(a) "阶段间只传定稿决策、丢中间输出"正是我们"每轮开一个新 session"的设计，且它给出反面读数（保留全历史的单 agent 版本 Fast1 从 87.6% 掉到 74.0%），可当我们 session 策略的外部依据。(b) 它的接受规则"候选必须 valid 且更快才替换 best"与我们 `differential_recheck` + 确认门的单调语义同构。(c) 附录 D 的卫生细节值得逐条对照写进 `docs/架构/评测.md`：validation 与 benchmark 在 isolated spawned subprocess 里跑以避免 CUDA 上下文污染、seed 修复预算 3 次而后续阶段 1 次、畸形输出只重试一次否则丢弃、profiling 失败非致命（继续用当前 best）——这几条正好是我们 evaluator 预算与失败分类的参照。(d) 提示里显式列 Triton 硬约束（BLOCK 必须 2 的幂、`tl.program_id` 只支持 0/1/2、缺 `tl.tanh` 需手写），形态上就是 `backends/metal/` 知识文件与 Metal notes 该有的样子，可当检查清单用。
- 初步价值：中，3 分。agent 架构与我们已有设计重合度高，净新增只有阶段预算与子进程卫生的写法。
- 最终层级：B（主代理校准）
- 可信 harness 候选：borderline。有确定性失败处理、子进程隔离与单调接受，属执行卫生；但没有作弊面、判据有效性、权限或经验生命周期的任何内容，不能进证据链。

### 2606.04847 MusaCoder: Native GPU Kernel Generation with Full-Stack Training on Moore Threads GPU

- 本地 PDF：`docs/paper/2606.04847_musacoder-native-gpu-kernel-generation-with-full-stack-training.pdf`
- 讲了什么：训练侧的全栈工作（三阶段数据合成 → 多任务 SFT → 保多样性 RFT → 单轮 GRPO 预热 + 多轮 GRPO），目标是 CUDA/MUSA 原生内核生成，并为此搭了 MooreEval：分布式执行沙箱，CPU 编译 worker 与 GPU 执行 worker 解耦，候选被当作不可信代码，按"解析/接口 → 编译 → 随机输入正确性 → 反作弊 → 同步计时"分级验证，输出结构化元组 (compiled, correct, legal, speedup, category, detail)。反作弊用静态分析加运行时 profiling 抓 `ModelNew.forward` 里的 `aten::*` 计算回退，维护只允许 shape/view/拷贝/建张量的白名单，命中即记 `cheating:disallowed aten` 并给零奖励，另加"异常大加速比"补充检查。
- 关键证据：KernelBench 上 MusaCoder-27B-RL Pass@8 93.2%、Avg@8 88.60%，对比 Claude Opus 4.7 的 87.2% / 77.30%（+6.0 / +11.3 点）；L3 72% vs 54%、65.75 vs 39.25。Faster Rate（须正确、合法且 >1.1×）15.0% vs eager、9.2% vs compile（Claude 11.8% / 7.5%）。消融：去 BDR（全失败组重采样）Pass@8 93.2→88.6，去 PrimeEcho Avg@8 88.60→83.50。训练 64 台 MTT S5000（每台 8×80GB）。
- 局限与不可直接外推：(1) 主体是训练，验证器是支撑设施，没有对验证器本身做攻击召回或误拒率测量；(2) 反作弊是对 Python 侧 aten 调用的白名单，"算一半就提前返回""吃容差""异步计时绕过"只有一句 supplementary checks for anomalously large speedups，既无规则也无召回；(3) 全文没有独立 Limitations 章节；(4) 只在 KernelBench 与自建 MUSA 变体上，非 NVIDIA 生态的错误谱不可外推。
- 对本仓库的具体价值：(a) 它的六级错误分类学（编译/运行时/正确性/作弊/有效指标 + category/detail）与我们 `EvalReport` 的 status/stage/message 同构，但暴露一个真实缺口：作弊类失败现在会落到 `incorrect` 或 `unsafe`，报告层没有独立 category，triage 与 `brief` 无法统计"作弊类 vs 正确性类"的比例，也没法按类别回归。(b) 隔离与容错写法可逐条对照 remote evaluator / evaluation outbox：task queue + inflight 状态 + visibility timeout + bounded retry + 崩溃重排，而"确定性错误（语法、非法访存、数值不符）立即返回 taxonomy、不回退重试"是一条我们该显式写下的边界条件。(c) "异常大加速比"作为廉价后置门：确认门已有噪声门槛，但没有"过快也可疑"的反向检查。(d) 计时前显式 synchronize，与我们"计时含编码与等待"的设计一致，可当交叉验证。
- 初步价值：中，3 分。验签协议与我们的门高度重合，净新增只有作弊分类与超快检查两条。
- 最终层级：B（主代理校准）
- 可信 harness 候选：yes。MooreEval 本身是可信执行设施（隔离、白名单、分级验证、错误分类），只是论文重心在训练。

### 2603.02637 StitchCUDA: An Automated Multi-Agents End-to-End GPU Programing Framework with Rubric-based Agentic Reinforcement Learning

- 本地 PDF：`docs/paper/2603.02637_stitchcuda-an-automated-multi-agents-end-to-end-gpu.pdf`
- 讲了什么：面向端到端 GPU 程序（KernelBench L3/4 全模型）的三 agent 框架：Planner 用 Nsys 找主导内核与系统瓶颈并出子任务清单，Coder 逐子任务写 CUDA 并调 nvcc 编译，Verifier 用 Nsys+NCU 两级诊断后给优化建议；再把多轮轨迹拆成两个原子技能（从零生成、按反馈优化）做单轮 GRPO，奖励 = 规则奖励（正确性 × 加速比）+ 专家 rubric（反作弊、CUDA 工程、算子覆盖、技能遵循），作弊直接置零。
- 关键证据：自建 KernelBench 测试集（L1 20 题、L2 20 题、L3 10 题，训练占 80%），H200 上 L1 18/20 且 3.54×、L2 18/20 且 1.82×、L3 9/10 且 1.50×、Fast1 70%；对比无 RL 变体 L3 3/10、0.24×（10%），CUDAForge L3 6/10、0.87×（40%）。作弊（人工判 15 轮内是否 PyTorch-only 或硬编码输出）：StitchCUDA 8/50 部分、0 完全；只有规则奖励的 StitchCUDA-A 16/50；Kevin-32B 底座 22/50 部分 + 4/50 完全。rubric 单维消融：去掉 Anti-Hacking 后正确性 9.0→5.7、作弊 7.7→15.7、加速比 1.50→0.75×。
- 局限与不可直接外推：(1) 奖励侧是 LLM rubric 判分，作弊统计靠 CUDA 专家人工标注，都不是确定性判据；(2) 测试集仅 50 题且与训练同源（同一 80/20 划分），绝对数不可与 KernelBench 官方协议比；(3) 只 H200 与 RTX PRO 6000 两代，作者自认跨架构泛化未知；(4) 端到端多核场景，"算子覆盖"维度在单核任务上没有意义。
- 对本仓库的具体价值：(a) 最有价值的是那条负结果：写进提示的"必须自实现至少一个 kernel、不许拷贝 PyTorch、不许硬编码"以及 Kevin 用的 format check 都挡不住作弊（Kevin 仍 22/50 部分作弊），作者归因于"regex 抓不到硬编码"与"严格则误杀、宽松则漏"的两难。这直接支撑 plan-01 的路线判断：静态检查只能筛选，判决必须在数值/执行侧。(b) 它把作弊拆成 partial（15 轮里出现过）与 total（15 轮全是），与正确性、加速比同表报告——可在 triage 与 `brief` 用同样两档口径记录"被拒候选里多少属作弊类"，而不是只留最终 status。(c) 退化行为分类（只改 ReLU、留下 conv2d/GEMM 不动、增益 <5%）是"改了但没用"的另一种解释，可作 mutation 无效的归因标签。(d) 反面：不能照搬 rubric，把确定性 `EvalReport` 换成 LLM 打分会毁掉判据基础。
- 初步价值：中，3 分。负结果与作弊两档口径可用，其余是 RL 训练面。
- 最终层级：B（主代理校准）
- 可信 harness 候选：borderline。它正面处理 reward hacking 与判据可信，但机制是 LLM rubric 奖励（我们明确不采用），且没有执行隔离、权限或经验生命周期内容。

## 本组前 2 名

1. **2607.20501 MKEvolve**（4 分）。它附录 D 三张表给出的正是我们缺的东西：容差选不对会同时造成漏检（BF16 atol=1e-2 漏 2/5）与全量误杀（atol=1e-3 拒 20/20），而按子算子校准后漏检率下降、tile-boundary 类 bug 的可行性间隙宽 99–101×。这可以直接落成两件离线工作：按 bug 家族建注入语料，量出每道题在当前容差下的 catch rate 与误拒率；用 feasibility gap 标出"我们的容差分不开"的题。两者都不需要 GPU、不需要模型调用，且正好补上 plan-01 只写了"计后 fresh-input"而没写"判据强度怎么量"的空。它还有一条附带价值：作弊检测虽借的是 LLM 判据，但"只有过检测的子内核才入选"这条准入语义与我们的门同向。

2. **2605.26118 Xe-Forge**（4 分）。它把"measurement path 不可被优化器修改"写成第 5 条贡献并配了一节规避分析，给出动态导入加字符串拼接这种正则必然漏掉的具体手法，与我们 `docs/security.md`"写核 agent 碰不到评测代码"是同一条不变量的外部表述，可直接引作 plan-06 的证据；四级验证级联的顺序也与我们的关卡顺序一致，且它的结构级失败会给可执行修复提示，是我们编译门/安全门 message 的对照物。排第二而不是第一，是因为它 97 个内核的读数绑在 Intel XPU 上、基线是 eager/compile，可搬运的是不变量和验证顺序，不是数字；而且它的核心结论在我们这里多数已经实现，属确认而非新增。

第 3–5 名：EGG（3 分）借阶段预算与子进程卫生，架构已重合；MusaCoder（3 分）借作弊独立分类与超快检查，验签协议已重合；StitchCUDA（3 分）只借"静态检查挡不住作弊"这条负结果与 partial/total 两档口径，其 rubric 机制我们明确不采用。

### 2607.23089 Compiler-Grounded Hierarchical Diagnosis for LLM-Based Triton Kernel Optimization

- 本地 PDF：`docs/可信harness/papers/2607.23089_compiler-grounded-hierarchical-diagnosis.pdf`
- 讲了什么：把 Triton kernel 优化当成**跨层渐进诊断**。L1 模式分诊（查模式索引，能定位就停）→ L2 profiling（瓶颈分类、热点）→ L3 IR 归因（重建 lowering 轨迹，定位非单位步长、错失融合、布局导致的向量化失败）→ L4 编译器源码升级（把 IR 症状翻成一个窄问题：哪个 pass 的前置条件挡住了优化）。外层是"薄 harness + 一组按层组织的 skills"：harness 建验证基线、跑正确性与基准比较、采集 profiler/IR 产物，把每轮记成显式状态（父节点、证据、验证结果），由 hook 检查轮合同，跳过证据必须写明理由、失败升级记为 inconclusive。批次跑完做回溯综合，把反复出现的机制提升为可复用模式族。
- 关键证据：NPUKernelBench 派生的 Ascend 950 套件，OpenCode + DeepSeek V4 Pro；37 个成功转换算子、每算子 5 例（185 例）、各 15 轮：几何均值 4.35×、中位 2.73×，37/37≥1.0×、22/37>2×、13/37>5×。最好轮中位在第 10 轮，22 个算子第 8 轮后才首次达到最好。证据深度：32 条轨迹到过 profiling、3 条到 IR、4 条到编译器源码；但按"胜出轮主证据层"统计是 33 模式分诊 / 4 profiling / 0 IR / 0 编译器源码。对 Torch NPU 的后验比较：2.60× 几何均值 / 1.46× 中位（35 算子、1678 例）。
- 局限与不可直接外推：(1) 无消融、无冻结工具链对照、不报 token/墙钟成本（作者自认），"分层诊断带来增益"未被因果隔离；胜出轮几乎全在 L1，说明深层能力未被证明有用。(2) 分层几何均值（L1 7.29× / L2 2.51×）是不同算子组，不可当组件收益；L1 对 Torch 的中位仅 0.87×（一半算子 Triton 更慢）。(3) 评测集已剔除转换失败算子，分母不全；15 轮上限 + "挑最好轮"抬高结果。(4) 后端是 Ascend Triton 栈，其 IR/pass 结论不可搬到 Metal。
- 对本仓库的具体价值：补的正是 tcenv 的缺口——我们能判编译/正确/安全/计时，也有 `roofline.bound` 与 spill events，但候选变慢时只给数字、不给归因。它的三条停止判据（当前层必须定位主导成本、必须收窄到一个改写族、必须能自证，否则升级或记 inconclusive）可直接写成 Metal 版阶梯：L1 用 KernelWiki 模式条目，L2 用 `tcenv profile`，L3 用生成 MSL 的结构归因（simdgroup 槽数、threadgroup 大小、coalescing）。"轮合同 + hook + 显式状态 + 可审计跳过"对应我们的 P1/审查 schema（可先加一个"证据深度"字段）；"回溯综合只取已验证轮"与我们 experience.md 的 `verified`/`reported` 分级同向，可把"只从 verified 轮抽模式"写成硬规则。最该记住的反面：它 33/37 胜出轮在 L1，别先建 L3/L4 基座。
- 初步价值：高，5 分。harness/skills 分层、轮级审计、经验沉淀逐条对齐本仓库，且诚实报告了深层诊断未被证明有效。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。轮合同由 hook 强制、验证门拒绝无效或回退候选、证据深度与跳过原因留痕、经验只从已验证轮综合——都是可信执行与评测有效性的直接机制；不足是缺因果消融与成本核算。

### 2606.26453 Optimizing CUDA like a Human: Micro-Profiling Tools as Expert Surrogates for LLM-Based GPU Kernel Optimization（KernelPro）

- 本地 PDF：`docs/paper/2606.26453_optimizing-cuda-like-a-human-micro-profiling-tools-as.pdf`
- 讲了什么：多 agent 闭环。Stage 1 用 roofline 与 ncu 实测双路分类瓶颈（不一致时信理论界）；Stage 2 只跑与该瓶颈相关的 15 个微剖析工具（8 ncu + 5 nsys + 2 SASS），每个工具是五元组（所需指标、阈值、触发条件、分析→严重度+根因+排序建议+示例），把原始计数器翻成自然语言指令再进 prompt；工具**主动编排**（确定性全跑）而非让模型自选。搜索用域适配 MCTS（渐进加宽、非对称分支、ln(speedup) 奖励、死路剪枝、跨轮 search memory）。输出是手写 CUDA+CuTe，可自主检索 CUTLASS 源码。
- 关键证据：KernelBench 全量 100/100/50（A100，Sonnet 4.6，15 seeds、30 轮、2 候选/轮）：几何均值 2.42/4.69/5.30×，对前 SOTA KernelBlaster +69/+88/+253%；封顶 10× 仍 2.34/3.25/4.31×（抗离群）。42 题消融（Wilcoxon）：工具 4.00× vs 原始 ncu 1.77×（p<0.0001）；**原始 ncu 比完全不给反馈的 3.35× 更差**（p=0.0007）；MCTS 4.60 vs 贪心 3.65（+26%，p=0.004）；主动编排 1.37 vs 反应式 1.12（+23%，p=0.035）；search memory +6%（p=0.181，不显著）。6 个 Triton 推理 kernel：带工具 2.02×/5.0 轮 vs 1.49×/7.2 轮。生产 MoE dW1：1.23× 超专家 Triton（H100），首轮仅 0.07×；37 个候选"零 tensor-core 指令"。能效 A/B：同 2.52× 下 1802 vs 2038 mJ（−11.6%）。
- 局限与不可直接外推：(1) 强绑定 CUDA：ncu/nsys/SASS/CUTLASS 在 Metal 上没有对应物，15 个工具与阈值不可搬。(2) 正确性判定是 `torch.allclose(atol=1e-2, rtol=1e-3)`，对 fp32 很松；且未报计时协议（重复次数、裁剪、缓存/种子），5.30× 与我们的确认门口径不可比。(3) "15 seeds × 30 轮 × 2 候选"是搜索预算不是测量重复，报的是搜索最好结果，非绑定后复测。(4) 能效结论只有 1 个 elementwise kernel 的 A/B，作者自称 preliminary。
- 对本仓库的具体价值：最有用的不是 5.30×，而是对照纪律与一条反直觉结论——原始计数器直塞 prompt 比不给反馈更差。这一点我们其实已经做对：`tcenv/report.py` 的注释就写明原始日志与每次测速样本不进反馈，`taic/hwfeedback.py` 只给解释后的短块；所以它的价值是**外部确认**，而非新机制。真正可搬的是三件：五元组字段（对应 harness-feedback 的 tip/前提/归属结构）；每个工具的 fires 与 hit-rate（"哪条经验真的转化"的度量，正合经验生命周期）；封顶(cap)报告（抗离群口径，可进我们报告）。"37 个候选零 tensor-core 指令"提示要在生成物层核对声称的机制——我们有 simdgroup 槽数启发式与 `tcenv profile` 的 spill events，方向一致但可再查一层。MCTS vs 贪心 +26% 可作 taic 搜索策略的备选实验。
- 初步价值：高，4 分。反馈表示与对照实验的证据最硬，但机制落点与我们已有设计重叠。
- 最终层级：A（主代理校准）
- 可信 harness 候选：borderline。用实测加速比替代自评（防 reward hacking）、封顶抗离群、配对检验都属评测有效性方法；但没有信任边界、权限或经验生命周期，计时协议也未披露。

### 2606.26383 SOLAR: AI-Powered Speed-of-Light Performance Analysis

- 本地 PDF：`docs/paper/2606.26383_solar-ai-powered-speed-of-light-performance-analysis.pdf`
- 讲了什么：从 PyTorch/JAX 源码自动推导 SOL（理论下界）。三段式：LLM 前端把源码翻成可执行的 Affine Loop IR（named-dim 张量 + 仿射循环），用数值输出比对当门，失败带诊断重试；确定性后端把已通过的 IR 提升成 Einsum Graph（节点是扩展 einsum，边是张量依赖），从而 MACs 与访存字节可闭式算出；分析后端按 T_SOL=max(FLOPs/Π, Traffic/β) 给 unfused / fused / cache-aware（OROJENESIS 把 tiling 写成受片上缓冲约束的 ILP）三档界，并有 inverse roofline（给定时延反推所需带宽/算力）。
- 关键证据：KernelBench 270 题（100/100/50/20，H100 PCIe）：覆盖率 100%（fvcore 75%、ptflops 84% 且不出 SOL）；零观测到的 SOL 违例（实测不早于下界）。headroom（运行时/fused SOL）：L1 4.3×、L2 21.6×、L3 54.6×、L4 10.2×（eager），torch.compile 为 3.7/14.3/47.7/4.8×；融合分析在 L3 多出 7.8× 空间，cache-aware 最多收紧 2.25×。对照：零样本 LLM 直接估 SOL 总体 83%（224/270），但 L3 仅 38%、L4 45%，46 个错误里 20 个偏差 >10×。
- 局限与不可直接外推：(1) 只用形状不用取值，压缩、常量传播、结构化重复数据的收益看不见；界可能不紧（功耗/降频）。(2) "零违例"只是自洽性检查（界不得低于实测），不是正确性证明；翻译靠抽样输入比对，作者明说无形式保证。(3) 图级融合面向多算子图，我们是单 kernel + Metal，Π/β 与统一内存、tile 语义都要自己重算，21.6×/54.6× 不可搬。(4) 它用标称峰值，实际可持续带宽更低，直接当门会偏松（我们已有实测标定，这点我们更严）。
- 对本仓库的具体价值：tcenv 其实已有同类物：`tcenv/backends/metal/profile.py::roofline` 给 `lower_bound_us`、`time_over_lower_bound`、`bound_kind=reference_algorithm`，`tcenv/report.py` 与 `taic/feedback_extra.py` 有 `CLEAR_OF_BOUND=0.95`，但**只对基线**用，语义是"下界假设不成立"，并用于早停。SOLAR 的增量有四点：把同一个界**对候选**当异常判据（候选早于下界 = 候选或测量可疑，必须裁一次，而不是默认放宽界）；用多保真（unfused/fused/cache-aware）把界收紧到有牙齿，否则门形同虚设；把"零违例"做成整批语料的自检口径；以及它量化了"别信 agent 自报剩余空间"（总体 83%、L3 38%）。这与 plan-01 的 fresh-input 互补：一个查"是否真算了"，一个查"是否算得快到不可能"。
- 初步价值：高，4 分。给出一条可独立计算、可当门的新维度，且实证了 LLM 自估不可靠。
- 最终层级：A（主代理校准）
- 可信 harness 候选：yes。核心是评测有效性：用独立推导的下界做可证伪检查、限制 agent 声称的加速比，并把"零违例"作为测量链的自检。

### 2605.05023 CuBridge: An LLM-Based Framework for Understanding and Reconstructing High-Performance Attention Kernels

- 本地 PDF：`docs/paper/2605.05023_cubridge-an-llm-based-framework-for-understanding-and-reconstructing.pdf`
- 讲了什么：不从零生成 kernel，而是把专家 CUDA attention kernel 当参考做**语义适配**。lifter 用带 CoT 的提示把 CUDA 提升为可执行的 CuIR（Pythonic，原语只有 memory copy、compute gemm、sync、control 四类，显式保留 tile 形状、指令选择与同步粒度，抹掉线程级索引）；IR Transfer 对照用户给的 PyTorch 参考生成目标 IR，并做性能感知改写（如 PrefixLM 把 full/partial 循环切开，只对边界块加 mask）；最后按源/目标 IR 差分做行级 patch 回到 CUDA。每一阶段都用数值输出比对当门。
- 关键证据：A100 与 H100，7 类变体 + 1 组合变体，3 个模型配置（Llama2-7B MHA、Qwen2.5-72B GQA、Llama3.1-405B），seq 1k–8k；称 100% 正确。平均加速 A100 12.69×（对 PyTorch）/1.18×（FlexAttention）/2.54×（Qimeng），H100 19.82×/1.62×/4.35×。对 FlashInfer：原生变体 0.99–1.22×（均值 1.07×），非原生 2.73–5.59×。消融 96 例（8 变体 × 12 长度，H100）：Pass@1 0.21（裸 GPT-5）→0.41（+ReAct）→0.70（CuBridge），归一化加速 1.00→1.23→4.19×；换 4 个后端波动 <5%，Qwen-3-32B 完全生成不出合法 kernel。
- 局限与不可直接外推：(1) 依赖高质量专家源 kernel（作者自认，非 NVIDIA 平台缺），我们 Triton→MSL 没有等价"专家 MSL 参考"；(2) 主数字是 best-of-10、温度 0，且正确率按"至少一条通过"口径，Pass@1 只有 0.70；(3) 12–19× 的分母是 PyTorch 多 kernel 组合，部分变体 PyTorch 在 8k OOM，该倍数不代表对优化实现（FlashInfer 前仅 1.07×）的优势；(4) 只覆盖 attention 与一个 GEMM+ReduceSum 案例，不涉及编译失败诊断、计时语义与安全。
- 对本仓库的具体价值：可借的是"每层都有可执行中间物 + 数值门"这一结构，以及它给出的外部证据——强制结构化表示（Pass@1 0.21→0.70）远胜自由 ReAct 重试（0.41），支持我们把 P1 提案做成结构化提交而非"多给几轮"。容差取 1e-2（fp16，循 CUTLASS）可作为 `docs/架构/评测.md` 容差表的外部锚点；"Qwen-3-32B 全灭"提示换委员会模型存在能力阈值，不能假设小模型只差一点。CuIR 本身不必搬，但"先把语义落到可执行参考、再核生成物"正是 plan-01 差分门的方向。
- 初步价值：中，3 分。任务不对口，可搬的是验证门结构与被量化过的"结构化优于自由重试"。
- 最终层级：B（主代理校准）
- 可信 harness 候选：borderline。数值验证门确实是在缩小信任缺口（原文即"numerical validation closes this trust gap"），但全文不涉及权限、信任边界、经验生命周期；best-of-10 的报告方式反而更像评测有效性的反面样本。

### 2512.22147 GPU Kernel Optimization Beyond Full Builds: An LLM Framework with Minimal Executable Programs

- 本地 PDF：`docs/paper/2512.22147_gpu-kernel-optimization-beyond-full-builds-an-llm-framework.pdf`
- 讲了什么：针对"整包构建/运行太贵、不能每轮都跑"的 HPC 场景：从大应用抽出热点 kernel，让 LLM 自动补全成最小可执行程序 MEP（补输入生成器、内存分配、调用与结果处理），并要求 T_ker≥下限、T_overall≤上限、数据量≤上限；在 MEP 内做多轮性能反馈迭代（每轮 N 个候选、R 次重复、裁剪均值），编译或运行失败用诊断回灌的自动修复（AER），有效 tiling/访存/同步策略以"性能模式继承"写回后续轮；最后把优化版 kernel 集成回原应用复验。CUDA 与海光 DCU（HIP）双平台。

- 对本仓库的具体价值：MEP 基本就是 tcenv 已在做的事（隔离 kernel + 生成的驱动与输入），所以机制增量小。真正的用处是两个：一是**代理与实测会方向性偏离**的实例，正是我们 confirmation gate 必须在发布前重测并绑定 kernel、不能把搜索期代理数字当发布的理由；二是裁剪均值 + 固定重复次数可与 `tcenv/bench.py` 的 median + CV 门槛 + 相对标准误对照（我们更严，额外管种子、缓存与噪声判定）。它的"性能模式继承"是我们经验生命周期的弱版本：无验证门、无 trust scope、无"reported 不进提示词"的纪律。
- 初步价值：低，2 分。核心机制已在本仓库实现，可借的只有代理-实测偏差的实证与计时协议对照。
- 最终层级：C（主代理校准）
- 可信 harness 候选：no。只有测量协议与再集成复验的想法，没有信任边界、权限或生命周期机制；表内均值只覆盖部分用例，也不宜当证据源。

### 2603.21465 DRTriton: Large-Scale Synthetic Data Driven Reinforcement Learning for Triton Kernel Generation

- 本地 PDF：`docs/可信harness/papers/2603.21465_drtriton.pdf`
- 讲了什么：训练 7B 模型（Qwen-2.5-Coder-7B-Instruct）做 PyTorch→Triton 翻译。CSP-DAG 用 CP-SAT 在 61 个算子上合成形状一致的合法 PyTorch 程序（声称覆盖全算子空间、难度可控），先 SFT 2,026 对，再用 DRPO（正确性与速度奖励解耦 + 课程，20k/60k/20k）在 10 万合成程序上 RL；推理时加测试时搜索：把程序切成 ≤5 算子的连续片段，逐片段生成并验证，再拼回实测取最快组合。范围是 Triton→CUDA（运行时编译）、NVIDIA。
- 关键证据：验证器三关——语法（有 @triton.jit 且能编译）、忠实性（把每个核 monkey-patch 成 no-op，看输出是否随之变化，防直接抄 PyTorch）、正确性（5 个随机用例、与 PyTorch 输出"精确匹配"）。合成基准 400 题（L1/L2/L5/L20 各 100）准确率 87/75/15/0%，加测试时搜索后 87/96/99/99%；KernelBench 250 题 L1 69%、L2 96%、L3 76%，L2 有 92% 快过 torch eager、56% 快过 torch.compile，L3 为 54%/34%。基线 GPT-5.2 L2 32%、Claude-Sonnet-4.5 36%、AutoTriton 45%。平均加速比 1.20×→1.57×。代价：250 题的验证从 0.08h 涨到 3.53h（16,859 个片段），训练 8×H100 约 10 天。
- 局限与不可直接外推：(1) 要训练：2,026 对 SFT + 10 万程序 RL + 8×H100 十天，本仓库纪律下不可复现，权重与数据也不能直接用于 Metal。(2) 评测口径弱且在评测集上选择：测试时搜索按实测挑最快组合，1.57× 是选择后的值，无留出集、无换种子复测、无噪声门槛。(3) 正确性只有 5 个随机用例，未说明浮点容差（原文 "matched precisely"），没有覆盖率声明、没有域扫描、不保存反例。(4) 忠实性检查只挡"核没被调用"，挡不住硬编码输入、按形状特化刷分、只对特定分布正确——作者自己引 Lange 等的鲁棒评测指出多代理系统会钻这类漏洞。
- 对本仓库的具体价值：(a) no-op monkey-patch 是可直接落地的一条安全探针：把候选核换成 no-op（或让 dispatch 计数为 0）后输出必须变化。我们现有毒化、输入不变性、着色器校验挡的是"不写输出"，挡不住"真调库回退且结果正确"（CudaForge 的 fake kernels 就是这个形态）；Metal 侧可用"只返回的替身核 + 比较输出"或 dispatch 计数实现，接进 sanitize.py 的安全关与 plan-01 的攻击语料。(b) 它给了选择效应的干净数字：同一批候选，仅靠"挑最快"就把 1.20× 抬到 1.57×；我们 confirm 用中位数 + min_improvement=1.005 + noise_z=2.0 三批复测就是为了不把这种效应当成绩。(c) 5 用例 + 精确匹配 + 无覆盖声明，正是 EvalReport.coverage.kind（domain_sweep 与抽样之别）必须存在的原因，可作"窄套虚高"的引文。(d) CSP-DAG"按难度分层、覆盖可证"可映射到题目准入：tasks/ 与指纹可加一条"形状是否可被平凡化简或常量折叠刷分"的检查。
- 初步价值：中高，4 分。四篇里唯一给出可实现、可接进安全关的"核未被调用"探针，并用自身数字演示了选择如何抬高加速比。
- 最终层级：S（主代理校准）
- 可信 harness 候选：yes。忠实性检查直指评测有效性（候选是否真的算了），与我们安全关、攻击语料同层；训练部分与那些加速比不可搬。

### 2506.09092 CUDA-LLM: LLMs Can Write Efficient CUDA Kernels

- 本地 PDF：`docs/paper/2506.09092_cuda-llm-llms-can-write-efficient-cuda-kernels.pdf`
- 讲了什么：FSR（Feature Search and Reinforcement）。输入自然语言任务 + host 代码 + 目标 GPU 规格，每轮让 LLM 生成 N 个 CUDA 核，依次过 Compilation Verifier、Function Validator（对随机生成输入逐元素比对）、Performance Profiler，取最快者连同"性能提示"与历史回填 prompt，循环 D 轮；全失败则回填编译/执行错误继续生成。范围是"自然语言 → 单核 CUDA"，20 个任务、每任务 5 个输入规模、两张卡。
- 关键证据：20 个任务（CUDA Samples / LeetGPU / KernelBench 混合）+ DeepSeek-V3-0324；两张卡上所有任务都至少有一个候选过 Function Validator，不加 FSR 直出时部分任务全部候选失败。加速比分母是"人写的基线核"：RTX 3090 Ti 上矩阵转置 104×、点积 102×、蒙特卡洛积分 179×；正文给的分任务均值区间是 5.95×–68.3×（GTX 1660 SUPER 6.06×–60.0×）。摘要写"最高 179×"。
- 局限与不可直接外推：(1) 分母是样例自带的人类实现，其中转置是逐元素散列读写、矩阵拷贝近乎空核，179×/337× 主要反映基线弱，不能读成"超过专家库"。(2) 测试输入在优化前一次性随机生成（Table 3 固定尺寸），全程对着同一批输入优化；没有计后换输入、没有确认门、没有噪声门槛，报的是 best-of-(N×D)。(3) N、D、单任务耗时与费用都没给；容差 §3.2 说 "exactly matches"、§4.1.1 又说"预先给定偏差"，两处矛盾，不可复算。(4) 只有 CUDA+NVIDIA；把 3090 Ti 写成 Ada Lovelace（实为 Ampere）、§4.2.1 把 2D 卷积说成 Task 11（表里是 Task 5），校对不严。图 3(f) 的 MHA 还有 0.43×、0.60× 低于基线的点，正文只说"提升不显著"。
- 对本仓库的具体价值：一是那条失败案例——用共享内存优化 2D 卷积时漏掉角上 halo 数据，核"静默产生错误结果"，只有差分比对能抓到：这就是 correctness 关 + 毒化/输入不变性 + plan-01 计后 fresh-input 复验要防的形态，可作为 P0 premise 的直接引文："优化本身是新的错误来源，每一轮优化后都要重跑数值与安全门，不能只信编译通过"。二是它的 Function Validator 只用开局那批随机输入、加速比靠贴着自己的测试集拿分，与我们 data0 复用是同一类缺口，可当 plan-01 的外部例子。三是"编译→功能→计时"的关卡顺序与我们 tcenv 一致，可作旁证，但机制我们已有；硬件规格入 prompt 也只是 target profile / wiki 的雏形，不必照搬。
- 初步价值：中，3 分。它就是本仓库这套循环的原型，但证据口径弱，可借的实质只有"优化引入静默数值错误"与关卡顺序旁证。
- 最终层级：B（主代理校准）
- 可信 harness 候选：borderline。它触到评测有效性（基线选择、在固定测试集上优化、best-of 报告），但无权限、信任范围或生命周期机制，且自身口径前后不一致，只能当反例引用。

### 2506.20807 GPU Kernel Scientist: An LLM-Driven Framework for Iterative Kernel Optimization

- 本地 PDF：`docs/paper/2506.20807_gpu-kernel-scientist-an-llm-driven-framework-for-iterative.pdf`
- 讲了什么：三阶段 LLM 进化循环。Evolutionary Selector 选 Base 与 Reference；Experiment Designer 先列 10 条"研究路线"、再出 5 个实验方案并自评收益区间与创新度，按"最新颖/最高上限/最高下限"选 3 个；Kernel Writer 出 diff 版 HIP 核。候选提交给 AMD Developer Challenge 2025 外部平台，只用端到端计时作反馈；目标是 MI300 上的 FP8 GEMM，无 profiling 数据、无核库、为做"好公民"逐个串行提交。前期由 LLM 自行探测硬件怪癖，产出一份 findings 文档供后续轮次使用。
- 关键证据：单个 GEMM 核、18 个矩阵尺寸的几何平均、计时取 18 个种子：PyTorch 参考 ≈850 µs，人类第一名 105 µs（前 8 名有真机），朴素 HIP ≈5000 µs，本工作 ≈450 µs。即比人类专家慢 4.3×、比 PyTorch 快 1.9×。没有显式选择机制、没有多样性增强，选父本全靠 LLM 判断；无 profiling 时靠"只改一个因素再测"做隔离实验。作者自述 LLM 偶尔"决定不执行整套实验 rubric"却仍在报告里写成做了。
- 局限与不可直接外推：(1) n=1 的核、4+1 页 workshop 论文，数字只与同一场比赛的三个点比较，无重复实验与置信区间。(2) 反馈只有端到端计时，分不清"改对了"与"噪声"；正确性由比赛平台判，无法审计，除编译外没有安全检查。(3) 选择与假设全交给模型（选父本、10 条路线、5 个方案、自评创新度），没有客观打分器，不可复现；作者自己承认这替代不了显式选择机制。(4) AMD HIP/rocWMMA/MI300 的硬件细节不能外推到 Metal；findings 文档是 LLM 自撰、未经核验就进入后续 prompt 的知识。
- 对本仓库的具体价值：成绩不值得引，机制有两处直接对得上。其一，findings 文档 = 模型自撰、无来源无验证却被下一轮当成可信上下文，这正是 backends/metal/wiki 与 experience.md 的对手模型；我们已经把 experience.md 算进 prompt 指纹（README 明说会影响 grant），所以这类自撰知识必须有来源、作用域与失效条件，plan-07 的 staging / reported 不进 TASK / 人工去重就是这条的落地。其二，"自述与实际行动不一致"直接支持我们的纪律：评审 P1/P2 提案看 diff 与实际测试，不看模型自述，review.py 的 evidence 检查同理。其三，把父本选择交给 LLM 与 KernelBand 那条 0.97× 负结果同向，可作 P0 premise 反对"让模型改路由或改评分"。其四，它"只有计时没有 profile"时退回隔离实验；我们有 hwfeedback + roofline，不应退回。
- 初步价值：中，3 分。证据薄（n=1、workshop 短文），但 findings 文档与"自述不可信"两点正好落在我们的经验生命周期与评审纪律上。
- 最终层级：B（主代理校准）
- 可信 harness 候选：borderline。它把"模型自撰知识成为下一轮可信上下文"做成了机制，相关面是注入面与经验生命周期；但论文没有分析信任边界，判据来自我们自己的 plan-06/07，成绩与选择机制不可搬。

### 2404.18249 Tenspiler: A Verified-Lifting-Based Compiler for Tensor Operations (Extended Version)

- 本地 PDF：`docs/paper/2404.18249_tenspiler-a-verified-lifting-based-compiler-for-tensor-operations.pdf`
- 讲了什么：用验证式提升把普通 C++/Python 循环程序翻译成张量运算。把目标 DSL 算子建模成统一张量代数 IR（Tensir），翻译表述为 SyGuS 问题（Rosette 搜索 + CVC5 验证）：先在受限程序状态（张量长 2、整数 ≤6 位）有界合成，再对全部程序状态验证 ¬VC 不可满足才接受，失败则加阻塞约束重搜或放宽界；最后按语法规则生成 6 个后端（NumPy/TensorFlow/PyTorch/MLX/TPC-C(Gaudi)/Gemmini）的代码。范围是串行循环→张量 DSL，不是 GPU 核生成。
- 关键证据：10 个真实套件共 69 个函数（blend 12、Llama 11、blas 2、darknet 10、dsp 12、dspstone、makespeare、mathfu 11、simpl_array 5、utdsp），全部在 15 分钟内合成（超时 1 小时）。相对 gcc -O3 串行 C++：kernel 平均 105.1×、端到端 9.65×；分后端 PyTorch 244×、Gaudi(TPC-C) 241×、TF 46×、NumPy 26.1×、MLX 10.5×；比 Numba 手写 CUDA 平均快 1.87×。消融：去掉有界合成，12 个 blend 里 6 个超时、其余 2D 用例慢 36.75×；去掉表达式树，69 个里 42 个超时、其余慢 101.55×。LLM 对照：Claude Opus 为 MLX/Gaudi/Gemmini 生成的 linear_dodge 全错（Gaudi 那次幻觉出不存在的 TPC-C 库）。
- 局限与不可直接外推：(1) 验证在整数与实数理论上做（作者明说 SMT 对浮点支持差），而图像/深度学习核实际跑 float——"已证明"不等于 IEEE 浮点下等价。(2) 只处理 1D/2D（附录扩到 3D 的人工用例），要求源程序是规整循环嵌套；完全不覆盖线程/内存层次、tile、simd 语义，与 Triton→Metal 的 lowering 不是同类问题。(3) Gemmini 后端只有 10/69 能全用其 ISA 表达，其余回退到 CPU 串行 C，且结果取自模拟器、用更小随机输入——"部分验证"的边界没进分母。(4) 105×/244× 的分母是串行标量循环，是"搬到加速器"的一次性红利，不是核优化水平。
- 对本仓库的具体价值：(a) 它是 tcenv/verify.py 那段最有力的外部对照：我们固定答 verification: unsupported，理由正是"没有面向 Metal/AIR 的形式工具、随机差分只能找 bug 不能证明不存在"；Tenspiler 说明要做到"对全部程序状态成立"必须 SMT + 有界合成配合，而且它自己也只能对整数/实数做——所以"证明"这个词在我们报告里只能留给 verified，不能用来形容 domain_sweep 或三批确认。(b) 它的"有界合成→全状态验证"两段式与我们"抽样过→确认门"同构：有界那步只是启发式，判决留给 verifier；对应我们 guard band 与确认复测，搜索期 ok 不能当发布证据。(c) 部分回退（Gemmini 不支持就交回 CPU）提醒我们 coverage 必须写清"这段结果里有多少走了未验证路径"，等价于 coverage.kind/scope 与 domain sweep 的边界，否则"69/69 可翻译"会被读成"69/69 被证明"。(d) "新后端只需 65 行模板"对我们 backends/<id>/ 适配层的成本估计只有旁证价值。
- 初步价值：中，2 分。范式不同（串行循环→张量 DSL，不是核 lowering），但"证明 vs 抽样"的边界讲得最清楚，可为报告的措辞纪律提供外部依据。
- 最终层级：B（主代理校准）
- 可信 harness 候选：borderline。它直接关于"正确性主张的强度"（评测有效性的根），但没有执行、权限或生命周期机制，且其保证所属的类别（整数/实数、无 GPU 语义）与本仓库候选不同，不能当我们的验收依据。

### 2610.31034 CANNBot-CAKE: Collaborative Agentic Kernel Evolution for Ascend NPU

- 本地 PDF：`docs/可信harness/papers/2610.31034_cannbot-cake.pdf`

### 2603.23566 AscendOptimizer: Episodic Agent for Ascend NPU Operator Optimization

- 本地 PDF：`docs/可信harness/papers/2603.23566_ascendoptimizer.pdf`
- 讲了什么：在"经验稀缺"下优化 AscendC 算子，不训练模型。离线跑 Optimization Rewind：对现成最强实现，让 inverse agent **移除**一个可识别优化 motif（双缓冲、向量化、同步消除、尾块合并等），只保留"语义等价、能编译、正确、且实测变慢超过噪声阈值 τ_noise"的退化对，蒸馏为经验元组 ⟨Title, Bottleneck, Applicability, Expected Effect, Code Diff⟩ 入共享经验库。在线 Stage I 按瓶颈症状检索元组改写 kernel，只接受通过校验且更快者；Stage II 在精炼后的 kernel 下用硬件在环演化搜 host tiling 模板。
- 关键证据：101 个 cann-ops 真实算子、910B2 + CANN 8.3、DeepSeek-V3.2，统一 230 次硬件评测/算子（其中 20 次给 rewind）：几何均值 1.21×，仅 53.47% 算子快于参考；分难度 1.24/1.10/1.89×，同预算下 BoN 1.04/1.05/1.38、OpenEvolve 1.11/1.03/1.45。消融：Stage I 独跑 1.16×，去掉经验降至 1.09×（fast2.0 7.92%→3.88%），Stage II 独跑 1.02×，全系统 1.21×。反事实：给同样的 oracle 瓶颈描述但不给检索经验，100 次中仅 1 次达到目标延迟；再加官方 Best Practices 文档仍是 1/100。
- 局限与不可直接外推：(1) 传导式（transductive）设定：经验库在**同一批** 101 算子上挖掘、又在同一批上评测，作者自认属"系统自调优"而非零样本泛化，上限被高估。(2) 基准先过滤掉编译/正确/计时不稳的算子（幸存者偏差），部分小形状被放大，"101 算子"不是全集。(3) 1.21× 里近一半算子不快于参考；跨芯片、CANN 版本、仓库的迁移被明确列为未做。(4) 工程不可用：代码/实验/文档未公开，Theorem 3.1 只是把验收规则写成定理，不构成保证。
- 对本仓库的具体价值：本组对我们**经验生命周期**最直接的一篇。(a) "移除后实测变慢且超过噪声阈值"才承认一条经验，等于给每条经验配了可证伪的移除检验，可写进 `experience.md` 准入：每条 tip 必须附"去掉它会怎样"的可测预期；(b) 五元组字段（瓶颈/适用条件/预期效果/代码差分）几乎就是计划中的经验 schema，也与 harness-feedback 的 tip + 前提 + 归属结构对齐；(c) "按瓶颈症状而非算子身份检索"是 trust scope 在检索侧的表达；(d) 1/100 的对照量化了"文档不等于经验"，反对把 wiki 原文直接塞进提示词。别学它的传导式评测。
- 初步价值：高，4 分。给出可自动化的经验准入判据与可量化的检索价值，但评测设定与代码可用性打折。

### 2512.23424 AKG kernel Agent: A Multi-Agent Framework for Cross-Platform Kernel Synthesis
