# 当前工程做不到什么

本文只写边界。系统怎么分工见 [架构说明.md](架构说明.md)。不需要先懂机器学习。

读完记住四句：

1. **算对是抽查，不是证明。** 没找到错例，不等于所有输入都对。
2. **留下的那一版可以比现成库更慢。** 另开一次搜索，默认不拿上次的好稿接着改。
3. **图形芯片同时画屏幕。** 超时会杀掉进程，死循环仍可能把电脑冻住几秒，甚至要按电源键重启。
4. **论文的方法在这台机器上只对上了一部分。** 搜索能打平现成库；「再多告诉模型硬件细节就会更快」没有测出来。论文用 GPT-6 Astra，我们用 DeepSeek，这是差距的一个原因；同一颗 DeepSeek 把预算加到 $15 已经能打平现成库。他们在 NVIDIA 上的具体倍数，我们没有重跑，核验不了。详见第 6 节。

## 1. 先别把它当成什么

| 容易当成 | 实际是 |
| --- | --- |
| 一个能编译任意计算的编译器 | 只做仓库里写好的那些题。要加新题，得自己交题目、标准答案、现成库和一份写得慢但算得对的小程序 |
| 大模型保证写出更快的程序 | 它只写文字。留下的稿子只是这次搜出来的里面，又安全、又在抽到的输入上合格、并且比**这次里的其他合格稿**更快。相对现成库的倍数可以小于 1，小于 1 就是更慢 |
| 和论文里「证明与 Triton 等价、并且超过 NVIDIA 上的 Triton」同一句话 | 这里没有面向 Metal 的形式证明。可选的 triton-msl 对照是估计，而且比「超过 NVIDIA 官方 Triton」弱 |
| 下次会自动接着上次的好结果磨 | 再执行一次 `taic run`，会新建目录，让模型重新写第一版。上次的 `best.metal` 还在磁盘上，搜索不会去读它 |

验收仍然只是：自检命令能打出成绩单；搜索结束后目录里有 `result.json`，有合格稿时还有 `best.metal`。验收里没有「一定比 MLX 快」。

## 2. 算对盖不住的洞

资格在代码里是 `EvalReport.eligible`：成绩单状态为 `ok` 就合格。它只表示安全检查过了，并且抽到的那些输入落在允许误差里。

`tcenv/verify.py` 的 `verify()` 是形式证明的空位。现在固定回答 `unsupported`（没有面向 Metal 的证明工具）。这个结果写进成绩单，**不参与**过不过。不能把「没证明」读成「已证明」，也不能读成「已证伪」。

把一种 16 位浮点的全部取值都跑过，也只覆盖那一个输入的数值域。那不包括线程是否互相独立、下标和边界、并发，以及所有启动配置，所以不是整个内核的证明。将来若做有界检查，范围写在 `scope` 里，并且不能改 `EvalReport.eligible`。

抽查本身还有这些边界：

- 输入是按名字造的几组随机数（普通、很大、很小、正负抵消、NaN 和无穷大等），不是所有可能的输入。
- 图形芯片用的是较粗的小数（FP16 或 BF16）。允许和 CPU 上更精细的答案有一点差。现成库自己更差时，允许的误差会放到库的误差的 2 倍，并且不超过 8 倍。所以「通过」可以是「没比一个本身就算得不太准的库差太多」。
- 安检只拒绝写明的 `while (true)` 和没有条件的 `for (;;)`，以及不是苹果标准头的 `#include`。一个条件看起来会结束、实际上永远不结束的循环，安检抓不住。
- 杀掉工作进程是事后补救。正在图形芯片上跑的小程序无法被中途抢走。单次启动超过 2 秒（芯片自检时 4 秒）会发杀死信号；电脑仍可能卡住。一次超时后，整次搜索停止。
- 真正往芯片上扔死循环的测试默认不跑。

## 3. 更快盖不住的洞

- **对照可以很弱。** 有的题（例如 Lion、把权重压成比特再做的矩阵乘）没有现成的、把步骤合在一起的库算法。手写的慢版本已经超过对照时，倍数里有一部分是对照弱。
- **计时锁只管本仓库。** 别的程序同时用图形芯片，测出来的时间仍会变慢。波动太大时会重测，最多 3 次；三次都吵，成绩单会标成不安静，搜索仍可能收下这份数。
- **复测减小碰巧。** 结束时把最好的和误差范围内的并列者再用新随机数测一遍。这去掉「在很多嘈杂测量里挑最大的那个」的偏差，没有变成精确到百分之一个位数的保证。
- **启动规模不能改。** 切成多少块、每块多少路，写在题目的契约里。模型不能靠改开多少路来提速。
- **成绩单会被截短。** 发回给模型的文字大约到 6000 字为止。排在后面的问题，它可能看不见。
- **交卷前的自查不报时间。** 所以它不能靠某一次碰巧很快给自己加分；相对地，它在正式判卷之前也不知道这份改动快了还是慢了。
- **帮它看芯片细节的开关默认关着。** 用 Instruments 录「还比现成库慢」的稿子（`profile_poor`）、静态检查缺了哪些芯片特性（`hw_feedback`）、每轮留一种小改（`plan_mix`）、搜索结束后再录优胜稿（`profile_best`），都要另外打开。关着时，它主要靠成绩单里的时间和「离理论最快还差几倍」。苹果这块芯片能稳定读到的硬件计数器，本来就比 NVIDIA 那套剖析少；没有事先准备好的 Instruments 模板时，更细的计数器读不到。
- **钱可以略微超出预算。** 闸门拦的是下一次请求。已经发出去的那一次仍会计费。供应商已经计费、本地转录还没写下时进程死了，续跑账本会少算（`cost_may_be_incomplete`）。`budget_events.json` 有一行没写上就丢掉，不能当成完整账单。这不是硬的美元上限。和供应商账单逐笔对账要另外授权。

## 4. 一次运行盖不住下一次

好结果会写在 `runs/<这次>/`：每一稿、`best.metal`、`result.json`。这个目录不进 git，换一台机器就没有。

| 你想做的事 | 现在会怎样 |
| --- | --- |
| 同一道题再搜一次，希望从上次的好稿接着改 | 不会。新目录，重新写第一版。默认只抽 1 份第一稿（`init_samples`） |
| 批量实验里已经做完的题再跑 | 默认跳过。这是不重复整道题，不是接着优化 |
| 钱用完了，或进程中途死了，但已经有一份合格稿 | 可以加预算后续跑，网页上的「加预算」就是这件事 |
| 因为收敛、轮数用完、图形芯片挂死或模型接口出错而停下 | 不能续。要再搜就新开一次 |
| 中途死掉时一份合格稿都还没有 | 不能续。没有可以接着改的底稿 |

跨次会复用的只有机器测量：这台机器的最快速度、可选的 triton-msl 对照、批量实验里那份手写慢版本的参照。这些不是模型写过的好稿。

## 5. 机器和题目的范围

本节给改代码的人。只想知道能不能拿去当通用工具的人，到这里可以停。

- 目标是这台 Mac 的苹果图形芯片。没有 NVIDIA 那条路，也不做 FP8。
- BF16 / FP32 特别小的「次正规数」会被这颗芯片变成 0。测试里的很小的数因此停在还能正常表示的范围上，没有覆盖「小到会被变成 0」的那一档。FP16 的次正规数在测试范围内。
- Triton 在主环境里只是题目文本。用社区程序 triton-msl 把它编译成 Metal 要另装环境和苹果的 Metal 工具链；装不上，主路径仍能跑。那个对照按相对 MLX 的比例估算，不是和候选在同一次计时里头对头量出来的。
- 题目清单以 `tasks/__init__.py` 为准：`TASK_NAMES` 12 道，`PHASE2_TASK_NAMES` 再加 4 道。另有 `SEMANTIC_NAMES` 里故意把名字和注释写错的题，用来看模型是不是在读计算步骤。那几道题能失败。失败说明这一次它看了名字；通过也不说明以后每次都看代码。
- 新搜索的预设名是 `taic.llm.DEFAULT_PRESET`。具体预算和轮数在 `taic.toml` 与对应的预设文件里，不在这里再抄一份数字。没有记下预设的旧运行，续跑用 `base`。
- 网页不是纯只读。写入口在 `observe/app.py`：加预算、重置预算、改下次搜索的默认模型、停止正在跑的进程。权限检查在 `observe/actions.py` 和 `observe/settings.py`（回环地址、页面令牌、同源）。它不编译、不提交内核。

## 6. 论文里的话，我们核对到哪

论文是 arXiv 2609.36800（仓库里的 `docs/2609.36800v1.pdf`）。它在 NVIDIA 上让模型把 Triton 改成 PTX，并报告超过或打平厂商库和 Triton 编译器。我们做的是同一套循环，硬件换成这台 Mac 的苹果图形芯片，目标语言是 Metal。所以下面只回答「这套方法在这台机器上是否像论文说的那样」，不回答「他们表里的 NVIDIA 倍数是否测错」。

记录日期：2026-10-07。数字是当时 `runs/p1/` 里已经写完或仍在跑的搜索。另开一次搜索，这些倍数会变。

**对得上的。** 循环本身能工作：模型写核，机器编译、对答案、计时，只留下明显更快的一版。有余地的题会涨，已经贴着实测最快的题涨不动。

| 题 | 我们测到的 | 和论文哪句话对得上 |
| --- | --- | --- |
| Mamba-2（`runs/p1/mamba2`） | 从 0.62 倍涨到确认后的 1.46 倍（相对编译过的 MLX）。$3 花完时还在涨。离按直接算法算出的最快还有大约 2.3 倍 | 现成库没把这道题调到顶时，搜索能超过它 |
| 矩阵乘（`runs/p1/gemm_paper`） | 大约 1.00 倍 MLX，14.5 万亿次/秒，是这台机器实测矩阵峰值的 98% | 搜索能打平已经调好的矩阵乘 |
| FlashAttention（`runs/p1/fa_paper`，预算 $15） | 确认前最好 1.004 倍。对照是 Apple 的融合注意力，本身已到峰值的 89%，理论上最多再快约 13% | 打平强库是强结果。$3 的几次搜索多半还在 0.57 到 0.74 倍，见下表 |
| 赢的那几份核 | 用了这颗芯片的矩阵指令、在线 softmax、流水线（`runs/hw_features/REPORT.md`） | 优胜核会用上硬件专有指令。但计算受限的题里，第一份算对的核往往就已经在用矩阵指令，所以「用了矩阵指令」解释不了后来为什么这一稿赢 |

**对不上，或不能照单全收的。**

多喂硬件信息，没有让 FlashAttention 稳定变快。下面都是同一道题、大约 $3，只改了一个条件。倍数是结束时换了随机输入再测的确认值。

| 条件 | 目录 | 确认后相对最快现成库 |
| --- | --- | ---: |
| 默认 | `runs/p1/fa_flash` | 0.735 倍 |
| 换成上一代的 `deepseek-v4-pro`（V4，不是 V4.1） | `runs/p1/fa_pro` | 0.566 倍 |
| 加上 Instruments 计数器 | `runs/p1/fa_flash_prof` | 0.672 倍 |
| 换一种切块 64×32 | `runs/p1/fa_64x32t256` | 0.610 倍 |
| 换切块 32×16 | `runs/p1/fa_32x16t128` | 0.970 倍 |
| 预算加到 $15 | `runs/p1/fa_paper` | 搜索中最好 1.004 倍，第 13 轮时还在跑，确认值以结束后的 `result.json` 为准 |
| 每个算对的核再列「用了哪些特性、缺哪些」 | `runs/p1/fa_flash_hw` | 0.622 倍。第 2 轮因账户余额中断，不能用来判断这个反馈有没有用 |

$15 比 $3 更接近打平，更像是多搜了几轮。计数器和多写进提示里的硬件清单，都没有单独高于「默认」那一行。pro 那一行更低，原因在下面的模型表：它是上一代，不是同代里更贵的一档。

同一道题波动很大。只报最好的那一次，数字可以是测出来的，但不是典型值。论文的重复试验表如果给的是多次的均值，这个偏差会小一些。我们自己的 5 次重复还没跑完。

| 同一次测量里的两个数 | 较高的那个 | 较低的那个 | 在哪 |
| --- | ---: | ---: | --- |
| FlashAttention，不同次搜索的确认倍数 | 1.00 倍（$15 那次，搜索中） | 0.57 倍（`fa_pro`） | 上表 |
| 矩阵乘，搜索过程中的测量对换输入重测 | 1.005 倍 | 0.986 倍 | `runs/suite_full/gemm_fp16` |

成绩单会把模型带偏。反馈若按直接算法说「已经到峰值的 94%」，模型会去微调，而不是换算法。论文若也用直接算法的运算量来报「离峰值还有百分之几」，卷积这类题上会有同样的问题。

| conv2d 的时间 | 微秒 | 含义 |
| --- | ---: | --- |
| 按直接卷积算出的最快 | 932 | 成绩单里的理论下界 |
| torch-mps 实测 | 777 | 用了运算更少的算法，所以能快过这个下界 |
| 我们搜到的最好核 | 大约 995 | 相对 torch-mps 大约 0.78 倍。目录 `runs/repeat_20261007-015329/conv2d/` |

还有一块钱不是花在改核上。这是我们自己的接口记录，不是论文里的对照。DeepSeek 把思考和正文分开返回。思考很长、正文是空的、并且 `finish_reason` 是 `length` 时，就是额度用在了模型内部的长篇思考上，内核没有写出来。论文没有写 GPT-6 Astra 有没有同样把 token 花在看不见的思考上，所以不能说他们没有、我们有。

| 花费去了哪 | 占比 | 在哪 |
| --- | ---: | --- |
| `deepseek-flash` 把输出额度用在模型内部的长篇思考上，正文里没有核 | 13 次运行的模型花费里大约 37% | `runs/plan_type_analysis/REPORT.md`。依据是接口分开返回的思考和正文，加上 `finish_reason=length`。那些记录的单次上限是 48000 |
| 逐元素题第一稿已经贴着带宽屋顶之后，搜索还在继续花 | 总花费里大约 47% | 同一份报告 |

单次输出上限仍是 48000。2026-10-07 考虑过 96000，也考虑过接口最大值的一半 196608，当天改回 48000。请求超时仍是 900 秒。速度来自那批被截断回复里最慢的一次。

| 单次上限 | 按最慢实测速度写满 | 决定 |
| --- | ---: | --- |
| 48000 | 251 秒，大约 4 分钟 | 现在的默认，也是那些 37% 记录用的值。`taic.toml` 的 `max_tokens` |
| 96000 | 大约 8 分钟 | 当天考虑过，不采用 |
| 393216 的一半，196608 | 大约 17 分钟 | 不采用。等不了十几分钟 |

**模型不同，是论文自己标出的一档差距。** 第 4 节写明主实验的编译模型是 GPT-6 Astra。下面是他们在 FP16 矩阵乘上、同一套流程和同一笔推理预算的对比，对照的是 Triton 编译器。他们因此只拿 Astra 做后面的实验，并写了：有竞争力的降级只在最新的前沿模型上出现。

| 论文用的模型 | 相对 Triton |
| --- | --- |
| GPT-5.4 | 0.73 倍 |
| GPT-5.5、GPT-5.6 Terra | 0.87 倍 |
| GPT-5.6 Luna | 没有交出合格的核 |
| GPT-5.6 Sol | 0.97 倍 |
| GPT-6 Astra | 1.00 倍，他们对比里第一个打平的 |

我们的主实验叫 `deepseek-flash`。按 [DeepSeek API 更新日志](https://api-docs.deepseek.com/updates)（2026-09 起，2026-10-04 仍如此），这个名字现在就是 **DeepSeek-V4.1-Flash**。`deepseek-v4-pro` 仍是上一代 **V4 Pro**，不是 V4.1 里更贵的一档。官方还没有 V4.1 Pro。V4.1 Flash 在 DeepSeek 自己的代码和智能体评测上高于 V4 Pro（例如 DeepSWE v1.1：74.2% 对 62.7%），V4 Pro 只在部分推理题上略高（GPQA Diamond：92.4% 对 90.9%）。所以 flash 比 pro 好，是版本差，不是「便宜的意外赢了贵的」。

同预算下换过一次 `deepseek-v4-pro`。那是一次搜索。它说明：换到上一代，没有补上和 Astra 的差距。

| 我们用的模型 | 实际版本 | 题 | 确认后相对最快现成库 | 目录 |
| --- | --- | --- | ---: | --- |
| `deepseek-flash` | V4.1 Flash | FlashAttention，$3 | 0.735 倍 | `runs/p1/fa_flash` |
| `deepseek-v4-pro` | V4 Pro | FlashAttention，$3 | 0.566 倍 | `runs/p1/fa_pro` |
| `deepseek-flash` | V4.1 Flash | FlashAttention，$15 | 搜索中最好 1.004 倍 | `runs/p1/fa_paper` |
| `deepseek-flash` | V4.1 Flash | 矩阵乘，$15 | 大约 1.00 倍 | `runs/p1/gemm_paper` |

同一颗 flash 把预算加到 $15 之后，搜索已经能打平这台机器上的现成库。Astra 在 Metal 上会不会更好，没有跑过，差多少不知道。还叠着两件不一样的事：

| | 论文 | 我们 |
| --- | --- | --- |
| 对照是谁 | NVIDIA 上的 Triton 编译器 | 这台 Mac 上的 MLX / PyTorch |
| 模型内部的长篇思考占模型花费 | 论文没写 | flash 大约三分之一。只说明我们的接口记录，不能当成他们没有 |

一句话：这套循环有能力搜到打平现成库的核，优胜核也会用上硬件指令。再多给模型一些硬件反馈，加速比就会上去——这句话在这台机器上没有证据。模型不同是论文量过的真差距，头寸和预算在我们这边同样决定结果。

## 怎样核对本文没有说大

| 主张 | 在代码里看哪里 |
| --- | --- |
| 形式证明固定答「不支持」，且不影响过不过；穷举一种 16 位输入也不是整个内核的证明 | `tcenv/verify.py` 的 `verify()`；`EvalReport.eligible` 只看状态是不是 `ok` |
| 安检抓不住所有死循环 | `tcenv/screen.py` 只匹配 `while (true)` 和没有条件的 `for` |
| 新的一次搜索不读上次的 `best.metal` | `taic/orchestrator.py` 从「请模型翻译题目」开始；目录名带时间戳 |
