# 维护决策记录

记录会影响数据/协议、但不需要每次改代码的决定。新条目写在最上面。

每条的结构一样：先写决定，再写理由和边界。想看一项是已采用、默认关还是不采用，看文首两张表；想查生效的具体值，看后面的默认值表；想看为什么这样定，看对应日期那一节。

状态只用这四个词。`已采用` 是现在就这样做。`默认关` 是开关在，不开就不发生。`不采用` 是决定不做。`空位` 是还没有工具。

## 三个名字各管一个版本

`measure_serial = false` 和 `PROTOCOL_VERSION = "3"` 是 2026-10-22 同一天写下的两个字段。放在同一行里不表示「协议版本 3」等于「关掉串行对照」。

| 名字 | 当前值 | 它管什么 | 和另外两个的差别 |
| --- | --- | --- | --- |
| `PROTOCOL_VERSION` | 字符串 `"3"`，定义在 `tcenv/schema.py` | 测量协议。计时窗口、确认批或目标上限变了就加。旧运行保留旧值，用 `protocol_epoch` 分成几桶。当前 `"3"` 放进第 3 桶 | 它不是成绩单的文件格式，也不是续跑标签 |
| 评测请求与 `EvalReport` 的 `schema_version` | 整数 `4`。请求是 `REQUEST_SCHEMA_VERSION`，报告是 `REPORT_SCHEMA_VERSION` | 子进程请求和成绩单 JSON 的字段集。报告读入只认 4。请求版本 4 要求 `target_id`，并可带 `measure_serial` | 两个 4 是两套计数，只是现在数值相同。`result.json` 自己的 `schema_version` 是 1 |
| `loop_protocol` | 字符串 `"flame_chase_1"`，写在 `run_config.json` | `taic resume` 只接这个标签。其他目录可以读，不能续 | 它不调用 `hmz` 的 `flame_chase` 流程。更早的目录若把测量协议记成这串字，读侧放进 `protocol_epoch` 的第 2 桶 |

## 2026-10-24 · 父进程被杀后的 hmz 孤儿会话与 cost_incomplete 续跑

- 终止信号处理器从 SIGTERM/SIGINT 扩到 **SIGTERM/SIGINT/SIGHUP/SIGQUIT**。关闭 IDE/终端窗口发的是 SIGHUP；以前它会让 `hmz` 会话活下来继续调用 provider，而父进程已经无法记账。
- `taic/kernel_agent.py::epic_spend_by_label` 读 `~/.hmz/epics/.../epic.jsonl`，按 workspace 的会话标签汇总 `usage.cost`。resume 时与 `transcript.jsonl` 里同一标签已记账的成本比较，只把正差写成一条 `unaccounted`；不重复计费，也不跨 run。
- `cost_incomplete` 默认仍不可续（没有 token 账单不能自动继续）。`taic resume RUN --accept-cost-gap` 是人的显式确认：先完成 epic 对账，再继续跑；对账差额进 `unaccounted`，历史文件另存为 `*.before_topup_<n>.json`。
- 这仍不是硬上限：已经在飞的会话可能超预算；对账只保证已发生的 `hmz` 会话尽量不漏记。

## 2026-10-23 · 尾段预算门槛与寄存器提示去误导

- 新会话开始前用最近三场已完成模型会话的成本中位数做门槛；剩余预算低于这个中位数时停止，不再开一场注定只能复测种子的会话。`result.json` 记 `session_budget_stop=true`；这仍是 `budget_exhausted`，但没有新增预算时 `taic resume` 会要求 `--add-budget/--budget`，有足够 top-up 才继续。该门槛不改评测 reps、不伪造会话成本。
- `maxTotalThreadsPerThreadgroup` 不再被报告/反馈直接解释成“寄存器压力”或“提高线程数会更好”。它只是管线的线程组上限；没有显式属性时通常等于设备上限，低值也可能来自线程组内存。要判断 spill 需要编译器或计时证据。
- 消融方法论（DCE、寄存器释放、同指令数对照）先作为 P2 skill 候选，等 review 和人工确认，不自动改技能文件。

## 2026-10-22 · code agent 只做 P2 执行者，不做信任来源

- 已批准提案默认交给 code agent 在 worktree 里实现、补测试、生成 patch；人也完全可以自己做。人看 diff 后 apply/commit。
- 实现者不继承模型覆盖层的信任；AI 实现者不能自批、自 merge、改 `trust.toml`/预算/控制文件；人实现时也不能自批自己的 P2。`implemented_by` 与 `approved_by` 必须是不同角色。
- `change_ref` 在 git 提交时生成，形如 `commit:<sha>`；本地阶段用 `local_patch_sha256` 追溯。审计加 `implemented_by`/`approved_by`/`tests_run`。已提供 `taic/code_agent.py` 的 worktree 代码补丁 worker；它不自动 commit/merge。`apply-code` 写 `code_promotion`/`status=local` 且 `change_ref` 为空；`taic harness commit` 同时处理 `promotion` 与 `code_promotion`，提交前校验补丁哈希，在独立 Git index 中从 HEAD 顺序重放并比较暂存快照，拒绝漂移。

## 2026-10-22 · `data/deleted` 保留 30 天，手动清理

- 默认 TTL：**30 天**（`taic gc --older-than-days 30`）。
- 默认只报告；只有显式 `--apply` 才删除，并在 `data/deleted/gc_log.jsonl` 追加审计行。
- 不做自动定时删除。运行 `taic gc` 的频率建议每月一次，或在大规模批跑前看一次 dry-run。
- 理由：删除不可逆；30 天覆盖一次“跑完—汇总—发现问题—回滚”的周期，又不会让 `data/deleted` 无限增长（当前约 266MB）。

## 2026-10-22 · `candidate_serial` 默认关闭，`eval_cache` 默认开启

- 2026-10-22 A/B（3 轮 × conv2d/flash_attention/relu）：串行对照占计时 GPU 的约三分之一；关闭后墙钟下降 4–8%，候选中位数差 −0.8% / +0.1% / +1.1%（在 2–4% 的 cv 内，无系统偏差）。完整说明见 `docs/架构/数据层.md` §3.3。
- `measure_serial = false`，`PROTOCOL_VERSION = "3"`；旧 run 保留旧值，用 `protocol_epoch` 分桶。`taic resume` 只接 `loop_protocol = flame_chase_1` 的目录；更早的目录可读、不能续。这三个名字各管一件事，对照见 [三个名字各管一个版本](#三个名字各管一个版本)。
